# 알림 발송 기준

> `AI/notify/` 가 무엇을 내보내고 무엇을 막는지. 코드(`config.py` · `nodes.py`)가 이 문서를 따른다.
> 설계 배경은 [AGENTIC.md](../AGENTIC.md) 2장 "도구 연동".

## 0. 다시 쓰지 않는다

보낼 글은 이미 정해져 있다 — **Gate 2 에서 교사가 승인한 인사이트**다. 코드가 그대로 이어 붙인다.

```
START → assemble → check ─┬─(통과)─→ send → END
                          └─(막힘)──────────→ END
```

| 노드 | 하는 일 | 모델 |
| --- | --- | --- |
| `assemble` | 승인된 글을 이어 메일을 만든다 | 안 부름 |
| `check` | 다른 아이 이름이 없는지 본다 | 안 부름 |
| `send` | 통과한 것만 MCP 로 내보낸다 | 도구 |

### 전에는 모델을 불렀다 (#419 → #433)

처음에는 `compose` 노드가 Luna 를 불러 교사용 글("~했다")을 보호자용("~했어요")으로 다시 썼다.
인사이트가 해요체로 통일되면서(#433) 할 일이 없어졌다 — **해요체를 해요체로 다시 쓰는 호출**이었다.

**중복이라서만 뺀 것이 아니다.** 승인 뒤에 다시 쓰면 "교사가 승인한 문장 = 보호자가 받는 문장" 이
또 깨진다 (#430 리뷰). 통일로 얻은 것을 발송 단계가 도로 잃는다. 지금은 승인된 글자를 코드가
그대로 복사하므로 **구조적으로 같다.**

덤으로 사라진 것: 발송 시점 LLM 비용·지연, `503 llm_unavailable`, 그리고 "모델이 지어낸 숫자·기관"
이라는 실패 종류 전부.

## 1. 손대는 것과 안 대는 것

| | |
| --- | --- |
| 인사이트 본문 | **한 글자도 안 고친다.** 고치면 교사가 승인한 글이 아니다 |
| 제목 · 인사말 · 맺음말 | 코드가 쓴다. 아이 기록이 아니라 틀이라 승인 대상이 아니다 |

```
Subject: [잇다] 김지후 이번 주 소식 (4월 1일 ~ 4월 7일)

김지후 보호자님, 이번 주 소식입니다.

<승인된 인사이트 1 — 글자 그대로>

<승인된 인사이트 2 — 글자 그대로>

이 글은 선생님이 확인하고 보낸 내용이에요.
잇다 앱에서 근거가 된 일지도 함께 볼 수 있어요.
```

## 2. 수신자는 계약에 없다

`NotifyInput` 에 이메일 주소가 없다. `child_id` 만 있고, 주소는 MCP 서버가 찾는다.

```
❌ send_email(to="parent@example.com", ...)
✅ send_email(child_id=12, ...)   ← 주소는 서버가 찾는다
```

`insight/tools.py` 의 `find_claims` 와 같은 원칙이다 — **모델은 무엇을 보낼지만 정하고, 어디로 갈지는
코드가 정한다.** 지금은 모델이 아예 없지만 원칙은 그대로 둔다: 주소가 어느 모델 문맥에도 들어가지 않는다.

로그에도 주소가 없다. **받는 사람 수만** 적는다.

## 3. 무엇이 걸리는가 — 하나

| 이유 | 언제 |
| --- | --- |
| `다른아이이름` | 다른 아이 이름이 메일 제목이나 본문에 있다 |

숫자·기관·근거번호 검사는 **의미가 없어져 뺐다** — 승인본을 글자 그대로 복사하니 어긋날 수가 없다.

### 이 검사가 유일한 코드 방어선이다

**인사이트 입력(`InsightInput`)에는 다른 아이 이름 목록이 없다.** 그래서 AI 는 이 검사를 못 하고
프롬프트 규칙(`DROP_OTHER_CHILD_NAMES`)뿐이다. 메일은 기관 경계 밖으로 나가는 길이라 여기서 한 번 더 본다.

**승인된 글이어도 막는다.** 승인은 그 기관 안에서 한 판단이고, 메일은 밖으로 나가는 일이다.

> ⚠️ **메일만 지킨다.** 같은 글이 보호자 앱 화면(`GuardianInsightService`)에는 이 검사 없이 그대로 뜬다.
> 제대로 막으려면 BE 가 인사이트 요청에 다른 아이 이름을 넣고 AI 가 생성 시점에 봐야 한다 — 별도 과제다.

## 4. 한 줄이 걸려도 통째로 막는다

요약은 근거 없는 문장만 빼고 나머지를 낸다 (`summary/CRITERIA.md §2`).
메일은 **한 줄이라도 걸리면 전체를 막는다** (`config.BLOCK_WHOLE_MAIL`).

- 한 줄 빠진 메일은 **교사가 승인한 적 없는 조합**이다
- 보낸 뒤에는 되돌릴 수 없다. 요약은 교사가 Gate 1 에서 다시 보지만, 메일은 이미 받은편지함에 있다

## 5. 끝나는 길은 다섯이다

| 응답 | 뜻 | BE 가 할 일 |
| --- | --- | --- |
| `200 sent` | 나갔다 | 끝 |
| `200 no_recipient` | 글은 통과했는데 **받을 사람이 없었다** | 끝. 장애가 아니다 |
| `200 nothing_to_send` | 승인된 인사이트가 없었다 | 끝 |
| `200 blocked` | 다른 아이 이름이 섞였다 | **교사 확인 큐로.** 재시도하지 않는다 |
| `503 delivery_failed` | 메일 서버 장애 | 재시도 |

`llm_unavailable` 은 **없다** — 모델을 부르지 않는다.

`no_recipient` 를 `sent` 로 묶지 않는다 (#430 리뷰). 장애는 아니지만 **메일은 안 나갔다.**
합치면 BE 가 `SENT` 로 적고 교사는 "보냈다" 고 믿는데, 실제로는 아무에게도 안 갔다.

**근거 미달을 503 으로 올리면 BE 가 영원히 재시도한다.** 반대로 메일 서버 장애를 `blocked` 로
내리면 교사가 고칠 수 없는 것을 큐에서 본다. 요약의 `llm_unavailable` ↔ `no_grounded_claims` 와
같은 구분이다 (#148).

## 6. 같은 묶음은 한 번만

`notification_id` 가 멱등성 기준이다. 같은 값으로 다시 오면 보내지 않고 처음 `message_id` 를
그대로 돌려준다. BE 재시도가 보호자에게 메일 세 통이 되면 안 된다.

기록은 MCP 서버가 `evals/generated/notify/sent.json` 에 남긴다.
**본문은 남기지 않는다** — 아이 기록이다. 식별자와 받는 사람 수만 적는다.

구멍 둘을 막았다 (#430 리뷰).

- **동시 호출** — 보내기 전에 파일 락을 잡고 자리를 먼저 적는다. 안 그러면 같은 키가 동시에 두 번
  왔을 때 둘 다 "기록이 없다" 를 보고 각자 보낸다
- **보호자 여럿** — 한 명 보낼 때마다 적는다. 둘째 보호자에게 보내다 SMTP 가 끊겨도, 다시 부르면
  첫 보호자는 건너뛴다

`delivered` 에는 주소가 들어 있어 도구 응답에서 가린다.

## 7. 코드가 막지 못하는 것

- **명부에 없는 아이 이름.** `other_child_names` 에 있는 이름만 본다. BE 가 안 보낸 이름은 모른다
- **말투.** 인사이트 쪽에서 재고 막지 않는다 (`insight/CRITERIA.md §8-b`). 여기서는 보지 않는다
- **지어낸 사실.** 승인된 글을 그대로 보내므로 이 단계에서 생길 일은 없다. 생겼다면 인사이트 쪽 문제다

## 8. 아직 안 한 것

- 블라인드 측정. 다른 아이 이름이 섞인 승인본을 일부러 만든 세트로 **막히는 비율**을 재야 한다
- 보호자 이메일 수집 — #420 (시연은 `evals/generated/notify/recipients.json`)
