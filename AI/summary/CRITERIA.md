# 요약 판정 기준

**이 문서가 기준이고 `config.py` 가 그것을 따른다.** 어긋나면
`evals/scripts/summary/test_criteria_sync.py` 가 깨진다.

---

## 0. 요약에는 판정이 없다

매칭은 `auto / review / multi / unmatched` 중 하나를 고르고, 검증은
`PASS / REVIEW / BLOCK` 중 하나를 고른다. 요약은 고르지 않는다. **글을 쓴다.**

그래서 재는 것이 다르다.

| | 매칭·검증 | 요약 |
| --- | --- | --- |
| 하는 일 | 고른다 | 쓴다 |
| 틀리는 방식 | 잘못 골랐다 | **지어냈다 · 빠뜨렸다** |
| 기준 | 어느 status 가 정답인가 | **무엇을 버리는가** |

임계값이 없는 것은 그래서다. 아래 규칙은 전부 불리언이다.

---

## 1. 묶음 단위는 아동 × 날짜 × 기관이다

**기관을 가로지르지 않는다.** 한 기관이 같은 아이에 대해 같은 날 쓴 기록들만
한 편으로 묶는다.

초안은 기관을 가로질렀다. 2026-10-05 에 되돌렸고, 이유가 셋이다.

**① Gate 1 에 승인할 사람이 없어진다**

승인 주체는 그 기록의 **작성자**다. 세 기관 기록을 한 편으로 묶으면 작성자가
셋이다. 햇살학교 교사가 승인하면 늘봄센터가 쓴 문장을 읽고 고쳐서 내보내는
셈인데, 그 교사에게 센터 기록을 볼 권한이 있다는 보장이 없다.

**② 승인 전에 이미 섞인다**

BLOCK 기록을 요약에 넣지 않는 이유와 같다 — 교사가 그 글을 읽는 순간 이미
공유다. Gate 1 은 내보내기 전 검토인데, 묶는 시점이 그보다 앞선다.

**③ 동의가 기관별이다**

`sharing_consent(child_id, guardian_id, organization_id, scope, status)` 로
보호자가 기관 단위로 정한다. 묶으려면 매번 "이 기관들이 서로 다 `ACTIVE` 인가"
를 확인해야 하고, 한 곳이 `REVOKED` 되면 합본을 다시 만들어야 한다.

### 기관을 가로지르는 문장은 인사이트가 만든다

```
기관별 요약 → [Gate 1 그 기관 작성자] → child_context ┐
기관별 요약 → [Gate 1 그 기관 작성자] → child_context ├→ 인사이트가 가로지른다
기관별 요약 → [Gate 1 그 기관 작성자] → child_context ┘
```

> `schema.md §9.2` — Insight 는 원본이 아니라 **`child_context` 를 기반으로** 분석한다.

"학교에서는 혼자 했는데 센터에서는 도움이 필요했다" 는 사라지지 않는다. 그 문장이
나오는 자리가 요약이 아니라 인사이트일 뿐이다. 승인을 거친 글들 위에서 만들어지므로
권한과 동의도 그때 한 번에 본다.

**한 기관 안에서도 묶을 것이 있다.** 같은 날 오전·오후 기록이 따로 올라오고,
그 사이의 변화가 하루의 흐름이다.

### 읽는 사람은 부모가 아니다

```
요약 → [Gate 1 교사 승인] → child_context → 인사이트 → [Gate 2] → 부모
                                 ↑
                      다른 기관 담당자가 조회하는 곳 (O-14)
```

교사가 검토하고, 승인된 뒤에는 **다음 돌봄을 하는 다른 기관 담당자**가 읽는다.
부모가 받는 것은 요약이 아니라 그다음 단계인 인사이트다.

## 2. 무엇을 버리는가 — 코드가 거르는 네 단계

모델이 내는 것은 `claims` 뿐이다. 본문도, 좌표도, 반영된 일지 목록도
모델에게 받지 않는다.

```
모델이 주는 것   claims = [{ text, evidence: [{ journal_entry_id, quote }] }]

① 인용을 원문에서 찾는다            못 찾으면 그 근거를 버린다
② 근거 0 개가 된 문장을 버린다
③ 고유명사가 근거에 없으면 버린다    이름 · 숫자 · 시간 · 기관명
④ 남은 claims 로 본문을 잇는다       순서는 claims 배열 순서다
   남은 근거로 covered 를 센다
```

| 단계 | 플래그 | 왜 |
| --- | --- | --- |
| ① | `DROP_UNFOUND_QUOTES` | 다듬은 인용은 원문이 아니다. 조사만 바꿔도 버린다 |
| ② | `DROP_CLAIMS_WITHOUT_EVIDENCE` | 근거가 아예 없는 문장만은 코드가 막는다 |
| ③ | `CHECK_PROPER_NOUNS` | 환각이 가장 눈에 띄게 드러나는 자리다. 기관명 대조는 묶음이 한 기관이 되면서 필요 없어졌다 |

#### 날짜의 숫자는 관찰의 숫자가 아니다

③ 이 보는 숫자는 **횟수·시간·층수 같은 관찰 내용**이다. 날짜를 가리키는 숫자는
입력으로 받은 값이라 근거가 없어도 되지만, **그 문장에서 날짜로 쓰였을 때만**
면제한다 — 연·월·일 단위가 붙어 있고 묶음 날짜와 값이 같아야 한다.

```
묶음 날짜 2026-10-07

"공을 7번 주고받았다"        인용에 7 이 없으면 버린다   ← 날짜의 7 은 근거가 아니다
"10월 7일 체육에 참여했다"    둔다                      ← 날짜 표현이고 묶음 날짜와 같다
"10월 9일 체육에 참여했다"    버린다                     ← 묶음 날짜와 다르다
"오전 7시에 등원했다"        인용에 7 이 없으면 버린다   ← 시간은 관찰 내용이다
```

예전에는 `entry_date` 의 숫자를 통째로 면제했다. 그러면 2026-10-07 에 쓴 요약에서
`7번` · `10번` · `2026번` 이 전부 통과한다 — **날짜 숫자가 관찰 횟수의 근거가 된다**
(2026-10-08 멘토 리뷰).
| ④ | `CONTENT_FROM_CLAIMS_ONLY`<br>`COVERAGE_FROM_EVIDENCE` | 본문을 따로 받으면 claims 밖 문장이 검사를 안 거친다 |

### 인용은 최소 구간만

얼마나 가져올지를 말하지 않으면 모델은 **일지를 통째로 복사한다.** 줄일수록
버려질 위험만 커지기 때문이다. 대조는 통과하지만 Gate 1 에서 하이라이트가
일지 전체라, 교사가 "이 문장 어디서 나왔지" 를 눌러도 아무것도 알려주지 못한다.
그 클릭이 Gate 1 에서 교사가 하는 일의 전부다.

검증이 `#59` 에서 쓴 "판정 근거가 된 최소 구간만" 과 같은 계약이다.

```
2026-10-06 dev 12건          규칙 추가 전   후
인용 길이 ÷ 원문 길이 중앙값      1.0       0.404
일지를 통째로 인용한 근거      21/23       6/35
버려진 근거                     0/23       0/35
```

**짧게 줄이되 원문에서 끊기지 않고 이어진 한 구간**이어야 한다. 띄엄띄엄 이어
붙이면 `content.find()` 가 못 찾아 그 근거가 통째로 버려진다.

1.0 이 늘 나쁜 것은 아니다. 문장이 실제로 일지 전체를 덮으면 1.0 이 정답이다.
통과 기준이 아니라 **기준선 대비 변화**로 본다.

### 좌표는 모델이 주지 않는다

모델은 글자 수를 세지 못해 `start / end` 를 거의 틀린다. 인용문만 받고 위치는
`spans_for_quotes` 가 찾는다 — `matching/llm.py:126` 에 이미 있는 방식이다.
**좌표를 지어낼 자리 자체가 없어진다.**

### 전부 걸러지면 빈 요약을 내보내지 않는다

재료를 받았는데 ①②③ 을 지나 남은 문장이 **하나도 없으면** 200 으로 돌려주지 않고
`NoGroundedClaims` 를 올려 **503** 으로 응답한다.

빈 요약을 200 으로 주면 교사가 빈 글을 승인하고 일지는 반영된 것처럼 닫힌다.
BE 도 빈 `claims` 를 저장하지 않고 요약 전체 실패로 본다 (`#146`).

```
모델을 못 씀 (LlmUnavailable)      503  llm_unavailable      BE 가 재시도
근거가 하나도 안 남음              503  no_grounded_claims   같음 — 다시 부르면 될 수 있다
근거·좌표가 어긋남 (BE 재검사 실패)  AI 버그다. BE 가 요약 전체를 실패로 끝낸다
```

앞의 둘은 **이번 호출에서 못 한 것**이고 마지막은 **고쳐야 할 것**이라, 되돌릴
수 있는지가 다르다.

#### 503 은 하나가 아니다 — body 로 나눈다

앞의 둘은 상태 코드가 같지만 **BE 의 후속 처리가 다르다.**

```json
{ "detail": { "reason": "no_grounded_claims", "message": "근거가 남은 문장이 없음" } }
```

```
llm_unavailable      모델이 죽었다       차례를 통째로 멈추고 나중에 다시
no_grounded_claims   이 묶음이 안 됐다   그 묶음만 되돌리고 다음 묶음으로, 2번 넘으면 FAILED
```

상태 코드만 보면 BE 는 전자로 읽어 차례를 멈춘다. 그러면 근거가 늘 0 개인 묶음
하나가(예: "특이사항 없음" 한 줄) 후보 맨 앞에 남아 **뒤의 다른 아이들이 영영
처리되지 않는다** — 503 → 전체 중단 → 재시도 → 503 이 반복된다. "최대 2번" 도
무엇 때문인 503 인지 몰라 셀 수 없다 (2026-10-09 `#148` 박찬진).

`reason` 값은 예외 클래스가 들고 있다 (`common/errors.py`). 새 사유를 더할 때는
예외를 하나 더 만들고 `reason` 만 덮어쓴다 — `main.py` 는 고치지 않는다.

### 좌표는 저장되는 모양에서 필수다

`Evidence.span` 은 선택이 아니다. 원문에서 못 찾은 근거는 ①에서 버려지므로
저장 시점에는 항상 채워져 있다. BE 의 근거 재검사도 `span` 이 없으면 요약 전체를
실패로 본다 (`#146`) — 느슨한 쪽이 이 계약이었다.

### 코드가 막지 못하는 것

인용이 원문에 있어도 **그 문장이 그 인용으로 뒷받침된다는 보장은 없다.**
요약의 `text` 는 생성문이라 검증 에이전트와 사정이 다르다. 이 부분은
표본 판정으로 잰다 (§5).

## 3. 말투 — 돌봄 기관의 전문가 기록체

무슨 일이 있었고 어떤 대응이 통했는지가 중심이다. 감상이나 애정 표현은 쓰지
않는다. 길이는 고정하지 않는다 (`FIXED_LENGTH = False`) — 기록이 한 건인 날과
세 기관에서 온 날의 분량이 같을 이유가 없다.

말투를 다듬다 **내용이 바뀌는 것**이 진짜 위험이다. 두 가지를 막는다.

| 플래그 | 막는 것 |
| --- | --- |
| `KEEP_HEDGES` | "~인 듯함" → "~이다". 추측이 단정이 된다 |
| `DROP_SENTIMENT_KEEP_FACT` | 감정을 지우다 "대응이 어려웠다" 는 정보까지 지운다 |
| `ANONYMIZE_OTHER_NAMES` | 다른 사람 이름이 다른 기관까지 전파된다 |

**이 둘은 인용 대조로 안 잡힌다.** 헤지를 지워도 인용은 원문에 그대로 있다.
프롬프트 규칙으로 쓰고, 지켜졌는지는 평가에서 본다.

### 요약 대상이 아닌 사람의 이름은 쓰지 않는다

`ANONYMIZE_OTHER_NAMES` — 이름 대신 **관계**로 적는다.

```
"옆자리 서준호가 과자를 나눠 주자"   →   "옆자리 아동이 과자를 나눠 주자"
"형 김지원이 데리러 오자"           →   "형이 데리러 오자"
"박소연 선생님의 질문에"            →   "교사의 질문에"
```

막아야 하는 것은 **전파**다. 요약 본문은 `child_context` 를 거쳐 다른 기관과
인사이트까지 간다. 검증이 `다수아동언급` 으로 잡지만 `REVIEW` 라 교사가 승인하면
통과하고, 그다음을 막는 것이 없었다.

**가명을 쓰지 않는다.** 가명은 읽는 사람이 진짜 이름으로 믿고, 교사가 Gate 1 에서
원문과 대조할 수 없게 만들며, 같은 아이에게 같은 가명을 유지하려면 가명↔실명 표가
필요한데 그것이 또 하나의 개인정보 저장소가 된다. 관계어는 거짓을 만들지 않고,
모른다는 것까지 그대로 말한다.

**명부 안팎을 구분하지 않는다.** "다른 아동" 과 "기관 내 아동" 을 나누면 뒤쪽이
그 기관 명부 안이라는 뜻이 되어 범위가 좁혀진다. 익명화 수준을 세분화할수록
식별성이 올라간다.

**바꾸는 것은 `claims[].text` 뿐이다.** 근거 인용(`quote`)은 원문 그대로 둔다 —
고치면 원문에서 찾지 못해 그 근거가 버려진다 (§2 ①). 이름은 인용에 남지만,
인용이 가는 곳은 Gate 1 교사와 인사이트 **입력**까지다. 인사이트는 모델에게
인용을 보여주지 않고 출력에도 담지 않으므로, 체인 밖으로 나가지 않는다.

```
quote 가 머무는 곳   summary_result.claims · 인사이트 입력
quote 가 안 가는 곳   인사이트 출력 · child_context · Gate 2 · 부모
```

```
2026-10-07 dev 8건        규칙 전   규칙 후
명부 안 아이 이름이 본문에   6 / 6     0 / 6
명부 밖(형·교사·옆 반 아이)    —       0 / 2
근거 인용에 남은 이름        —        7건 (원문이라 정상)
```

#### 남았으면 사람이 보게 표시한다

`REVIEW_ON_OTHER_NAMES` — BE 가 보내는 `other_child_names` 를 본문과 대조해,
이름이 남아 있으면 출력에 표시한다.

```
needs_review     true
review_reasons   ["다른아동이름"]
```

**막지 않는다.** 교사가 Gate 1 에서 보고 고칠지 정한다. 코드가 자동으로 지우면
두 가지가 나빠진다 — 프롬프트가 안 지켜졌다는 사실이 가려지고, 조사가 깨져
문장이 어색해진다(`"기관 내 아동가"`).

**세는 일만 한다는 것이 중요하다.** 이름을 지우는 쪽은 프롬프트고, 이 검사는
그것이 실패한 횟수를 드러내는 자동 신호다. 0 이 아니면 프롬프트를 고칠 때다.

> ⚠️ **이것은 프롬프트 규칙이라 코드가 보장하지 못한다.** §3 의 다른 규칙들과 같다.
>
> `other_child_names` 는 `ACTIVE` 명부 아이만 담는다. 동의 전 아동·다른 기관
> 아이·형제·교사·성을 뗀 이름·오타는 빠진다. **동의하지 않은 사람일수록 이
> 검사에서 빠지므로**, `needs_review` 가 `false` 여도 "안 샌다" 는 뜻이 아니다.
>
> 매칭의 `mentioned_child_ids` 를 이름 목록으로 받으면 **센어 볼 수는** 있다. 다만
> 그 목록은 `ACTIVE` 명부 아이만 담는다 — 동의 전 아동·다른 기관 아동·형제·교사·
> 오타로 적힌 이름은 빠진다. **동의하지 않은 사람일수록 그 검사에서 빠지므로**,
> 측정값이 0 이어도 "안 샌다" 는 뜻이 아니다. 차단이 아니라 측정으로만 쓴다.

### 검증 에이전트는 기준이 아니다

말투 기준은 `schema.md §9.2` 의 독자에서 나온 것이지 검증 에이전트에서 나온
것이 아니다. 검증은 원본 일지만 보고 요약문은 보지 않는다.

> **요약 품질을 검증 통과율로 재는 순간 자기충족이 된다.** 품질은 환각·누락으로
> 재고, 검증 에이전트는 안전장치로만 쓴다.

## 4. Gate 1 — 교사가 손대면 근거가 끊긴다

Gate 1 에서 교사가 할 수 있는 일은 셋이다. **"반려" 는 두지 않는다** — 입력이
그대로면 재생성해도 같은 글이 나와서, 갈 곳이 없는 상태가 된다.

| 교사 행동 | 결과 |
| --- | --- |
| 승인 | 그대로 `child_context` 로 |
| **수정 후 승인** | 고친 본문으로. 기본 경로다 |
| 보류 (HOLD) | `child_context` 로 올라가지 않는다 |

재생성은 **입력이 바뀐 경우만** 한다 — 새 일지가 도착했고 아직 승인 전일 때다.

### 교사가 고친 문장은 근거 없음으로 표시한다

`span` 은 AI 원문 기준이라, 교사가 문장을 고치면 근거와의 연결이 끊긴다.
승인 시점에 **각 claim 의 `text` 가 최종 본문에 그대로 있는지** 코드가 확인하고,
없으면 그 claim 을 버린다. ①과 같은 방법이다.

```
FE 표시   근거 있음 / 교사 작성     두 가지면 된다
```

조용히 두면 **교사가 쓴 문장이 AI 근거를 단 것처럼 보인다.** 다른 기관이 그걸
AI 가 원문에서 뽑은 사실로 읽는다.

> ⚠️ 이 대조는 백엔드가 한다. AI 쪽 플래그가 아니라 승인 API 의 규칙이다.

### 교사가 고친 문장은 검증을 거치지 않았다

표시만으로는 막히지 않는다 (2026-10-04, @geunchanKim).

```
원본 일지   검증 ✅ → 요약 → Gate 1
교사 수정   검증 ❌ ─────────────┘ → child_context → 인사이트 → 부모
```

수정 중에 다른 아이 이름이나 연락처가 들어가면 **아무 검사도 거치지 않고**
다른 기관까지 나간다. 검증 에이전트는 원본 일지만 보기 때문이다.

**바뀐 문장만 검증한다.** 위 대조가 이미 교사가 고친 문장을 집어내므로,
그 목록을 그대로 `POST /validation` 에 보내면 된다. 문장당 한 번씩 부르고,
`subject_child_id` / `subject_name` 에는 그 아이를 넣는다. 보통 1~3 문장이다.

| 판정 | 승인 API |
| --- | --- |
| `BLOCK` (진단명 · 개인정보표현) | **승인을 막는다** |
| `REVIEW` | 경고만 보여주고 교사가 판단한다 |

`BLOCK` 을 막는 이유는 그 정의가 "그 자체로 위험해서 통과 자체를 막는 것"
이어서다. 연락처가 다른 기관으로 나가는 사고는 원본에서 왔든 교사가 썼든
같다. 이것은 반려와 다르다 — **그 부분만 지우면 바로 승인**이라 교사가 갈
곳이 있고 루프가 생기지 않는다.

> ⚠️ 검증 판정 기준(v1.3)은 **원본 일지 문체로 튜닝됐다.** 요약문은 생성문이라
> 과탐·미탐이 다르게 날 수 있다. 적용은 하되 "교사가 고친 문장" 모양의 세트로
> 따로 재기 전까지는 기존 숫자를 그대로 가져다 쓰지 않는다.

### 인사이트는 근거가 있는 문장만 받는다

원문으로 추적되지 않는 내용이 다른 기관과 부모에게 나가지 않게 한다
(2026-10-04, @geunchanKim).

여기서 따라오는 결과가 하나 있다 — **교사가 직접 쓴 문장은 인사이트에
반영되지 않는다.** 교사가 "이건 꼭 알려야 한다" 고 적은 문장이 부모에게
가지 않는 것이라, **Gate 1 화면이 그 사실을 알려야 한다.** 조용히 빠지면
교사는 전달했다고 믿는다.

## 5. 같은 날 기록이 더 올라올 때

```
승인 전   같은 revision 을 다시 생성한다 (덮어쓴다)
승인 후   revision + 1 로 새 요약을 만든다. 새 일지만 묶는다
```

**승인 후의 새 판은 이전 판을 대체하지 않는다.** 둘 다 유효하고, 타임라인에
같은 날짜로 나란히 뜬다. `revision` 은 "몇 번째 판" 이지 "최신본" 이 아니다.

이전 요약 본문을 새 요약의 재료로 넣지 않는다. 넣으면 그 문장들은 원문 대조가
안 되고, **교사가 추적할 수 없는 문장을 승인**하게 된다. §2 를 통째로 무력화한다.

### 언제 묶는가 — 하루가 끝나야 묶을 수 있다

```
기본      entry_date 다음 날 03:00 (KST) 에 그 날짜를 1회 요약
과거 날짜  마감이 지난 날짜의 일지가 들어오면 debounce 30분
공통      같은 아이·같은 날짜에 처리 중인 일지가 없을 것
수동      교사가 "지금 요약" 으로 마감을 앞당길 수 있다
```

**분 단위 debounce 하나로는 안 된다.** 학교가 오후 4시, 센터가 저녁 7시에
올리면 두 편으로 쪼개지고, 그러면 §1 의 이유가 사라진다. 기관 **간** 간격은
마감이 덮고, debounce 는 같은 사람이 연달아 올리는 간격만 덮는다.

> **03:00 과 30분은 임의값이다.** 실제 업로드 시각 분포를 보고 정한 것이
> 아니라 하원 시각에서 거꾸로 잡았다. 숫자만 바꿀 수 있게 백엔드 설정으로 둔다.
>
> 이 방식은 `entry_date` 에 전적으로 의존한다. 날짜 없는 일지는 묶을 수가 없다.
