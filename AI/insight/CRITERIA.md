# Insight Agent 판정 기준 (v0.5)

> 원본은 레포의 `AI/insight/CRITERIA.md` 입니다. 기준을 바꿀 때는 이 문서를 먼저 고치고, 코드(`prompts.py`, `config.py`)가 따라갑니다.
> 이 문서는 "어떤 인사이트가 성립하는가, 무엇을 쓰지 않는가, 무엇을 재료로 쓰는가"라는 원칙만 다룹니다.

---

## 1. 인사이트란

여러 날, 여러 기관의 승인된 요약을 **겹쳐 봐야만 보이는** "상황 → 반응 → 대처와 결과" 묶음입니다.

> 다른 선생님이 내일 이 아이를 만날 때 바로 쓸 수 있는 정보인가?

이 질문에 "예"라고 답할 수 없으면 인사이트가 아닙니다.

| | 요약 | 인사이트 |
| --- | --- | --- |
| 재료 | 하루치 일지 (한 기관) | 여러 날·여러 기관의 승인된 요약 |
| 답하는 질문 | 오늘 무슨 일이 있었나 | 이 아이를 돌볼 때 무엇을 알면 좋은가 |

**요약 한 편에서 그대로 나올 수 있는 문장이면 인사이트가 아닙니다.** 인사이트는 아래 네 가지 중 하나 이상이어야 합니다.

| 종류 | 뜻 | 예 |
| --- | --- | --- |
| 묶기 | 겉모습이 다른 장면을 같은 상황으로 묶음 | 1교시 종, 정리 시간, 체육 후 → "활동이 바뀔 때" |
| 효과 비교 | 같은 상황에서 통한 대처와 통하지 않은 대처를 나란히 둠 | 그림 카드를 보여준 두 번은 돌아왔고, 이름을 크게 부른 한 번은 더 울었다 |
| 기관 간 차이 | 같은 상황에서 기관마다 반응이 다름. **대처가 없어도 성립** | 학교에서는 차례를 기다렸고, 센터에서는 끼어들었다 |
| 변화 | 기간 안에서 반응이 달라짐 | 첫 주에는 거부했고, 셋째 주에는 스스로 참여했다 |

- 요약은 아동 × 날짜 × 기관 단위로 만들고 그 기관 작성자가 Gate 1에서 승인합니다. 기관을 가로지르는 문장은 승인을 거친 요약들 위에서 인사이트가 만듭니다.

---

## 2. 입력

승인된 요약의 claims 중 **원본 일지 근거가 있는 것만** 받습니다.

| 필드 | 뜻 | 요약에서 오는 값 |
| --- | --- | --- |
| `claim_id` | 인사이트가 근거를 가리킬 때 쓰는 번호 | BE가 `{summary_id}-{claims 배열 순서}`로 붙임 |
| `text` | claim 문장 (익명화됨) | `claims[i].text` |
| `entry_date` | 기록 날짜 | `entry_date` |
| `institution_id` | 기관 번호 | `institution_id` |
| `institution_type` | 기관 종류 | BE가 기관 테이블을 조인해 붙임. 이름은 받지 않음 |
| `evidence` | `[{journal_entry_id, quote}]`, 최소 1개 | `claims[i].evidence` (span은 버림) |

입력에는 보호자의 기관별 공유 동의(`sharing_consent`)가 ACTIVE인 기관 목록(`consented_institutions`)도 함께 옵니다. 재료 거르기(7절)에만 쓰고, 모델에게는 보여주지 않습니다.

- 기관 **ID**는 동의 필터와 기관 간 차이 판정에 씁니다. 같은 종류 기관이 둘일 때 종류만으로는 구별이 안 되기 때문입니다.
- 요약이 claims 배열 순서를 본문 순서로 고정하므로, 같은 판 안에서 `claim_id`는 바뀌지 않습니다. 승인 후 새 판은 새 일지만 묶고 summary_id가 달라 claim이 겹치지 않습니다.
- Gate 1에서 근거가 끊긴 "교사 작성" 문장은 넣지 않습니다. 원본으로 추적되지 않는 내용이 다른 기관으로 나가면 안 되기 때문입니다.
- **모델에게는 claim 문장과 번호만 보여주고, 인용(`quote`)은 보여주지 않습니다.** `text`는 요약이 익명화했지만 `quote`는 원문이라 다른 아이 이름이 그대로 남아 있습니다. 인용은 출력으로도 옮기지 않습니다. `test_reflect.py`가 프롬프트에 인용이 들어가지 않는지 확인합니다.

## 3. 출력

| 필드 | 작성 | 뜻 |
| --- | --- | --- |
| `situation` | 모델 | 언제, 어떤 맥락에서 |
| `behavior` | 모델 | 그 상황에서 관찰된 아이의 반응 |
| `supports` | 모델 | `[{action, result, claim_ids}]` 누가 어떻게 했고 어떻게 됐는지. 없어도 됨 |
| `claim_ids` | 모델 | 이 인사이트 전체의 근거 |
| `content` | 모델 | 교사·보호자가 읽을 한두 문장. 기관 간 차이면 기관 종류를 씀 |
| `source_entry_ids` | 코드 | 근거 claim이 가리키는 원본 일지 |
| `source_institution_ids` | 코드 | 근거를 낸 기관 |
| `institution_types` | 코드 | 근거를 낸 기관의 종류 |
| `cross_institution` | 코드 | 근거가 두 기관 이상이면 참 |

- 모델에게 기관 이름, 날짜, 위치를 쓰게 하지 않습니다. 근거 번호만 받고 나머지는 코드가 찾습니다. (매칭·검증·요약과 같은 원칙)
- 기관 **종류**(학교·센터·학원)는 본문에 씁니다. 기관 간 차이는 어디서 그랬는지가 핵심이기 때문입니다.
- **누가 볼 수 있는지는 출력하지 않습니다.** BE가 Gate 2 시점의 동의로 후보를 정하고, 교사가 고릅니다 (7절).
- **인사이트가 없으면 빈 배열이 정답입니다.** 억지로 만든 패턴이 과잉해석입니다.

## 4. 성립 조건 — 코드가 거릅니다

모델 출력을 그대로 믿지 않습니다. 아래를 하나라도 어기면 그 인사이트(또는 그 대처)를 버립니다.

| 조건 | 어기면 |
| --- | --- |
| `claim_ids`가 모두 입력 안에 있다 | 인사이트 버림 |
| 근거 claim이 2개 이상이다 (관찰 하나는 패턴이 아님) | 인사이트 버림 |
| 각 `support`에 자기 `claim_ids`가 있다 | 그 대처만 버림 |
| 각 `support`에 `result`가 있다 (결과가 기록에 없는 대처는 쓰지 않음) | 그 대처만 버림 |
| 상황·반응·본문에 나온 기관 종류가 근거 claim의 기관 종류 안에 있다 | 인사이트 버림 |
| 대처 문장에 나온 기관 종류가 그 대처 근거의 기관 종류 안에 있다 | 그 대처만 버림 |

- 근거 번호가 하나도 없는 대처는 플래그와 무관하게 항상 건너뜁니다. `REQUIRE_SUPPORT_EVIDENCE`는 "가리킨 번호가 전부 입력에 있는가"만 정합니다.
- 기관 대조는 이름이 아니라 종류(학교·센터·학원)로 합니다. 프롬프트가 기관 이름을 쓰지 않게 하고, 기관 간 비교 문장은 종류로 쓰이기 때문입니다. 같은 종류 기관이 둘이면 구별하지 못합니다.

## 5. 쓰는 원칙 — 무엇을 쓰고 무엇을 쓰지 않는가

요약과 같이, 기준은 숫자가 아니라 불리언입니다.

| 플래그 | 원칙 | 나쁜 예 → 좋은 예 |
| --- | --- | --- |
| `DROP_TRAIT` | 성격·특성으로 일반화하지 않는다. 상황과 반응으로만 쓴다 | "고집이 세다" → "활동이 바뀔 때 자리를 떠났다" |
| `DROP_DIAGNOSIS` | 진단이나 의학적 해석을 하지 않는다 | "감각 과민으로 보인다" → "큰 소리가 나자 귀를 막았다" |
| `DROP_PRESCRIPTION` | 처방하지 않는다. 기록된 대처와 결과만 쓴다 | "그림 카드를 사용하세요" → "그림 카드로 알려주자 스스로 이동했다" |
| `KEEP_HEDGES` | 원문이 추측이면 추측으로 남긴다. 원인을 새로 짐작하지 않는다 | "피곤해서 울었다" → (원문이 "피곤했던 것 같다"면) "피곤했던 것 같다는 기록이 있다" |
| `DROP_SENTIMENT` | 작성자의 감정 평가는 빼고 사실만 남긴다 | "너무 대견했다" → "혼자 신발을 신었다" |
| `DROP_OTHER_CHILD_NAMES` | 다른 아이 이름을 쓰지 않는다 | "민준이와 다퉜다" → "친구와 다퉜다" |
| `KEEP_FAILED_SUPPORT` | 통하지 않은 대처도 남긴다. 피해야 할 방법도 유용한 정보다 | "이름을 크게 부르자 더 거부했다" 유지 |
| `ONE_SITUATION` | 인사이트 하나에 상황 하나만 담는다 | 전환 상황과 식사 상황을 한 인사이트에 섞지 않음 |
| `WRITE_INSTITUTION_TYPE` | 기관마다 다르면 어느 기관인지 기관 종류로 쓴다. 기관 이름은 쓰지 않는다 | "반응이 일관되지 않았다" → "학교에서는 기다렸고 센터에서는 끼어들었다" |
| `CROSS_WITHOUT_SUPPORT` | 대처가 없어도 기관마다 반응이 다르면 인사이트로 쓴다 | (대처가 없어 빈 배열) → "학교에서는 혼자 신었고 센터에서는 도움이 필요했다" |
| `RELATE_RECORDS` | 기록 하나를 다시 말하지 않는다. 여러 기록을 묶거나 비교한 결과를 쓴다 | "새 반찬을 밀어냈다" → "새 반찬을 밀어낸 일이 세 번 있었고, 조금 덜어준 날은 한 입 먹었다" |

- 이 원칙들은 프롬프트로만 지킵니다. `WRITE_INSTITUTION_TYPE`은 "본문에 근거 기관 종류가 모두 나옴" 지표로, 나머지는 사람 표본 판정으로 잽니다 (9절).
- 다른 아이 이름은 요약 단계에서 지웁니다. 인사이트는 이름 목록을 입력으로 받지 않고, 프롬프트 규칙과 채점으로만 확인합니다.
- 다른 아이 이름을 **보장하며 막는 층은 없습니다.** 요약 1차(프롬프트 익명화), 요약 2차(이름 목록으로 남았는지 확인해 선생님에게 표시), 인사이트(`DROP_OTHER_CHILD_NAMES`) 모두 프롬프트이거나 확인·표시입니다. 요약의 이름 목록은 ACTIVE 명부 아이만 담아 동의 전 아동·형제·교사·오타로 적힌 이름은 빠집니다. 막으려면 검증의 다수아동언급을 BLOCK으로 올려야 하지만, 그러면 "짝과 공을 주고받았다" 같은 상호작용 기록이 전부 막혀 그렇게 하지 않습니다.

## 6. 판정 예시

| 출력 | 판정 | 이유 |
| --- | --- | --- |
| "활동이 바뀔 때 자리를 떠나는 일이 반복됐습니다. 학교에서 그림 카드로 미리 알려주자 스스로 이동했습니다." (근거 3개, 학교·센터) | 성립 | 묶기 + 효과 비교, 근거 있음 |

| "줄을 설 때 기다린 기록과 끼어든 기록이 모두 있어 반응이 일관되지 않았습니다." (근거 학교·센터) | 불성립 | 기관을 빼서 아이가 들쭉날쭉한 것처럼 읽힘 |
| "새 반찬을 밀어냈고 작은 접시에 덜어주자 한 입 먹었습니다." (한 claim을 다시 씀) | 불성립 | 요약 한 편에서 그대로 나오는 문장 |
| "이 아이는 변화를 싫어하는 성향입니다." | 불성립 | 특성 일반화 |
| "전환 시 그림 카드 사용을 권장합니다." | 불성립 | 처방 |
| "급식 시간에 반찬을 남겼습니다." (근거 1개) | 불성립 | 근거 2개 미만 |
| "학교에서는 혼자, 센터에서는 도움이 필요했습니다." (근거가 학교 claim뿐) | 불성립 | 본문의 기관 종류가 근거 기관에 없음 |
| "...다 먹어야 한다고 하자 울었다. 강요하면 울음으로 이어질 수 있다." | 불성립 | 기록을 넘어선 일반화 |
| 패턴이 없는 기간에 빈 배열 | 정답 | 억지 인사이트를 만들지 않음 |

## 7. 동의 — 재료와 수신 범위

**허락은 모델이 정하지 않습니다.** 인사이트는 재료를 거르는 데만 동의를 쓰고, 누가 볼 수 있는지는 BE가 정합니다.

### 재료 쪽 동의

- 동의하지 않은 기관의 claim은 인사이트 입력에서 뺍니다. 받는 쪽만 막으면 철회된 기관의 기록이 재료로 들어가 다른 기관으로 흘러가기 때문입니다.
- `consented_institutions`는 보호자의 기관별 공유 동의(`sharing_consent`)가 ACTIVE인 기관입니다.
- BE가 입력을 만들 때 거르고, 인사이트 인식 단계에서 한 번 더 거릅니다.
- 동의 목록이 비어 있으면 아무 claim도 쓰지 않습니다. 모르면 막습니다.

> ⚠️ **한계**: `sharing_consent`가 아직 구현되지 않아, 그 전까지 BE는 아이가 등록된 기관 전부를 동의한 것으로 넣습니다. 그동안 재료 쪽 필터는 실제로 거르는 것이 없습니다.

### 수신 범위 (MVP: 동의한 기관 안에서 교사가 고름)

| 단계 | 내용 | 정하는 주체 |
| --- | --- | --- |
| 후보 | Gate 2 화면을 열 때 그 시점에 동의한 기관 | BE |
| 최종 | 후보 중 교사가 선택 | Gate 2 교사 |
| 실제 접근 | 보내든 열람하든, 접근하는 시점에 동의를 다시 확인 | BE |

- 인사이트는 근거를 낸 기관(`source_institution_ids`)만 냅니다. 인사이트가 만들어진 순간 정해지는 고정된 사실입니다.
- 동의는 인사이트를 만든 뒤에도 바뀌어서, 후보는 생성 시점이 아니라 Gate 2 시점에 계산합니다.
- 공유 방식("보낸다" 또는 "열람한다")과 상관없이, 실제 접근 시점의 동의 검사는 BE가 맡습니다 (멘토 답변 Q8).

### 쓸모 추천 (MVP에서 제외)

"이 인사이트가 어느 기관에 쓸모 있는가"를 표시하는 추천은 MVP에서 하지 않습니다. 멘토 답변(Q8)에 따라 동의한 기관 안에서 교사가 고르는 방식으로 시작하고, 추천은 나중에 확장합니다.

| 시도 | 결과 | 버린 이유 |
| --- | --- | --- |
| v0.1 규칙: 근거가 나오지 않은 기관을 추천 | 거의 항상 참 | 근거 기관을 뒤집은 값이라 신호가 되지 않음 |
| v0.4 모델 태깅: 그 상황이 일어나는 기관 종류 | 근거 밖 태그 0/48 | 근거 기관을 그대로 복사. 신호가 되지 않고, 본문에 "참고할 수 있다"가 새고, 기관 언급이 30/30 → 28/30으로 떨어짐 |

나중에 다시 할 때의 조건은 v0.4 측정에서 확인했습니다.

- **B. 모델 태깅**: 모델에게 아이가 다니는 기관 종류를 알려주고(이름·동의 여부 없이), 근거가 나오지 않은 기관만 고르게 합니다. 합성 세트에 "학원에 다니지만 학원 기록이 없는 아이"와 "학원에는 없는 상황(급식)"을 넣어 정답을 심습니다.
- **C. 코드 계산**: 통한 대처가 아직 쓰이지 않은 기관(공백)을 코드가 계산합니다. 대처가 있는 인사이트에만 쓸 수 있습니다.
- 어느 쪽이든 추천은 참고일 뿐이고, 추천만으로 접근을 허용하지 않습니다.

### 동의 철회

- 동의가 철회되면, 그 기관 claim을 근거로 쓴 인사이트는 BE가 `source_entry_ids`로 찾아 무효 처리합니다. 인사이트는 여러 기관 claim을 엮은 결과라 문장 일부만 뺄 수 없습니다.
- 언제 다시 만들지는 정하지 않았습니다 (10절).
- 받는 쪽 철회는 접근 시점의 동의 검사로 막히지만, **재료 쪽 철회는 그것으로 풀리지 않아** 무효 처리는 그대로 필요합니다.

## 8. 출력 후 안전장치

- 인사이트는 다른 기관과 보호자에게 갑니다. Gate 2에서 교사가 최종 승인합니다. 볼 수 있는 범위는 7절을 따릅니다.
- (제안) `content`를 검증 에이전트에 한 번 통과시켜, 진단명·개인정보·다른 아이 이름이 남지 않았는지 확인합니다.

## 9. 평가 방법

| 지표 | 목표 | 재는 법 |
| --- | --- | --- |
| 근거 없는 인사이트 | 0 | 코드 검사 (`claim_ids` 유효성) |
| 근거 기관과 맞지 않는 기관 언급 | 0 | 코드 검사 (기관 종류 대조) |
| 동의 밖 기관 claim 사용 | 0 | 코드 검사 (재료 쪽 동의 필터) |
| 과잉해석 (특성·진단·처방·기록을 넘어선 일반화) | 0 | 판정 기준 대조 + 사람 표본 확인 |
| 요약 이어 붙이기 (기록 하나를 다시 말함) | 0 | 사람 표본 확인 |
| 기관 간 차이 본문에 근거 기관 종류 모두 언급 | 높을수록 좋음 | 패턴 단위 채점 |
| 다른 아이 이름 노출 | 0 | 세트의 금지어 대조 |
| 심어둔 패턴을 찾는 비율 | 정할 것 | 패턴을 심은 요약 세트로 측정 |
| 남는 인사이트 (어느 패턴과도 맞지 않음) | 0 | 패턴 단위 채점 |
| 패턴 없는 세트에서 빈 배열 | 높을수록 좋음 | 대조군 세트로 측정 |
| 같은 입력의 결과 일관성 | 높을수록 좋음 | 같은 세트를 여러 번 실행, 갈래별로 봄 |

- 대조군(패턴이 없는 아이)이 적으면 과잉해석률을 믿을 수 없습니다. 패턴군과 비슷한 규모로 만듭니다.
- 모델은 temperature를 고정할 수 없어 같은 입력에도 결과가 흔들립니다. 한 번 실행한 결과로 판단하지 않습니다.
- 블라인드 세트는 인사이트 판정 로직을 만들지 않은 사람이 씁니다. 한 번만 돌립니다. 결과를 보고 고친 뒤 같은 세트로 다시 채점하지 않습니다.
- 합성 세트 `gen_cases.py`: 반복 패턴 6 · 기관 간 차이 4 · 대조군 10 · 다른 아이 이름 6. 이름 갈래는 패턴 claim 두 개에 다른 아이 이름을 섞어, 요약 익명화가 실패했을 때의 2차 방어선을 잽니다. 블라인드 v1에는 이 갈래가 없습니다.
- 채점 단위는 심은 패턴 하나입니다. 패턴의 근거와 2개 이상 겹치는 인사이트가 있으면 찾은 것으로 보고, 어느 패턴과도 맞지 않는 인사이트는 "남는 인사이트"로 셉니다. 모든 패턴을 찾고 남는 인사이트가 0이어야 완전 정답입니다.
- 기관 간 차이 패턴은 그 근거 claim들의 기관 종류가 본문에 모두 나오는지 봅니다.
- `test_criteria_sync.py`는 이 문서와 코드가 어긋나지 않았는지 봅니다. §5 문장이 프롬프트에 그대로 들어 있는지, §4·§7이 전제하는 플래그가 켜져 있는지, §4 최소 근거 수가 config 값과 같은지 확인합니다.
- `test_reflect.py`는 §4 성립 조건, §7 재료 쪽 동의, §2 인용 비노출을 LLM 없이 확인합니다. 모델 응답을 손으로 만들어 넣어 매번 같은 결과가 나옵니다.
- `run_suite.py`는 세트를 여러 번(기본 3회) 실행하고 채점합니다. `--cases`로 세트를, `--name`으로 결과 파일 이름을 지정합니다. 결과는 `generated/insight/runs/`에 모델·세트 경로와 함께 저장해 `--rescore`로 LLM 없이 다시 채점할 수 있습니다. 쓸모 태그 지표는 B·C 재시도 때 쓰려고 남겨두었고, 지금은 태그가 없어 0으로 나옵니다.
