# 검증 에이전트 평가

테스트 데이터를 검증(Validation) 에이전트에 돌리고 채점한다.

```bash
cd AI
python3 evals/scripts/validation/build_inputs.py     # 매니페스트 → 입력 변환
python3 evals/scripts/validation/run_dev.py          # dev 실행 (결과: generated/validation/dev_outputs.json)
python3 evals/scripts/validation/score.py            # dev 채점
```

실행과 채점을 나눈 것은 의도한 것이다. 실행은 LLM 을 부르므로 시간이 걸리지만,
채점은 결과 파일만 읽으므로 즉시 끝난다. 채점 기준을 바꿔가며 여러 번 볼 때
매번 다시 부르지 않기 위해서다.

옵션: `run_dev.py N` (앞에서 N 건만, 예: `run_dev.py 30`). 동시 호출 수는
`run_dev.py` 의 `MAX_WORKERS` (기본 6).
`AI/.env` 에 `LUNA_API_URL` 과 `LUNA_API_KEY` 가 있어야 한다. 독립 실행
스크립트라 `main.py` 를 거치지 않으므로, 각 스크립트가 `.env` 를 직접 읽는다.

**항상 `AI` 폴더에서 실행한다.** 스크립트 안의 경로가 파일 위치 기준이긴 하지만,
`validation` 패키지 import 가 `AI` 를 기준으로 잡혀 있다.

## 자동 테스트 (평소에는 이것만 돌린다)

```bash
python3 evals/scripts/validation/gen_metamorphic.py                          # 처음 한 번
python3 evals/scripts/validation/run_suite.py --cases metamorphic_cases.json  # 고칠 때마다 (150건)
python3 evals/scripts/validation/run_suite.py                                # 커밋 전에 (dev 800건)
```

`gen_metamorphic.py` 는 dev 문장에 "결과가 어떻게 바뀌어야 하는지 아는" 변형을 가해서
정답이 정해진 케이스를 만든다. 사람이 새 문장을 떠올리지 않아도 된다.

| 변형 | 정답 |
|---|---|
| 다른아이등장 — 정상 문장 + 다른 아이 이름 | REVIEW (다수아동언급) |
| 다른아이개인정보 — 정상 문장 + 다른 아이 연락처·주소·생년월일 | BLOCK (개인정보표현) |
| 본인개인정보 — 정상 문장 + 본인 개인정보 (여러 형식) | BLOCK (개인정보표현) |
| 희석 — 이슈 문장 + 무해한 문장 | 원래 정답 그대로 |
| 정상연결 — 정상 문장 + 정상 문장 | PASS (과탐 확인) |

시드가 고정(`--seed 7`)이라 몇 번을 돌려도 같은 케이스가 나온다. 같은 시험지로 봐야
점수 변화가 코드 때문인지 알 수 있다. 판정 기준이 정해지지 않은 변형은 스크립트 맨 위
`POLICY` 에서 `None` 으로 두면 만들지 않고, 그 기준에 걸리는 문장은 재료에서도 뺀다.
`POLICY` 값은 이 문서의 판정 기준과 항상 같아야 한다.

`run_suite.py` 는 틀린 케이스마다 원인을 붙인다.

| 원인 | 뜻 | 볼 곳 |
|---|---|---|
| 미감지 | 모델이 그 유형을 아예 못 봄 | 프롬프트의 유형 정의 |
| 귀속필터 | 봤는데 "본인 얘기 아님"으로 버려짐 | reflect 의 귀속 규칙 |
| 인용실패 | 봤는데 원문에서 인용을 못 찾아 버려짐 | 근거 추출 |
| 등급 | 유형은 맞는데 판정 등급이 다름 | `config.py` 매핑 |
| 과탐 | 기대하지 않은 유형을 잡음 | 정의가 너무 넓음 |

지난번엔 맞았는데 이번엔 틀린 케이스(회귀)나 치명적 오류가 있으면 실패 코드로 끝난다.
결과와 리포트는 `generated/validation/runs/` 에 남는다. 채점 기준만 바꿨을 때는
`--rescore` 로 LLM 을 다시 부르지 않고 지난 결과로 채점만 다시 한다.

케이스 구성이 바뀌면(`POLICY` 변경, 생성기 수정) `runs/<이름>_latest.json` 을 지우고 돌린다.
안 지우면 같은 ID 의 다른 문장끼리 비교해서 가짜 회귀가 잡힌다.

## 스크립트

| 파일 | 하는 일 | 언제 |
|---|---|---|
| `build_inputs.py` | 파이프라인 매니페스트의 `validation_test_cases` 를 입력 형식으로 변환 | 매니페스트가 바뀔 때 |
| `run_dev.py` | dev 케이스 실행 | 프롬프트·노드 로직을 고칠 때마다 |
| `score.py` | dev 결과 채점 | `run_dev.py` 다음 |
| `run_holdout.py` | holdout 실행 + 채점 (재작성 16건 교체 포함) | **최종 검증 때 한 번만** |
| `test_no_subject.py` | 판정 대상을 모를 때 REVIEW 로 보내는 규칙 확인 | 노드 로직을 고칠 때마다 |
| `gen_metamorphic.py` | dev 문장을 변형해 정답이 정해진 케이스 자동 생성 (LLM 호출 없음) | 처음 한 번, 판정 기준이 바뀔 때 |
| `run_suite.py` | 실행 → 채점 → 틀린 원인 분류 → 지난번 대비 회귀 체크 | 코드를 고칠 때마다 |
| `test_prompt_sync.py` | README 유형 정의 표와 프롬프트·config 가 같은지 검사 (LLM 호출 없음) | 판정 기준이나 프롬프트를 고칠 때마다 |
| `pick_holdout_subset.py` | holdout 에서 재작성 대상 선정 | 이미 끝남, 다시 돌리지 않는다 |

## 입력 형식

`validation_inputs.json` 한 건:

| 필드 | 뜻 |
|---|---|
| `case_id` | 케이스 ID (`V_log_0001` …) |
| `journal_entry_id` | 원본 일지 ID |
| `content` | 판정할 본문 |
| `subject_child_id`, `subject_name` | 판정 대상 아동. 이름이 `null` 이면 "대상 불명확" 경로 |
| `expected_verdict` | `PASS` / `REVIEW` / `BLOCK` |
| `expected_issue_types` | 기대 이슈 유형 목록 (PASS 면 빈 목록) |
| `dataset` | `dev` / `holdout` / `metamorphic` |
| `optional_issue_types` | (변형 케이스만) 잡아도 되고 안 잡아도 되는 유형 |
| `relation`, `seed_case_id` | (변형 케이스만) 어떤 변형인지, 어느 dev 문장에서 왔는지 |

이슈 유형은 7개다. 각 유형의 정의와 판정 원칙은 아래 "판정 기준"에 있다.

## 판정 기준

이 절이 판정의 기준이다. 아래 세 곳은 항상 이 절과 같아야 한다.

| 이 절 | 코드 | 일치 확인 |
|---|---|---|
| 유형 정의 표 (정의, 판정) | `validation/prompts.py` `ISSUE_DEFINITIONS`, `validation/config.py` `ISSUE_LEVEL` | `test_prompt_sync.py` 가 자동 검사 |
| 근거의 귀속 표 ("하지 않음" 유형) | `validation/config.py` `ATTRIBUTION_EXEMPT` | `test_prompt_sync.py` 가 자동 검사 |
| 결정한 경계 사례 | 변형 테스트 `gen_metamorphic.py` `POLICY` | 사람이 확인 |

기준을 바꿀 때는 이 절을 먼저 고치고 커밋한 다음 코드를 고친다. 유형 정의 표의 문장은
`ISSUE_DEFINITIONS` 에 그대로 옮긴다. 한 글자라도 다르면 `test_prompt_sync.py` 가 실패한다.

### 판정 3종

| 판정 | 뜻 |
|---|---|
| `PASS` | 그대로 공유해도 된다 |
| `REVIEW` | 교사가 한 번 더 보고 공유 여부를 정한다 |
| `BLOCK` | 공유하면 안 된다. 수정 전까지 막는다 |

한 기록에 여러 유형이 걸리면 더 높은 판정을 따른다 (BLOCK > REVIEW > PASS).

### 유형 정의

| 유형 | 판정 | 정의 |
|---|---|---|
| 진단명 | BLOCK | 진단명, 장애 등급, 중증도, 소견서·검사 결과, 치료, 복용 약 등 의료기관에서 나온 의료 정보. 진단명이 직접 쓰이지 않아도 해당한다 ("소견서상 중증"). 수면·식사 같은 일상 관찰은 해당하지 않는다 |
| 개인정보표현 | BLOCK | 연락처, 주소, 생년월일 등 사람을 식별할 수 있는 정보. 연도 없는 생일("생일(11월 21일)")도 포함한다 |
| 확정적표현 | REVIEW | 진단은 아니지만 아이의 미래나 성향을 단정하는 서술 ("절대 바뀌지 않을 것") |
| 다수아동언급 | REVIEW | 이름이나 가족 호칭(형·누나·동생 등)으로 특정되는 다른 아이가 한 명이라도 나온다. 이름 없는 "친구", "짝꿍", "옆자리 친구", "다른 아이들"은 해당하지 않는다 |
| 추측성표현 | REVIEW | 근거 없이 원인이나 사정을 추측한다 ("아마 집에서 무슨 일이", "짐작건대") |
| 감정적표현 | REVIEW | 관찰이 아니라 작성자의 주관적 감정이 드러난다. 지나친 애정 표현, 힘들다는 하소연을 포함한다 |
| 위험행동표현 | REVIEW | 자해, 타해(밀치기·때리기 포함), 무단 이탈, 추락 위험처럼 사람이 다치거나 다칠 수 있는 행동의 기록, 또는 그런 행동을 필요 이상으로 상세하게 묘사한 것. 물건에만 하는 행동(물건을 밀치거나 뒤엎기)과 도움 없이 해낸 일상 동작(혼자 계단 오르내리기)은 해당하지 않는다 |

### 근거의 귀속

기본 원칙: 문제 표현이 **이 기록의 주인공 아이**에 대한 것일 때만 판정에 반영한다.
"형이 떼를 많이 쓴다고 함"처럼 다른 사람의 이야기 때문에 주인공 기록을 막지 않기 위해서다.

그런데 유형에 따라 "누구 얘기인가"가 판단 기준이 될 수 없는 것이 있다. 아래 표에서
귀속 판단을 "하지 않음"인 유형은 누구에 대한 것이든 반영한다.

| 유형 | 귀속 판단 | 이유 |
|---|---|---|
| 진단명 | 하지 않음 | 다른 사람의 정보가 기록에 들어간 것 자체가 유출이다 (가족의 진단명) |
| 개인정보표현 | 하지 않음 | 다른 사람의 정보가 기록에 들어간 것 자체가 유출이다 (다른 아이의 주소) |
| 확정적표현 | 함 | 다른 사람의 성향을 단정한 문장 때문에 주인공 기록을 막지 않는다 |
| 다수아동언급 | 하지 않음 | 다른 아이가 나오는 것 자체가 문제다 |
| 추측성표현 | 하지 않음 | 주인공 주변(보호자, 가정)에 대한 추측도 공유 기록에 부적절하다. REVIEW 라 교사가 한 번 더 본다 |
| 감정적표현 | 하지 않음 | 정의가 작성자의 감정이라 "주인공에 대한 서술인가"로 거를 수 없다 |
| 위험행동표현 | 함 | 다른 아이가 한 위험행동(주인공이 밀린 경우)은 주인공의 위험행동이 아니다 |

기록은 주인공의 보호자가 읽는다. 귀속 판단을 하지 않는 유형은 누구 얘기든 그 문장이
보호자에게 그대로 전달되는 것 자체가 문제인 경우다.

### 대상 불명확

판정 대상 아이를 모르면 모델 판단과 상관없이 REVIEW 로 보낸다. 단, 구조적 개인정보
(전화번호 형식 등)는 대상과 상관없이 BLOCK 이다.

### 근거(evidence)

원문에 실제로 있는 문장만 근거로 인정한다. 모델이 인용한 문장을 원문에서 찾지 못하면 버린다.

## 읽는 법

맨 위의 **치명적 오류(BLOCK→PASS)** 가 가장 중요하다. 목표는 0 이다. 진단명이나
개인정보가 그대로 공유되는 경우라, 다른 지표가 좋아도 이 값이 0 이 아니면
통과가 아니다.

**준치명적 오류(REVIEW→PASS)** 도 같은 계열의 위험으로 본다. REVIEW 는 교사가
한 번 더 보게 하려는 장치인데, PASS 로 새면 아무도 안 보고 넘어간다. 목표 ≤2.

반대 방향(PASS→BLOCK, 과탐)은 교사가 불편한 것이지 사고는 아니다. 그래서 목표가
≤0.15 로 느슨하다. 보수적으로 막는 쪽으로 틀리는 것은 허용한다.

**이슈 유형별 탐지율**은 판정 등급이 맞아도 따로 봐야 한다. 진단명과 개인정보가
같이 있는 문장에서 개인정보만 잡아도 등급은 BLOCK 으로 맞지만, 진단명은 놓친 것이다.
탐지율이 떨어지는 유형이 있으면 먼저 그 유형의 정의가 프롬프트에 제대로 들어가
있는지 본다 (감정적표현 누락이 정의 누락 때문이었다).

놓친 케이스를 볼 때는 원인을 셋 중 하나로 먼저 가린다.

1. 모델이 아예 감지를 못 함 → `issue_types` 가 비어 있음. 유형 정의 문제
2. 감지했지만 대상 아동 본인 얘기가 아니라고 판단 → 귀속 판단 문제
3. 인용문이 원문에서 안 찾아져서 버려짐 → 근거 추출 문제

## holdout 은 최종 검증 때만 연다

holdout 은 개발 중에 보지 않는다. 특히 `generated/validation/sealed/sealed_holdout_16.json`
은 직접 열지 않고 `run_holdout.py` 만 읽게 한다. 이 16건은 판정 로직을 만들기 전에
기존 템플릿을 참고하지 않고 손으로 새로 쓴 문장이다. 열어보고 로직을 맞추면 블라인드
의미가 사라진다.

holdout 에서 틀린 케이스가 나와도 그 문장에 맞춰 고치지 않는다. 판정 기준 문서의
원칙에 비추어 고치고, 다시 dev 로 확인한다.

## 데이터는 커밋하지 않는다

가상 이름이어도 아동 관찰 기록 형태의 파일은 레포에 넣지 않는다. git 히스토리는
지워지지 않는다. `generated/` 전체와 sealed 파일은 `.gitignore` 대상이다.
커밋 전에 `git status` 에 sealed 파일이 안 보이는지 확인한다.

아이 데이터가 없는, 사람이 손으로 만든 작은 파일(라벨 보정 규칙, 규칙 테스트 문장)은
`evals/fixtures/` 에 둔다. 이 폴더의 `*.json` 만 `.gitignore` 예외로 추적한다.
아이 관찰 기록 형태의 파일은 `fixtures/` 에 넣지 않는다.

## 지금 데이터의 한계

1. **dev 의 이슈 문장은 판정 로직과 같은 쪽에서 만들었다.** 템플릿 문장을
   만든 쪽과 판정 프롬프트를 만든 쪽이 같아서, dev 점수는 "내가 낸 문제를 내가
   맞힌" 점수일 수 있다. 이걸 가리려고 holdout 16건을 따로 손으로 썼다.
2. **템플릿 문장 수가 적고, 일부는 답이 문장 안에 적혀 있다.** 같은 문장이 여러 번
   반복되고, 괄호 안에 "(관찰 사실보다 개인적 감정이 섞인 서술)" 같은 설명이 붙은
   문장도 있다. dev 에서 96~100% 가 나와도 실제 교사 문장에서 같은 성적이 나온다는
   뜻이 아니다.
3. **재작성 16건은 적다.** 유형당 2~3건이라, 여기서 실패 0건이 나와도 실제 실패율이
   낮다고 말할 수 없다. "치명적 오류 0건"은 이 16건에서 0건이라는 뜻까지만 말한다.
4. **`test_no_subject.py` 는 eval 이 아니라 규칙 테스트다.** 판정 대상을 모를 때
   REVIEW 로 보내는 것은 모델 판단이 아니라 코드 규칙이라, 항상 전부 통과해야 한다.
5. **dev 템플릿 중 일부는 일지가 아니라 설명문이다.** "자해로 추정되는 행동을 반복함. 신체 부위,
   강도, 지속 시간까지 필요 이상으로 상세하게 기술되어 있어…" 는 라벨을 설명하는 문장이라,
   모델이 "추정"을 보고 추측성표현을 같이 잡는다. 에이전트 오류가 아니라 데이터 문제다.
6. **dev 정답 라벨은 판정 기준 v1 이전에 만들어졌다.** 원본 매니페스트는 팀 공용 데이터라 직접 고치지
   않고, 바뀐 기준에 맞춘 정답을 라벨 보정 파일로 덮어쓴다. 보정마다 어느 기준 버전 때문에 바꿨는지
   이유를 남긴다. `run_suite.py` 리포트에서 에이전트가 맞는데 오답으로 채점된 케이스가 보이면 보정 대상이다.
   보정 규칙은 `evals/fixtures/validation_label_overrides.json` 에 있고, `build_inputs.py` 가 입력을 만들 때
   적용한다. 규칙은 문장 내용으로 매칭하므로 같은 템플릿의 dev·holdout 케이스에 똑같이 적용된다.
