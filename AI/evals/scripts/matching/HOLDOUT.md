# 매칭 홀드아웃 절차

홀드아웃은 **한 번 쓰면 없어진다.** 실패한 문장을 보고 규칙을 고치는 순간 그 세트는
dev 가 된다. 그래서 만드는 법보다 쓰는 법이 중요하다.

## 세트는 서로 만든다

**에이전트를 만든 사람이 그 에이전트의 세트를 쓰지 않는다.** 매칭 세트는 검증
담당이, 검증 세트는 매칭 담당이 쓴다. 아는 규칙을 피해 가는 문장은 무의식적으로
안 써지기 때문이다.

한 가지가 더 따라온다. **실패한 문장을 본 사람은 그 판정 로직 수정에 관여하지
않는다.** 어디서 틀렸는지 알고 고치면 그 세트에 맞추는 것이고, 다음 측정이
의미를 잃는다. 본 사람은 무엇이 틀렸는지만 전하고, 고치는 쪽은 문장을 보지 않은
채 원인을 다시 찾는다.

## 왜 따로 관리하나

2026-09 튜닝에 쓴 1,130 건 안에 매니페스트의 `holdout` 200 건이 통째로 섞여 있었다.
`build_inputs.py` 가 `dev + holdout` 을 합쳐서 한 파일로 냈기 때문이다. 대조해 보니
holdout 아이 20명 전원의 이름이 `hint_name` 으로, 원문 144 종이 `content` 로 들어가
있었다. 그 세트는 소모됐다.

지금은 `--dataset` 없이는 dev 만 나온다.

```bash
python evals/scripts/matching/build_inputs.py                              # dev 665건
python evals/scripts/matching/build_inputs.py --dataset consumed-holdout   # 405건
python evals/scripts/matching/normalize_ids.py --dataset dev               # 문자열 ID → 정수
```

세트 이름이 `holdout` 이 아니라 **`consumed-holdout`** 인 것은 의도한 것이다. 매니페스트의
holdout 은 이미 소모됐고, 파일 이름이 `matching_inputs_consumed-holdout.json` 이라
나중에 누가 이걸 "블라인드 점수" 로 보고할 수 없다. 회귀 확인에는 쓸 수 있다.

미등록 50 건은 이 세트에서도 빠진다 — `UNMATCHED_WHEN_HINT_NOT_IN_ROSTER` 가
그 케이스들에서 나왔으므로 역시 소모된 데이터다.

**진짜 블라인드 점수가 필요하면 새 세트를 만들어야 한다.**

## 기준선과 나란히 본다

점수 하나만 보면 잘한 건지 알 수 없다. 2026-09-16 에 자체 채점 96% 가 나왔는데,
표지만 읽는 세 줄짜리 코드가 같은 데이터에서 100% 를 받았다.

```bash
python evals/scripts/matching/baseline.py <입력> /tmp/b1.json --mode hint
python evals/scripts/matching/baseline.py <입력> /tmp/b2.json --mode both
python evals/scripts/matching/baseline.py <입력> /tmp/b3.json --mode body-first
python evals/scripts/matching/score.py /tmp/b3.json
```

| mode | 규칙 |
| --- | --- |
| `hint` | 표지 이름을 명부에서 찾는다 |
| `both` | 표지가 없으면 본문에서도 찾는다 |
| `body-first` | **표지 이름이 본문에 없고 명부의 다른 이름이 본문에 있으면 그쪽을 고른다** |

**`body-first` 를 못 넘으면 표지를 뒤집는 데 LLM 을 쓸 이유가 없다는 뜻이다.**
셋 다 LLM 을 부르지 않으므로 즉시 끝나고 결과가 매번 같다.

> 2026-09-30 60건 측정에서 `body-first` 는 **표지·본문 불일치 15건을 전부 맞혔다.**
> 규칙으로 풀리는 자리는 규칙이 이미 다 푼다. 에이전트가 앞선 곳은 오타 15건,
> 동명이인 5건, 이름 부분포함 5건이었다.
>
> 다만 `body-first` 는 맞는 아이를 고르면서도 `hint_mismatch` 를 0/15 로 남긴다 —
> **표지가 틀렸다는 사실을 아무에게도 알리지 않고 조용히 덮어쓴다.** 교사가 확인할
> 기회가 사라진다. 그래서 정답률만 비교하면 안 되고 `hint_mismatch` 를 같이 본다.

## 세트 구성 (60건 기준)

| 갈래 | 건수 | 무엇을 재는가 | 정답 |
| --- | --- | --- | --- |
| 표지 없음 · 본문에 이름 있음 | 10 | 표지가 없어도 본문으로 잡는가 | `auto` + 해당 아동 |
| 표지 없음 · 단서 없음 | 10 | 근거가 없을 때 억지로 고르지 않는가 | `unmatched` |
| 표지 A · 본문 명백히 B | 15 | 표지를 뒤집고 사람에게 넘기는가 | `review` + B + `hint_mismatch` |
| 오타 이름 3유형 × 5 | 15 | 오타가 미등록으로 떨어지지 않는가 (#39) | `review` + 의도한 아동 |
| 동명이인 | 5 | 이름만으로 못 가르면 후보를 보여주는가 | `multi` + `ambiguous_identity` |
| 이름 부분포함 | 5 | 짧은 이름이 긴 이름 안에서 잘못 걸리지 않는가 | `auto` + 긴 쪽 |

명부는 **기존 매니페스트 150명과 겹치지 않는 새 이름**으로 만든다. 이름이 겹치면
이전 세트에서 본 패턴이 섞인다.

**다음 세트에서 늘릴 갈래** — 지금까지 한 건이 20%p 를 움직인 자리들이다.

| 갈래 | 지금 | 늘릴 이유 |
| --- | --- | --- |
| 동명이인 | 5 | 생년월일로 갈리는 경우와 안 갈리는 경우가 각각 2~3건뿐이다 |
| 오타 (유형별) | 5 | 유형마다 1건이 20%p 다 |
| 표지·본문 불일치 | 15 | 에이전트의 존재 이유라 여기만은 좁은 구간을 말할 수 있어야 한다 |
| 표지가 맞고 조연이 스침 | 0 | 2026-09-30 세트에 없었다 (아래 한계 참고) |

### 만든 뒤 반드시 돌리는 자체 검사

문장을 다 쓴 뒤, 에이전트를 부르기 **전에** 돌린다.

```bash
python evals/scripts/matching/verify_holdout.py <세트.json>
```

표지 불일치 케이스의 본문에 표지 이름이 남아 있는지, 단서 없음 케이스에 명부 이름이
섞여 있는지, 명부 밖 아이를 정답으로 적었는지 등을 본다. **여기서 걸리면 에이전트가
아니라 문제가 틀린 것이다.**

끝에 SHA-256 이 찍힌다. 세트 자체는 레포에 없으므로(아동 기록 형태라 커밋하지 않는다)
**이 값으로 서로 같은 파일을 보고 있는지 대조한다.** 세트를 공유할 때는 파일과 함께
이 해시를 적어 둔다.

## 실행 절차

```
1  세트 작성 → 정답 라벨까지 확정 → 봉인
2  자체 검사 통과
3  기준선 채점
4  에이전트 1회 실행 → 채점
5  기준선과 비교
```

**4번은 한 번만 한다.** 돌려 보고 고치고 다시 돌리면 그건 dev 다.

실패를 보고 규칙을 고치기로 했다면, 그 세트는 소모됐다고 기록하고 다음 검증에는
새 세트를 만든다.

### 세트 자체를 고쳐야 할 때

언제 고쳤는지로 갈린다.

| 시점 | 처리 |
| --- | --- |
| 돌리기 **전** — 자체 검사나 교차 검토에서 라벨 오류를 찾았다 | 고치고 그대로 쓴다 |
| 돌린 **뒤** — 결과를 보고 라벨이나 문장을 바꿨다 | **그 세트는 끝이다** |

뒤쪽이 왜 안 되냐면, 결과를 본 뒤의 수정은 "틀린 라벨을 바로잡는 것" 과
"에이전트가 맞게 보이도록 바꾸는 것" 이 구분되지 않기 때문이다. 고치는 본인조차
구분하지 못한다. 그래서 시점으로 자른다.

고친 세트로 숫자를 다시 내야 한다면 **그 숫자는 블라인드가 아니다.** 회귀 확인
용도로만 쓰고, 보고할 때 그렇게 적는다.

## 숫자를 읽는 법 — 표본이 얇다

60건은 작다. 갈래별로는 5~15건이라 **한 건이 크게 움직인다.**

| 갈래 | 건수 | 1건의 무게 |
| --- | --- | --- |
| 표지·본문 불일치 | 15 | 6.7%p |
| 오타 (유형별) | 5 | 20%p |
| 동명이인 | 5 | 20%p |

**"오매칭 0/15" 는 "오매칭률이 0" 이라는 뜻이 아니다.** 15번 봐서 한 번도 안 나왔다는
뜻이고, 여기서 말할 수 있는 것은 **실제 오매칭률이 대략 20% 미만**이라는 것까지다
(0건 관측의 상한은 대략 3÷n 이다). 300건을 돌려야 1% 아래를 말할 수 있다.

그래서 비율보다 **건수**를 통과 기준으로 삼는다.

```
✅ 오매칭 0건          auto 는 사람 확인을 건너뛰므로 여기가 가장 중요하다
✅ 오탐 0건            명부에 없는 아이를 특정하지 않았는가
🟡 정답률              참고치. %p 변화를 과잉 해석하지 않는다
```

### 보고 양식

**0 건은 분모 없이 적지 않는다.** "오매칭 없음" 은 몇 번 봤는지를 숨긴다.

```
✅  오매칭 0건 / auto 15건
❌  오매칭 없음
❌  오매칭률 0%
```

한 줄 덧붙인다 — **"이번 측정에서 나오지 않았다"** 이지 "안 난다" 가 아니다.
실제 비율의 상한은 위 표대로 대략 3÷n 이다.

세트를 바꿔 가며 비교할 때는 **어느 세트인지와 누가 만들었는지** 를 같이 적는다.
숫자만 나란히 놓으면 난이도가 다른 세트끼리 비교하게 된다.

### τ 스윕은 관찰일 뿐이다

`score.py` 가 τ 를 바꿔가며 자동 확정 건수와 오매칭을 찍어 준다. **이건 보기만 한다.**

홀드아웃 결과를 보고 τ 를 실제로 바꾸면 그 순간 튜닝이고, 그 세트는 소모된다.
τ 를 조정하려면 dev 에서 정하고, 홀드아웃은 그 결정이 처음 보는 데이터에서
버티는지 확인하는 데만 쓴다.

## 한계 — 자체 생성 세트일 때

에이전트를 만든 사람이 문제도 내면 블라인드가 약해진다. 아는 규칙을 피해 가는
문장을 무의식적으로 쓰지 않기 때문이다. 자체 생성이 불가피하면 최소한 이 셋은 지킨다.

- 문장을 쓰는 동안 에이전트를 한 번도 돌리지 않는다
- `config.py` 를 열어 두고 쓰지 않는다 — 실제 일지에서 일어나는 일을 기준으로 쓴다
- 기준선과 나란히 채점한다

그래도 **"처음 보는 표현에서의 성능"** 은 이 방식으로 측정되지 않는다. 그건 다른
사람이 만든 세트로만 알 수 있다.

**데이터로 못 잡는 종류**도 있다. 자동 확정 게이트가 그렇다 — 모델이 어느 아이를
고르는지가 실행마다 흔들려서, 게이트를 고쳐도 차이가 잡음에 묻힌다. 2026-10-03 에
1,050건을 전후로 돌렸더니 달라진 3건이 전부 모델 쪽 흔들림이었고, 게이트 때문에
달라진 건은 0건이었다. 그 자리는 모델 응답을 고정한 `test_auto_gate.py` 로 잰다.

**빠뜨리기 쉬운 갈래**도 있다. 2026-09-30 세트에는 "표지가 맞고 본문에 다른 아이가
스쳐 지나간다" 가 없었다. 하필 `body-first` 기준선이 그 케이스에서 무너지는데,
세트에 없어서 기준선이 실제보다 좋아 보였다. 다음 세트에는 넣는다.

## 데이터는 커밋하지 않는다

가상 이름이어도 아동 관찰 기록 형태의 파일은 레포에 넣지 않는다. 생성 결과는
`evals/generated/` 아래에 두고, 이 디렉터리는 루트 `.gitignore` 가 막는다.
