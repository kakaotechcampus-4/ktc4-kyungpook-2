# 요약 평가

판정 기준은 [`AI/summary/CRITERIA.md`](../../../summary/CRITERIA.md) 에 있다.
여기는 **어떻게 재는가** 만 적는다.

```bash
python evals/scripts/summary/baseline.py <입력> /tmp/b.json --mode copy   # 규칙 기준선
python evals/scripts/summary/run_eval.py <입력> /tmp/a.json               # 에이전트 (LLM 호출)
python evals/scripts/summary/score.py /tmp/a.json --sample 10             # 채점
```

---

## 환각·누락 지표만으로는 아무것도 증명되지 않는다

**일지를 그대로 베끼면 그 지표들이 전부 만점이다.** 인용이 원문 그 자체라 대조를
통과할 수밖에 없다. 2026-10-06 에 3건으로 확인한 값이다.

| | 기준선 `copy` | 에이전트 |
| --- | --- | --- |
| 버려진 근거 | 0 / 6 | 0 / 6 |
| 반영돼야 할 일지를 전부 반영 | 3 / 3 | 3 / 3 |
| 통째로 인용한 근거 | 6 / 6 | 6 / 6 |
| **여러 일지에 걸친 문장** | **0 / 6** | **2 / 4** |

**가르는 것은 묶음 하나뿐이다.** 매칭에서 표지만 읽는 세 줄짜리 코드가 100% 를
받았던 것과 같은 일이고, 그래서 기준선을 나란히 돌린다.

베끼기가 못 하는 것은 둘이다 — **여러 일지를 한 문장으로 잇는 것**과 **좁은 구간을
인용하는 것**. 이 둘이 요약이 하는 일의 전부다.

---

## 다섯 가지를 본다

| 지표 | 무엇을 잡는가 | 누가 |
| --- | --- | --- |
| 버려진 근거·문장 | 모델이 원문에 없는 인용을 냈는가 (환각) | 코드 |
| `uncovered_entry_ids` | 반영 안 된 일지 (누락) | 코드 |
| 인용 길이 ÷ 원문 길이 | 근거가 좁은 구간인가 | 코드 |
| 여러 일지에 걸친 문장 | 묶었는가, 베꼈는가 | 코드 |
| **문장이 그 인용으로 설명되는가** | **과잉해석** | **사람** |

마지막 하나가 핵심이다. 앞의 넷이 전부 통과해도 문장이 인용을 넘어설 수 있다.
`--sample N` 이 시드 고정으로 표본을 뽑는다.

### 인용 길이를 따로 재는 이유

`1.0` 이면 일지를 통째로 인용한 것이다. 대조는 통과하지만 **Gate 1 에서 하이라이트가
일지 전체**라, 교사가 "이 문장 어디서 나왔지" 를 눌러도 아무것도 알려주지 못한다.
그 클릭이 Gate 1 에서 교사가 하는 일의 전부다.

2026-10-06 기준선은 **1.0 (6/6)** 이다. 프롬프트를 고치면 이 값이 내려가야 한다.

## 세트 양식

`SummaryInput` 그대로에 정답 필드를 더한다. 없는 필드는 그 지표만 건너뛴다.

```json
{
  "case_id": "S-01",
  "category": "하루 흐름",
  "child_id": 1,
  "child_name": "김지후",
  "entry_date": "2026-10-05",
  "institution_id": 7,
  "institution_name": "햇살학교",
  "sources": [
    {"journal_entry_id": 1041, "content": "오전 블록 놀이에서 혼자 다섯 층까지 쌓음."},
    {"journal_entry_id": 1042, "content": "오후 같은 블록 활동. 3번 교사 손을 잡고 올림."}
  ],

  "expected_covered_entry_ids": [1041, 1042],
  "expected_droppable_entry_ids": [],
  "expected_facts": ["오전에는 혼자 했고 오후에는 도움이 필요했다"],
  "expected_absent": ["박서연"]
}
```

| 필드 | 뜻 |
| --- | --- |
| `expected_covered_entry_ids` | 반드시 반영돼야 하는 일지. 빠지면 누락이다 |
| `expected_droppable_entry_ids` | 빠져도 되는 일지 ("특이사항 없음" 같은 것) |
| `expected_facts` | 담겨야 하는 사실. **사람이 표본에서 확인한다** |
| `expected_absent` | 나오면 안 되는 문자열. 코드가 본다 |

**묶음 단위는 아동 × 날짜 × 기관이다.** 한 케이스의 `sources` 는 전부 같은 기관
것이다 (CRITERIA.md §1). 기관을 가로지르는 비교는 인사이트가 한다.

### 넣어야 할 갈래

| 갈래 | 무엇을 재는가 |
| --- | --- |
| 하루 흐름 (오전/오후가 다름) | 이을 수 있는가. **베끼기와 갈리는 자리** |
| 빠져도 되는 기록이 섞임 | "특이사항 없음" 을 억지로 넣지 않는가 |
| 다른 아이 이름이 남아 있음 | 요약이 그 이름을 그대로 옮기는가 |
| 숫자가 들어간 기록 | 횟수·시간을 바꾸지 않는가 |
| 추측 표현("~인 듯함") | 단정으로 바꾸지 않는가 |
| 일지 1건뿐인 날 | 재료보다 길게 늘여 쓰지 않는가 |
| 긴 일지 (여러 문단) | 인용이 문단째 가지 않는가 |

## 블라인드 규칙은 매칭과 같다

[`../matching/HOLDOUT.md`](../matching/HOLDOUT.md) 를 따른다. 요약도 예외가 없다.

- **에이전트를 만든 사람이 그 세트를 쓰지 않는다.** 요약은 백주은이 만들었다
- 평가 전에 문장과 정답을 확정하고 봉인한다
- 돌리기 **전** 수정은 그대로 쓰고, 돌린 **뒤** 수정은 그 세트를 끝낸다
- 실패한 문장을 본 사람은 그 판정 로직 수정에 관여하지 않는다
- **0 건은 분모 없이 적지 않는다** — "누락 0 / 20건" 처럼 쓴다
