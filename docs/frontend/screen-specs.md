# 기관 화면

## I-01 로그인 · `/login`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 진입 | 루트 접속, 세션 없음, 역할 불일치 리다이렉트 |
| 인증 | 불필요 (공개) |

**기능**

1. "카카오로 로그인" 버튼 → 카카오 인가 화면으로 이동 (이때 `state` 발급·저장)
2. 카카오에서 로그인·동의 → `/oauth/kakao/callback` 으로 복귀
3. state 검증을 통과하면 인가 코드를 백엔드로 교환 → `/dashboard` 이동
4. 안내 문구: "학부모라면 기관에서 받은 초대 링크로 들어와 주세요"

**상태**

| 상태 | 화면 |
| --- | --- |
| 기본 | 카카오 로그인 버튼 |
| 키 미설정 | 버튼 비활성 + `.env` 안내 (`VITE_KAKAO_CLIENT_ID` 가 비어 있을 때) |
| mock | "mock 데이터로 둘러보기" 버튼 추가 (`VITE_AUTH_MOCK=true` 일 때만 렌더링) |

**호출 API** · `POST /api/v1/auth/kakao?code=`
→ `{ result, data: { accessToken, kakaoId, nickname }, message }`

> 기획서 12절의 **SMS OTP 는 폐기**됐습니다. 백엔드 인증이 카카오 OAuth + JWT 로
> 구현돼 있고 SMS 발송은 구현 자체가 없습니다.
>
> 역할(기관/학부모)은 아직 서버가 알지 못합니다 — JWT 의 subject 가 kakaoId 뿐이라
> 콜백이 `grantRole("org")` 로 로컬에 기록합니다. `GET /api/v1/auth/me` 가 열리면
> 그 응답으로 교체합니다.

## I-01b · 카카오 콜백 `/oauth/kakao/callback`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 진입 | 카카오가 인가 코드와 함께 브라우저를 이 주소로 보냄 |
| 인증 | 불필요 (공개) |

성공하면 화면을 그리지 않고 곧바로 리다이렉트합니다. **실패했을 때만** 안내를 띄웁니다.

| 경우 | 메시지 |
| --- | --- |
| state 불일치 · 누락 | "로그인 요청을 확인할 수 없어 중단했습니다" |
| 사용자가 동의 취소 (`error=access_denied`) | "카카오 로그인을 취소했습니다" |
| 인가 코드 없음 | "인가 코드가 없습니다" |
| 교환 실패 | "로그인에 실패했습니다" + 서버 메시지 |

> **순서가 중요합니다** — state 검증을 통과하기 전에는 인가 코드를 백엔드로 보내지
> 않습니다. 먼저 보내고 검증하면 CSRF 를 막는 의미가 사라집니다.
>
> `useEffect` 가 아니라 `clientLoader` 를 씁니다. 인가 코드는 한 번만 쓸 수 있는데,
> StrictMode 의 이펙트 이중 실행에 걸리면 두 번째 교환이 반드시 실패합니다.

**호출 API** · (현재 mock 상수 사용. `getMyInstitution` / `updateMyInstitution` 신규 필요)

## I-03 오늘의 업무 · `/dashboard`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 인증 | `role === "org"` |

**기능**

1. 처리 대기 4종 카드 — 각각 건수와 링크
   - 확인이 필요한 기록 → I-06 (AI가 아이를 확정하지 못함)
   - 수정 요청 → I-07 (BLOCK 판정, 원본 수정 필요)
   - 1차 검토 대기 → I-08 (요약의 사실 정확성 검토)
   - 공유할 기록 → I-11 (되돌릴 수 없는 지점)
2. 처리 중인 기록의 파이프라인 진행 상황 도식
   (기록 등록 → 매칭 → 검증 → 요약 → **1차 검토 대기**)
3. 4종이 모두 0건이면 빈 상태 — "지금 처리할 일이 없습니다"

**호출 API** · `getMatchingQueue`, `getBlockedQueue`, `getGate1Queue`, `getInsights`

**비고** · 파이프라인 아래 파일 목록은 현재 정적 예시입니다. 실제 연동 시 진행 중인
기록의 서버 상태로 교체합니다.

## I-04 아이 등록 · 초대코드 발급 · `/children/new`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 인증 | `role === "org"` |

**기능**

1. 이름(필수) · 생년월일(필수) · 기관 내부 아동 ID · 보호자 연락처 뒤 4자리(선택) 입력
2. "등록하고 초대코드 발급" → 초대코드 생성 (`ITDA-XXXX-XXXX` 형식)
3. 코드 복사 / 초대 링크 복사 / 재발급
4. 등록된 아이는 `pending_consent` 상태로 시작

**규칙**

- 보호자 전화번호 **전체는 입력하지 않습니다.** 뒤 4자리는 초대코드를 받은 사람이
  실제 보호자인지 대조하는 데만 쓰고, 연락처는 보호자가 직접 입력합니다(P-01).
- 초대코드 유효기간 **7일 · 1회용**.
- 보호자가 동의를 완료하기 전까지 이 아이의 기록은 올릴 수 없습니다.

**호출 API** · `registerChild`, `generateInviteCode`

> ⚠️ 초대코드는 현재 **클라이언트에서 생성**하고 있습니다. 유효기간·1회용 보장을 위해
> 서버 발급으로 옮겨야 합니다.

> ⚠️ 파이프라인 진행 표시는 현재 `setTimeout` 시뮬레이션입니다. 실제 연동 시 서버
> 상태 폴링 또는 구독으로 교체합니다.

## I-06 확인이 필요한 기록 · `/queue/matching`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 인증 | `role === "org"` |

**기능**

1. 큐를 한 건씩 표시 — 남은 건수, 이전/다음 이동
2. 기록 미리보기 (파일명 · 본문 · 유형 · 기록 시각)
3. 상태별 제목
   - `multi` — "이 기록에 해당하는 아이를 선택하세요" (+ 후보 N명)
   - `unmatched` — "일치하는 아이를 찾지 못했습니다"
   - `low` — "이 기록에 해당하는 아이를 확인하세요"
4. 확신도 경고 표시 (`unmatched`는 "이름이 기록에 없거나 인식되지 않았습니다")
5. 후보가 있으면 라디오 선택, 없으면 아이 이름으로 직접 검색
6. "선택한 아이로 확정" / "이 기관 아동 아님" → 큐에서 제거, 사이드바 배지 갱신

**규칙** · 낮은 확신도 기록에 **자동 확정 버튼을 두지 않습니다.** 후보가 있는데
선택하지 않으면 확정 버튼은 비활성입니다.

**호출 API** · `getMatchingQueue`, `resolveMatchingItem`

> ⚠️ 현재 `resolveMatchingItem(id)`는 선택한 `childId`를 서버로 보내지 않습니다.
> 실제 연동 시 `childId` 또는 "우리 기관 아동 아님" 플래그를 함께 전송해야 합니다.

## I-07 수정 요청 · `/queue/reinput`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 인증 | `role === "org"` |

**기능**

1. BLOCK 판정 기록을 카드 목록으로 표시
2. 카드마다 BLOCK 배지 · 파일명 · 아이 이름 · 기록 유형
3. **멈춘 이유**(`violationReason`)를 한국어 문장으로 노출
4. 원본 미리보기

**규칙** · 원본은 수정하거나 삭제하지 않습니다. 고친 내용을 **새 기록으로 추가**합니다
(append-only).

**호출 API** · `getBlockedQueue`, `resolveBlockedItem`

## I-08 1차 검토 · 요약 확인 · `/gate1`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기록을 등록한 선생님 |
| 인증 | `role === "org"` |

**기능**

1. 승인 대기 요약 목록 — 아이 · 기관 · 날짜 · 기록 유형 · 검증 배지
2. 근거 칩 ("○○ 원본 N건")
3. AI 요약 본문 표시. `REVIEW`면 사유가 된 문장(`flaggedSpan`)을 본문 안에서
   하이라이트하고 `flagReason`을 별도 표시
4. **승인** — 그대로 확정
5. **수정 후 승인** — 본문을 직접 편집한 뒤 확정 (`edited_content` 전송)
6. **반려** — 사유를 입력해 반려. 반려 카드는 목록 하단에 "반려됨 · 재작성 대기 중"
   으로 남고 사유를 표시

**규칙** · 반려하면 이 요약은 저장되지 않고, 등록한 원본 기록으로부터 다시 작성됩니다.

**호출 API** · `getGate1Queue`, `decideGate1`

## I-09-1 아동 상세 (Child Context) · `/children/:id`

**기능**

1. 아이 기본 정보 + 연결된 기관 · 동의 상태
2. **기록 타임라인 (승인된 요약)** — 날짜순
   - 하루마다 기록 유형 · 검증 배지 · 요약 본문 · `원본 N건 · v{버전}`
   - 선생님이 수정한 요약은 "선생님 수정" 배지
3. 우상단 "상담 도우미로 이동" → I-13
4. 승인된 요약이 없으면 빈 상태 + 안내
   (`pending_consent`면 "보호자 동의가 완료되기 전에는 기록을 올릴 수 없습니다")

**규칙**

- 기록이 없는 날은 **그대로 비워 표시**합니다. 추정치로 채우지 않습니다.
- **승인된 요약만** 표시합니다. 승인되지 않은 기록은 나타나지 않습니다.

**호출 API** · `getChild`, `getTimeline` · 없는 아이는 404

## I-10 관찰·분석 결과 · `/insights`

**기능**

1. 아이의 승인된 기록에서 도출된 패턴(Insight) 목록
2. 각 항목: 아이 · 기간 · Gate 2 상태 배지 · 본문
3. 근거를 제공한 기관 + 근거 기록 칩 (클릭 시 해당 아동 상세로 이동)
4. 내 기관이 `primarySource`이고 `pending`이면 "공유 검토하기" → I-11
   아니면 "이 결과는 근거를 제공한 ○○ 선생님이 검토합니다" 안내

**Gate 2 상태 라벨** · `pending` 발송 검토 대기 / `approved` 발송 승인됨 /
`sent` 발송 완료 / `held` 보류

**호출 API** · `getInsights`

## I-11 공유 전 검토 (Gate 2) · `/gate2`

| 항목 | 내용 |
| --- | --- |
| 사용자 | **근거 기록을 제공한 기관**의 선생님 |
| 인증 | `role === "org"` + `insight.primarySource.id === 내 기관` |

**기능**

1. 내 기관이 근거 제공자이고 `gate2Status === "pending"`인 Insight만 노출
2. 본문 · 근거를 제공한 기관 · 근거 기록 목록(기관 표시 포함)
3. **받는 기관 선택** — 체크박스
   - 동의한 기관(`granted`)만 선택 가능
   - 미동의(`not_granted`) · 회수(`revoked`) 기관은 🔒 잠금 + 사유 표시
     ("보호자가 동의하지 않은 기관입니다" / "보호자가 공유를 회수한 기관입니다")
4. "되돌릴 수 없습니다" 경고 상시 노출
5. **발송 승인 (N곳 선택됨)** → 완료 카드로 전환 ("발송은 되돌릴 수 없습니다")
6. **보류** → 보류 카드로 전환

**규칙 (가장 중요)**

- 수신 기관 체크박스 기본값은 **전체 해제**. 미리 켜두지 않습니다.
- **0곳 선택이면 발송 버튼 비활성.** 빈 배열로는 호출하지 않습니다.
- 미동의 기관은 **선택 불가 + 사유 표시**. 선택 후 거부되는 방식은 쓰지 않습니다.
- 각 기관에는 원본이 아니라 **동의 범위에 맞게 변환된 최소 정보**만 전달됩니다.

**호출 API** · `getInsights`, `decideGate2`

## 공통 UI 규칙

화면을 고칠 때 아래를 깨지 않는지 확인합니다. 제품 원칙에서 직접 나온 것입니다.

1. Gate 2 수신 기관 체크박스 기본값은 전체 해제. 0곳이면 발송 버튼 비활성.
2. 낮은 확신도 기록에 자동 확정 버튼을 두지 않습니다.
3. 상담 도우미 답변에는 항상 근거 출처를 붙이고, 없으면 "확인된 기록에는 없어요".
4. 아동 타임라인에서 기록이 없는 날은 비워 표시합니다.
5. 수신함에는 원본이 아니라 변환된 최소 정보만 표시합니다.
6. 학부모 화면에 자유질의 챗봇을 넣지 않습니다.
7. 미동의 기관은 선택 불가 + 사유 표시입니다.
8. 동의 회수/권한 끄기 화면에는 "이미 보낸 정보는 회수되지 않는다" 문구가 반드시 있어야 합니다.
9. 상태는 색 단독으로 전달하지 않습니다. 텍스트 라벨을 항상 함께 씁니다.
10. 기관 화면 본문은 16px 이상, 클릭 타깃은 44px 이상(`tap` 유틸).
11. 아이별 데이터는 반드시 `childId`로 조회합니다.
