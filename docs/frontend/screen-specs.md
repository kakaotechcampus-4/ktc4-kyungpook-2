# 화면별 기능 명세

> 기준 코드: `frontend/app/routes/`
> 상태: **화면 구현 완료 · mock 데이터로 동작 중**

기관 대시보드는 데스크톱(1440), 학부모 웹앱은 모바일(375, `md`/`lg`에서 카드 폭만

나눕니다(React Router v8 SPA 모드).

각 화면의 "호출 API"는 [feature-interfaces.md](feature-interfaces.md) §3의 함수명입니다.

# 기관 화면

## I-01 로그인 · `/login`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 진입 | 루트 접속, 세션 없음, 역할 불일치 리다이렉트, 기관 화면을 쓰다 로그인이 풀림 |
| 인증 | 불필요 (공개) |

**기능**

1. "카카오로 로그인" 버튼 → 백엔드의 `/oauth2/authorization/kakao` 로 **페이지 이동**
2. 이후 인가 · 토큰 교환 · state 검증은 전부 백엔드(Spring Security)가 처리
3. 끝나면 `/oauth/success` 로 돌아옴 (실패하면 이 화면으로)
4. 안내 문구: "학부모이신가요? 보호자 화면으로 가기" → `/parent/invite` 링크
5. 로그인이 풀려서 왔으면 버튼 위에 "로그인이 만료됐어요. 다시 로그인하면 보던 화면으로 돌아가요". 다시 로그인하면
   보던 화면으로 갑니다(아래 "로그인이 풀렸을 때")

**상태**

| 상태 | 화면 |
| --- | --- |
| 기본 | 카카오 로그인 버튼 |
| mock | "mock 데이터로 둘러보기" 버튼 추가 (`VITE_AUTH_MOCK=true` 일 때만 렌더링). 로그인 착지를 거치지 않아 보던 화면으로 돌아가지 않습니다 |
| 로그인이 풀려서 옴 | 만료 안내 한 줄 추가 (돌아갈 주소가 남아 있을 때) |

**로그인이 풀렸을 때** (기관 · 보호자 공통)

- 출입증은 쓰는 동안 서버가 연장하지만(api-spec 결정 표 2번), 오래 두거나 12시간이 지나면 풀립니다
- 기관 · 보호자 화면은 **화면을 옮길 때마다** 로그인이 풀렸는지 봅니다(가드 안쪽의 세션 확인 레이아웃, `/auth/me` 한 번).
  풀렸으면 가려던 주소(경로 + `?` 뒤)를 그 탭(sessionStorage `itda_return_path`)에 역할과 함께 남기고 로그인 화면으로 보냅니다 —
  기관은 이 화면, 보호자는 `/parent/invite`(P-01)
- 화면을 불러오다 `401` 이 나도 오류 화면 대신 같은 방식으로 로그인 화면으로 보냅니다
- 화면 안에서 저장하다 `401` 을 받으면 그 자리에 둡니다. 고치던 내용이 화면에 남아 복사할 수 있고, 다음에 화면을 옮길 때 로그인 화면으로 갑니다.
  저장하지 않은 입력은 검토(I-08)와 기록 확인의 고쳐야 할 기록(I-06)만 되살립니다(각 절 "로그인이 풀렸을 때").
  저장이 `401` 이면 그 화면은 "로그인이 풀렸어요. 다시 로그인한 뒤 시도해 주세요." 옆에 [다시 로그인]을 둡니다 — 지금 화면을 돌아올 곳으로
  남기고 기관은 이 화면, 보호자는 `/parent/invite` 로. 저절로 보내지 않습니다(검토 · 고쳐야 할 기록 · 준비물 · 보호자 아이 상세정보)

**호출 API** · 없음 — 페이지 이동뿐입니다. 프론트에 카카오 키도 필요 없습니다.

> 기획서 12절의 **SMS OTP 는 폐기**됐습니다. 백엔드 인증이 카카오 OAuth 로 구현돼 있고
> SMS 발송은 구현 자체가 없습니다.
>
> dev 에서는 버튼이 `http://localhost:8080` 으로 갑니다(`VITE_AUTH_ORIGIN`).
> Spring 이 자기가 받은 주소로 `redirect_uri` 를 조립하기 때문에, Vite 프록시를 거치면
> 카카오 콘솔 등록값과 어긋나 KOE006 이 납니다.

## I-01b · 로그인 착지 `/oauth/success`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 진입 | 백엔드가 로그인을 끝내고 돌려보냄 (`app.auth.success-redirect`) |
| 인증 | 불필요 (공개) |

**화면을 그리지 않습니다.** 도착하자마자 `GET /api/v1/auth/me` 를 물어 갈 곳을 정합니다
(api-spec §2.2). 출입증은 이미 httpOnly 쿠키로 심겨 있어 프론트가 받아서 처리할 것이 없습니다.

| `/auth/me` 응답 | 보내는 곳 |
| --- | --- |
| `withdrawal: "in_progress"` (탈퇴를 처리하는 중) | `/withdrawal` — 아래 줄보다 먼저 봅니다 |
| `signupCompleted: false` (처음 로그인) | `/signup` — 누른 버튼이 있으면 `?role=org\|parent` 로 미리 골라 둡니다 |
| `role: "org"` | 기관 약관에 동의했으면 `/dashboard`, 아니면 `/org-terms`(I-16) |
| `role: "parent"` | 온보딩을 마쳤으면 `/parent`, 아니면 `/parent/invite` |
| `401` | `/login` |

**보던 화면으로 돌아가기** · 로그인이 풀려 로그인 화면으로 갔던 사람은 남겨 둔 주소(I-01 "로그인이 풀렸을 때")로 보냅니다.
**역할이 같고 위 표의 결과가 보통 첫 화면(기관 `/dashboard` · 보호자 `/parent`)일 때만**입니다. 가입 · 약관 · 온보딩이
남았으면 그 화면이 먼저이고, 같은 탭에서 다른 역할로 로그인하면 쓰지 않습니다. 남긴 주소는 여기서 한 번 읽고 늘 지웁니다.

실패는 여기로 오지 않습니다 — 백엔드가 `/login` 으로 돌려보냅니다
(`app.auth.failure-redirect`).

## I-01c · 회원가입 `/signup`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 카카오 로그인만 하고 역할을 안 고른 사람 (기관·보호자 공통) |
| 진입 | `/oauth/success`, 또는 가입 전에 보호 화면에 들어가려던 경우 각 가드가 보냄 |
| 인증 | 로그인 + 가입 미완료. 비로그인이면 `/login`, 가입 완료면 역할별 첫 화면 |

이메일·비밀번호 입력은 없습니다. 역할을 고르고, 기관이면 기관 정보를 넣는 것까지가
가입입니다(api-spec §2.6). 역할은 가입한 뒤 바꿀 수 없다고 안내합니다.

| 입력 | 조건 |
| --- | --- |
| 역할 | 기관 담당자 / 보호자. 고르기 전에는 "가입하기" 비활성 |
| 기관명 | 기관일 때. 앞뒤 공백 제거, 1~100자 |
| 기관 유형 | 기관일 때. 학교 `SCHOOL` · 센터 `CENTER` · 활동지원사 `ACTIVITY_SUPPORT` |
| 사업자등록번호 | 기관일 때. 숫자만 남기고 10자리 (하이픈을 붙여넣어도 지웁니다) |

보호자를 고르면 기관 입력란은 숨기고, 요청에도 싣지 않습니다(`{ "role": "parent" }`).

**기관 가입 방법 전환 (#478)** · 기관을 고르면 맨 위에 "새 기관 등록 / 인계 코드로 가입"을 고릅니다.

| 방법 | 입력 | 요청 |
| --- | --- | --- |
| 새 기관 등록 (기본) | 위의 기관명 · 유형 · 사업자등록번호 | 기관 필드 3개 |
| 인계 코드로 가입 | 인계 코드 1칸(`XXXX-XXXX`, 공백 · 하이픈 · 소문자 허용). 안내: 이전 담당자가 [담당자 넘기기]에서 받은 코드이고, 가입하면 그 기관의 명부와 기록을 이어받으며 이전 담당자 계정은 탈퇴된다 | `{ "role": "org", "handoverCode": "K7P3QX9M" }` — 기관 필드는 싣지 않음 |

**결과 처리**

| 응답 | 화면 |
| --- | --- |
| `201` | 기관은 `/org-terms`(I-16, 약관부터), 보호자는 `/parent/invite`(약관부터) |
| `409 DUPLICATE_BUSINESS_NUMBER` | 사업자등록번호 아래 "이미 등록된 사업자등록번호입니다" |
| `400 INVALID_HANDOVER_CODE` | 인계 코드 아래 "코드가 맞지 않거나 시간이 지났어요. 이전 담당자에게 새 코드를 받아 주세요" |
| `409 ALREADY_SIGNED_UP` | `/auth/me` 를 다시 불러 역할별 첫 화면으로 |
| `400 INVALID_REQUEST` | "입력한 내용을 다시 확인해 주세요." |
| `401` | `/login` |
| `403` (CSRF) | "보안 확인에 실패했습니다. 새로고침한 뒤 다시 시도해 주세요." |

성공 후 재시도 버튼은 두지 않습니다 — 같은 요청을 두 번 보내면 409 입니다.

**회원 탈퇴** · 카드 아래 작은 "회원 탈퇴" — 역할을 고르기 전에도 떠날 수 있어야 합니다. 확인 시트는
[탈퇴 확인 시트](#탈퇴-확인-시트-공통)의 가입 전 문구입니다. 탈퇴를 처리하는 중인 사람은 이 화면 대신 `/withdrawal` 로 갑니다.

## I-16 기관 약관 동의 · `/org-terms`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 가입한 기관 담당자 중 기관 약관(지금 판)에 동의하지 않은 사람 |
| 진입 | 회원가입 직후 · `/oauth/success` · 기관 화면 가드(`/auth/me` 의 `termsAgreed: false`) · 기관 화면에서 API 가 `403 TERMS_NOT_AGREED` |
| 인증 | 비로그인 → `/login`, 가입 미완료 → `/signup?role=org`, 보호자 · 이미 동의한 기관 → 역할별 첫 화면 |

기관 화면 묶음 밖에 있어 머리띠 · 메뉴가 없습니다. 회원가입 화면과 같은 모양입니다.
약관 받기 · [보기] 창 · 판이 바뀌었을 때는 보호자 약관 단계와 같습니다 — [약관 동의 화면 공통](#약관-동의-화면-공통-i-16--p-01).

- 제목 "기관 서비스 이용에 동의해 주세요" · 설명 "보호자가 공유한 아이 정보를 다루는 기관의 약속까지 함께 받아요."
- 체크박스(모두 필수): 기관 서비스 이용약관 동의 `org_tos` · 담당자 개인정보 수집 동의 `org_privacy` · 아동 정보 보호 서약 `org_child_data`
- 셋 다 체크해야 "동의하고 계속하기". 아니면 "필수 동의를 선택해주세요". 저장 중에는 체크박스도 잠급니다

  - Esc · 닫기 · 바깥 누름으로 닫힙니다. 본문은 창 안에서 스크롤하고 뒤 화면은 스크롤되지 않습니다

  - 공용 목록 팝업(`ListPopup`)은 포커스를 창 안에 가두지 않아 쓰지 않습니다

**기록 올리기**

1. 끌어다 놓기 상자 — "관찰일지 파일을 끌어다 놓으세요" · 형식 · "20MB까지 · 여러 개를 한 번에 올릴 수 있어요" · [파일 고르기]
   (올리는 중엔 "올리는 중…"으로 꺼짐). 형식은 `UPLOAD_EXTENSIONS`(csv · txt · docx · pdf)에서 만들어 안내 · 실패 문구 · 파일 고르기 창이 같이 바뀝니다.
   그 아래 "스캔하거나 사진으로 만든 PDF는 글자를 읽지 못해요. 워드·한글에서 PDF로 저장한 파일을 올려 주세요"
2. 파일마다 `POST /raw-records` 를 한 번씩 보냅니다 — **2개씩 차례로** 보냅니다(#424). 서버가 글자 뽑기를 서버 전체에서 동시에 2건까지만 해서, 한꺼번에 보내면 여러 파일을 고른 선생님이 그 상한에 걸립니다. 끝나면 대시보드 값을 바로 다시 받습니다
3. 실패한 파일은 상자 아래 빨간 줄 "{파일명} · {사유}"([X]로 닫음, 다음 업로드 때 새 결과로 바뀜). 성공한 파일은 이미 저장돼 다시 올리지 않습니다 — 원본 중복을 막기 위해서입니다

| 원인 | 사유 |
| --- | --- |
| 형식이 아님(보내기 전에 거름) · 400 | "올릴 수 없는 형식이에요 (csv · txt · docx · pdf)" |
| 413 | "20MB를 넘는 파일이에요" |
| 400 `RAW_RECORD_ENTRY_LIMIT_EXCEEDED` (#424) | "기록이 500건이 넘거나 한 기록이 5,000자를 넘어요. 나눠 올려 주세요" |
| 429 `AGENT_QUEUE_FULL` (#424) | "앞서 올린 기록을 처리하고 있어요. 끝나면 다시 올려 주세요" |
| 429 `RAW_RECORD_UPLOAD_BUSY` (#424) | "지금 올리는 파일이 많아요. 잠시 뒤 다시 올려 주세요" |
| 그 밖(네트워크 · 401 포함) | "잠시 문제가 있어 저장하지 못했어요" |

- 세 코드는 상태 코드보다 먼저 `code` 로 가릅니다 — 400 · 429 를 상태 코드로만 보면 "형식" · "잠시 문제"로 잘못 보입니다. 문구의 500건 · 5,000자는 서버 상한과 같게 둡니다(500건은 서버 설정이라 바꾸면 문구도 고칩니다)

- 20MB 는 실제 서버 모드에서 화면이 미리 재지 않고 서버의 413 으로 압니다(mock 만 미리 거름)
4. **올린 파일**(O-26, 최근 업로드 먼저 · 서버가 최근 50개) — "올린 파일 N개" + "처리 중 n" · "실패 n". 없으면 "아직 올린 파일이 없어요"

## I-06 기록 확인 · `/check`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 인증 | `role === "org"` |
| 진입 | 메뉴 "기록 확인" · 대시보드 선생님 차례 · 진행 현황 [아이 고르기] · [고치기] |

`routes/org/check.tsx` · 옛 매칭 확인(I-06)과 검증 수정 요청(I-07)을 한 화면에 합쳤습니다. 두 칸 모두 [목록 + 처리 팝업](#목록--처리-팝업-기관-공통)입니다.

**진입 주소** · `?open=confirm` / `?open=blocked` 는 그 칸의 첫 건 팝업을 연 채로 엽니다. `&id=` 를 붙이면 그 건을 열고, 목록에 없으면 아무것도 열지 않습니다(다른 건으로 대신하지 않음). 연 뒤에는 주소의 `?` 뒤를 지웁니다.

**화면 구성**

1. 머리 — "‹ 대시보드" · 제목 "기록 확인" · [?] · "지금 할 일 · 아이 확인 N건 · 고쳐야 할 기록 M건"(둘 다 0이면 "할 일이 없어요")
2. **아이 확인 {n}** — 한 쪽 5건. 한 줄: 날짜(없으면 "날짜 모름") · 파일 표지 이름이 있으면 "표지 이름 '{이름}'", 없으면 파일명 · 본문 미리보기 · 칩("AI 추천 {이름}" / "직접 골라야 해요") · [확인하기].
   비면 "아이를 확인할 기록이 없어요"
3. **고쳐야 할 기록 {n}** — 한 쪽 5건. 한 줄: 아이(없으면 "아이 미정") · 날짜 · 미리보기 · 막힌 유형 칩(없으면 "확인 필요") · [고치기]. 비면 "막힌 기록이 없어요"

- 두 칸은 건수와 상관없이 한 쪽(5건) 높이로 고정합니다 — 쪽을 넘길 때 아래 칸이 올라오지 않게

**아이 확인 팝업**

1. 제목 "아이 확인" · 부제 "{날짜} 기록 · {표지 이름 또는 파일명}"
2. **일지 내용**(전체 본문, 없으면 미리보기)
3. 안내 — AI 가 한 명을 지목(`review`)했으면 "AI 추천 {이름} {생년월일}". 아니면 이유 + "명부에서 직접 골라 주세요."

| status · 사유 | 이유 문구 |
| --- | --- |
| `multi` · `co_mention` | 한 기록에 여러 아이가 함께 나와요. 대표 아이를 골라 주세요. |
| `multi` · 그 밖 | 이름만으로는 구별되지 않아요. 생년월일을 보고 골라 주세요. |
| `unmatched` | AI가 누구의 기록인지 찾지 못했어요. 일지에 이름이 없거나, 아직 명부에 없는 아이일 수 있어요. |
| `failed` | AI 판정을 받지 못했어요. |
| `review`(추천 아이를 명부에서 못 찾음) | AI가 한 명을 골랐지만 확정하지 않았어요. |

4. **어느 아이의 기록인가요?** — 명부(O-10) 아이 카드. 후보 · 추천 아이가 앞에 오고, 추천 아이를 고를 수 있으면 미리 골라 둡니다.
   우리 기관 동의가 `not_granted` 면 "보호자 동의 전", 그 밖에 `granted` 가 아니면 "기록 중단"으로 고를 수 없습니다.
   명부를 못 받으면 "명부를 불러오지 못했어요. 새로고침하면 전체 명부에서 고를 수 있어요." — 후보만으로 고릅니다
5. [우리 기관 아이가 아니에요] → O-23 `{ "action": "not_ours" }`(확인 창 없음) · [{이름}에게 연결](고르기 전엔 "아이를 골라 주세요"로 꺼짐) → O-23 `{ "action": "assign", "childId" }`

**고쳐야 할 기록 팝업**

1. 제목 "고쳐야 할 기록" · 부제 "{아이} · {날짜}"
2. 빨간 상자 "{막힌 유형} · {막힌 이유}" → **문장 고치기** 칸. 칸 아래 오른쪽에 "N / 5,000자". 5,000자를 넘으면 그 줄이 빨갛게 "5,000자까지 보낼 수 있어요 · N / 5,000자" 가 되고 [다시 보내기]가 꺼집니다(#424 — 고친 본문은 그대로 검증 AI 에 가므로 업로드한 기록 하나와 같은 길이까지). 칸에 글자 수 제한을 걸지 않습니다 — 붙여 넣은 글이 말없이 잘리면 뒤쪽이 사라진 줄 모릅니다. 상한 전에 올라온 긴 기록은 줄여야 보낼 수 있습니다
3. [다시 보내기] — 본문이 비지 않고 원래와 다를 때만(앞뒤 공백 무시) → O-25 revise `{ "content" }`. 고친 본문은 검증을 다시 받고, 통과하면 요약으로 이어지고, 또 막히면 이 칸에 다시 뜹니다 (#357)
4. [이 기록 빼기] → 확인 창 "이 기록을 뺄까요?" · "되돌릴 수 없어요" · "요약과 리포트에 쓰지 않아요." → O-25 resolve `{ "action": "hold" }`
5. 전체 본문을 받지 못했으면 읽기 전용 + "전체 본문을 불러오지 못해 앞부분만 보여요. 본문을 고칠 수 없어 이 기록은 빼 주세요."

**규칙**

- **확신도(confidence) 숫자를 보여주지 않습니다.** 모델 점수가 같은 입력에도 0.72~0.98 로 흔들려(`AI/matching/config.py`) AI 쪽도 자동 확정 판단에서 이 값을 뺐습니다. 화면에 숫자가 남으면 교사가 그것을 근거로 삼게 됩니다.
- **일괄 처리를 두지 않습니다.** 자동 확정이 걸러 주고 남은 것만 와서 건수가 많지 않고, 일괄 버튼은 "대충 넘기기"를 유도합니다.
- 올린 원본 파일은 고치거나 지우지 않습니다. 막힌 기록의 본문만 고칩니다.
- 서버가 보내지 않는 값(표지 이름 · 기록 시각 등)은 칸을 비우거나 다른 값으로 대신합니다. "undefined" 나 "이름 없음" 같은 거짓 안내를 찍지 않습니다.

**로그인이 풀렸을 때** · 고쳐야 할 기록만 고치던 본문을 지킵니다(아이 확인은 고를 것만 있어 맡기지 않습니다). 공통 규칙은 I-01 "로그인이 풀렸을 때".

- 저장 · 빼기가 `401` 이면, 그 순간부터 고칠 때마다 그 탭(sessionStorage `itda_reinput_draft`)에 맡깁니다 — 검사 결과 번호 · 원래 본문 · 고친 본문. 원래대로 돌리면 칸을 지웁니다
- 통신 오류처럼 서버 응답을 확인하지 못한 실패에서는 맡긴 본문을 유지합니다. `401` 이 아닌 서버 응답을 받으면(다른 탭에서 다시 로그인) 아직 팝업에 그리지 않은 칸만 남기고 지웁니다(`lib/carriedDraft.ts`)
- 다시 로그인해 이 화면에 오면 맡긴 글이 있는 첫 건을 저절로 엽니다(바로가기 `?open=` 으로 온 게 아닐 때). **같은 번호 · 같은 원래 본문**일 때 같은 기록으로 봅니다
  - 같으면 되살리고 "로그인 전에 고치던 내용을 되살렸어요."
  - 원래 본문이 바뀌었으면 "로그인하는 사이 기록이 바뀌어 고치던 내용은 지웠어요."
  - 목록에 없으면 위에 "로그인하는 사이 N건은 이미 처리돼 고치던 내용을 지웠어요."
- 로그아웃하면 지웁니다

## I-08 요약 검토 · `/gate1`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 우리 기관 선생님 |
| 인증 | `role === "org"` |
| 진입 | 메뉴 "요약 검토" · 대시보드 선생님 차례 · 진행 현황 [검토하기] · [다시 검토] · [확인하기] |

`routes/org/gate1.tsx` · 옛 요약 검토입니다. 카드 목록이 [목록 + 처리 팝업](#목록--처리-팝업-기관-공통)으로 바뀌었고, 요약 실패도 여기서 정합니다.
요약은 문장(`claims`)마다 [유지] · [수정] · [삭제]로 고르고 새 문장을 [추가]한 뒤 승인 한 번으로 보냅니다(C안, #221).

**진입 주소**

| 주소 | 열리는 것 |
| --- | --- |
| `?tab=hold` | [보류] 칸 (없으면 [전체]) |
| `?open=first` | 지금 칸의 첫 건 (요약 다시 만드는 중인 건 제외) |
| `?open=summary&id={요약 id}` | 그 요약. 목록에 없으면(그새 처리됨) 다른 건을 대신 열지 않음 |
| `?open=failed&child={아이 id}&date={YYYY-MM-DD}` | 그 날의 요약 실패 |

연 뒤에는 `tab=hold` 만 남기고 주소의 `?` 뒤를 지웁니다.

**화면 구성**

1. 머리 — "‹ 대시보드" · 제목 "요약 검토" · [?] · "지금 할 일 · 검토 N건 · 보류 N건"(없으면 "할 일이 없어요")
2. 칸 — [전체 N] · [보류 N]. N 은 방금 처리해 ✓ 로 보이는 건을 뺀 수
3. 목록(10건씩) — [전체]는 요약 실패 + 검토 대기를 **오래된 날짜부터, 같은 날은 실패 먼저**. [보류]는 서버 순서
   - 한 줄: 아이 · "M월 D일 (요일)" · 미리보기(첫 문장, 실패는 첫 일지) · 표시 · 버튼
   - 표시: "요약 실패" · "요약 다시 만드는 중"(버튼 없음, 열 수 없음) · "보류" · "특이사항 없음"(요약할 내용 없음) · "확인 필요"(경고가 있을 때)
   - 버튼: 실패 "확인하기" · 보류 칸 "다시 보기" · 그 밖 "검토하기"
   - 비면 "검토할 요약이 없어요" / "보류한 요약이 없어요"
4. 다음 단계 안내 — [전체]에 선생님이 열 수 있는 건이 0이면(요약 다시 만드는 중인 건만 남아도) 목록 아래에 "요약 검토를 다 마쳤어요." + 승인할 리포트 안내 + [주간 리포트 보러 가기 ›](`/children?tab=approve`).
   안내는 메뉴 배지와 같은 숫자(O-80 `turn.approve`)로 "승인을 기다리는 주간 리포트가 N건 있어요" / 0이면 "아직 승인할 주간 리포트는 없어요. 한 주가 끝나면 AI가 리포트를 만들어요"(버튼은 테두리만) / 숫자를 모르면 "다음은 주간 리포트를 읽고 승인하는 단계예요".
   다시 만드는 중인 건이 남았으면 아래에 "AI가 다시 만드는 요약 N건은 끝나면 여기서 검토할 수 있어요"

**검토 팝업** (검토 대기)

1. 제목 "{아이} · M월 D일 (요일)" · 부제 "문장마다 유지·수정·삭제를 고른 뒤 승인해 주세요"
2. 경고 — `needsReview` 면 "다른 아이 이름이 들어 있을 수 있어요"(그 밖 사유는 "공유 전에 한 번 더 확인해 주세요"), `reviewFlags` 가 있으면 "검증이 확인을 요청한 원본 일지 N건" 아래에 경고마다 한 줄 — "2 · 3번 문장 · {사유}"(O-30 `claimIndexes`), 문장 번호가 없는 경고(어디가 문제인지 모름 · 문장을 못 읽은 요약)는 "원본 일지 · {사유}". 막지 않고 알리기만 합니다
3. **AI 요약 N문장** — 줄마다 번호 · 문장 · [근거] · [유지][수정][삭제]
   - 검증 경고가 짚은 문장(`claimIndexes`): 경고색 테두리(유지 상태일 때만 — 수정 · 삭제 색을 가리지 않습니다) + 칩 "⚠ {사유}".
     그 문장을 짚은 사유가 둘 이상이면 어느 사유가 그 문장 것인지 몰라 "⚠ 검증 사유 N가지 · 위 안내를 봐 주세요". 칩은 고치거나 지워도 남습니다(경고는 원본 일지 기준)
   - 수정: 원문을 채운 입력칸(최대 1000자). 앞뒤 공백만 다르면 고치지 않은 것으로 봅니다. 고치면 원문을 취소선으로 아래에 두고 "수정함"
   - 삭제: 취소선 + "삭제함"
   - "+ 문장 추가": 점선 칸 "일지에 없던 사실을 적어요" · "새로 쓴 문장" · [빼기]. 원래 + 추가 문장이 100장이면 더 못 넣습니다
   - 문장을 못 나눈 요약(`claims` 0개)은 본문만 보이고 "문장을 나누지 못한 요약이라 그대로 승인하거나 제거해 주세요."
4. **원본 일지** — 늘 보입니다(O-30 `entries`). 요약에 안 들어간 일지는 흐리게 + "요약에 안 들어간 일지 N건 · 승인하면 함께 끝나요". 일지가 없으면 "원본 일지를 불러오지 못했어요"
5. **[근거]** — 한 번에 한 문장. 그 문장의 근거 인용(`claims[].evidence`)을 원본 일지에서 노랗게 칠합니다(`lib/evidence.ts`).
   인용 그대로 → 공백 · 문장부호 · 기호를 빼고 다시 찾습니다. 인용이 가리킨 일지를 먼저, 없으면 다른 일지에서 찾습니다

| 결과 | 안내 |
| --- | --- |
| 찾음 | 노란 부분이 고른 문장의 근거예요 |
| 못 찾음 | 근거 위치를 못 찾았어요. 원본 일지를 직접 읽어 봐 주세요 |
| 근거 인용이 없는 문장 | 이 문장에는 근거로 든 일지가 없어요. 원본 일지를 직접 읽고 맞는지 확인해 주세요 |

6. 버튼 줄 — [요약 제거] · "수정 a · 삭제 b · 추가 c" · [보류] · [승인](고친 게 있으면 [변경 내용으로 승인])

**승인 — 5초 뒤 보내고 [되돌리기]**

- 누르면 바로 ✓ 처리되고 다음 요약이 열립니다. 서버에는 **5초 뒤** 보냅니다(O-31). 0.7초 안에 다시 누른 승인은 무시합니다(키를 꾹 누름 방지)
- 토스트 "{아이} M월 D일 (요일) 요약을 승인했어요"(여러 건이 기다리면 " 외 N건") + [되돌리기]. **가장 최근 승인부터** 하나씩 취소합니다.
  목록에 되살리고, [전체] 칸에서 열린 팝업이 없으면 그 요약을 고치던 내용 그대로 다시 엽니다(같은 판일 때만). [보류] 칸에서는 목록에만 되살립니다
- 다른 화면으로 옮기면 기다리던 승인을 **바로** 보냅니다. 탭을 닫거나 새로고침하면 `keepalive` 로 보냅니다(이번에 보낸 본문 합이 60,000바이트를 넘으면 keepalive 없이 — 끊길 수 있음)
- 보내기가 실패하면 그 요약을 목록에 되살리고, 화면을 떠났어도 메뉴가 토스트로 알립니다(`lib/notice`)

| 실패 | 알림 |
| --- | --- |
| 401 | 로그인이 풀려 {아이} 승인을 보내지 못했어요. 다시 로그인하면 고치던 내용을 되살려요 (고치던 글을 맡김) |
| 409 `SUMMARY_REGENERATING` · `SUMMARY_CHANGED` | {아이} 요약에 새 기록이 들어와 승인하지 못했어요. 검토에서 다시 읽고 승인해 주세요 |
| 그 밖 | {아이} 승인을 보내지 못했어요. {오류 문구} |

**그 밖의 결정** — 승인 말고는 바로 보냅니다.

| 버튼 | 확인 창 | 보내는 것 |
| --- | --- | --- |
| [보류] | 고친 게 있을 때만 "{아이} 요약을 보류할까요?" · "고치던 문장은 저장되지 않아요" | O-31 `hold` |
| [요약 제거] | "{아이} 요약을 제거할까요?" · "이 요약과 그 일지를 모두 지워요."(+ 안 들어간 일지 수) · "제거하면 되돌릴 수 없어요" | O-31 `remove` |

- 바꾼 게 없으면 `cards` 없이 보냅니다(AI 요약 그대로 승인). 바꿨으면 원래 문장을 모두 순서대로 보내고 새 문장은 뒤에 붙입니다
- 남는 문장이 없으면 승인을 막고 "남는 문장이 없어요. 요약을 통째로 지우려면 요약 제거를 눌러 주세요.", 수정칸이 비면 "고칠 문장이 비어 있어요. 문장을 빼려면 삭제를 눌러 주세요."
- 팝업을 닫으면(✕ · Esc · 바깥) 고치던 내용은 남지 않습니다(묻지 않음). 승인을 되돌렸거나 로그인이 풀려 맡긴 경우만 되살립니다

**요약할 내용 없음 팝업** (`noContent`, #244) — 부제 "AI가 특이사항을 찾지 못했어요" · "이날 기록에는 특이사항이 없어요" + 원본 일지. 안내는 "기록에 따로 알릴 관찰이 없어 요약을 비워 뒀어요. 아래 원문을 읽고 [확인]으로 마무리해 주세요."
  일지가 "특이사항 없음" 뿐인 날도 요약 실패가 아니라 AI 를 거치지 않고 여기로 옵니다 (기술멘토링 11/9, #448)

- [다시 요약] → 확인 "{아이} 기록을 다시 요약할까요?" · "이 결과는 목록에서 빠지고, 그 사이 들어온 같은 날 기록과 함께 AI가 새로 요약해요." → O-31 `revert`
- [확인] → 확인 "{아이} 기록을 요약 없이 끝낼까요?" · "확인하면 되돌릴 수 없어요" · 아동 타임라인에 올라가지 않음 → O-31 `confirm`

**보류 팝업** — 부제 "보류한 요약은 보호자와 다른 기관에 가지 않아요". 문장은 읽기만 하고 원본 일지를 함께 보입니다.

- [보류 풀기] → 확인 "{아이} 요약의 보류를 풀까요?" · "AI 요약 그대로 전체 칸으로 돌아가요." → O-33
- [요약 제거] → 위와 같은 확인 → O-31 `remove`

**요약 실패 팝업** (O-35~37) — 부제 "요약 실패 · 선생님이 정해 주세요". "AI가 요약을 마치지 못했어요." + 사유 + 원본 일지 N건

- 사유: `NO_GROUNDED_CLAIMS` "요약 문장의 근거를 원문에서 찾지 못했어요.", 그 밖 "원본 일지를 보고 정해 주세요."
- [다시 요약] → 확인 없이 O-36. 또 실패하면 다시 이 카드로 옵니다
- [요약 없이 마무리] → 확인 "{아이} 기록을 요약 없이 끝낼까요?" · "되돌릴 수 없어요" · "이날 기록 N건은 보호자·아동 기록·주간 리포트로 가지 않아요." → O-37

**처리 결과(✓ 줄)** · "AI 요약 그대로 승인했어요" · "고친 내용으로 승인했어요" · "보류로 옮겼어요" · "요약을 제거했어요" ·
"보류를 풀었어요 · 전체 칸에서 다시 볼 수 있어요" · "요약 없이 마무리했어요" · "다시 요약하도록 돌렸어요"

**오류** (승인 외 결정)

| 응답 | 화면 |
| --- | --- |
| 409 `SUMMARY_CHANGED` · `SUMMARY_REGENERATING` | 팝업을 닫고 "새 기록이 들어와 요약을 다시 만들고 있어요" + 목록 다시 받기 |
| 409 `SUMMARY_ALREADY_REVIEWED` | 닫고 "이미 처리된 요약이에요. 목록을 새로 불러왔어요." |
| 409 `SUMMARY_HELD` | 닫고 "보류된 요약이에요. 보류함에서 보류를 해제한 뒤 승인해 주세요." |
| 409 `SUMMARY_NOT_HELD` | 닫고 "이미 보류가 풀린 요약이에요. 검토 대기에서 확인해 주세요." |
| 400 `SUMMARY_INVALID_REQUEST` | 닫고 "고친 문장이 지금 요약과 맞지 않아요. 목록을 새로 불러왔으니 다시 확인해 주세요." |
| 400 `INVALID_REQUEST` | 팝업 안 "고친 문장을 보내지 못했어요. 빈 문장이나 1000자가 넘는 문장이 없는지 확인해 주세요." |
| 429 `AGENT_QUEUE_FULL` (#424, 요약할 내용 없음 [다시 요약] · 요약 실패 [다시 요약]) | 팝업 안 "앞서 올린 기록을 처리하고 있어요. 끝나면 다시 해 주세요." |
| 404 | 닫고 "더 이상 볼 수 없는 요약이에요. 목록을 새로 불러왔어요." (요약 실패는 "이미 처리했거나 볼 수 없는 기록이에요. 목록을 새로 불러왔어요.") |
| 401 | 팝업을 두고 "로그인이 풀렸어요. 다시 로그인한 뒤 시도해 주세요." + [다시 로그인] |
| 403 | "보안 확인에 실패했어요. 새로고침한 뒤 다시 시도해 주세요." |
| 그 밖 | "처리하지 못했어요. 잠시 뒤 다시 시도해 주세요." (네트워크 오류는 "네트워크 연결을 확인하고 다시 시도해 주세요.") |

**로그인이 풀렸을 때** · 공통 규칙은 I-01 "로그인이 풀렸을 때". 이 화면은 고치던 문장을 더 지킵니다.

- 결정(또는 기다리던 승인 보내기)이 `401` 이면, 그 뒤로 검토 팝업에서 고칠 때마다 그 탭(sessionStorage `itda_gate1_draft`)에 맡깁니다 —
  요약마다 판(`version`) · 문장별 처리 · 고친 글 · 새 문장. 고친 게 없으면 칸을 지웁니다
- [다시 로그인]은 이 화면을 돌아올 곳으로 남기고 로그인 화면으로 갑니다. 저절로 보내지 않습니다
- 다시 로그인해 이 화면에 오면 맡긴 글이 있는 첫 요약을 [전체] 칸에서 저절로 엽니다(바로가기 `?open=` 으로 온 게 아닐 때)
  - 판 · 문장 수가 같으면 되살리고 "로그인 전에 고치던 내용을 되살렸어요." 저장은 다시 눌러야 합니다
  - 판이 바뀌었거나 "요약할 내용 없음"이 됐으면 "로그인하는 사이 요약이 바뀌어 고치던 내용은 지웠어요."
  - 검토 대기에 없으면(처리 · 보류 · 다른 기관) 목록 위에 "로그인하는 사이 N건은 이미 처리돼 고치던 내용을 지웠어요."
  - 팝업에 반영한 칸은 저장소에서 지웁니다
- `401` 뒤 다른 요청이 서버에 닿으면(다른 탭에서 다시 로그인) 이 화면이 맡긴 칸을 지웁니다. 로그아웃하면 모두 지웁니다
- 맡긴 사람과 다시 로그인한 사람을 비교하지 않습니다. 서버가 우리 기관 요약만 주므로 다른 기관에는 되살아나지 않습니다

**호출 API** · `getGate1Queue`(O-30, `pending` · `hold`), `decideGate1`(O-31), `reopenGate1`(O-33),
`getFailedSummaries`(O-35), `retryFailedSummary`(O-36), `closeFailedSummary`(O-37)

## I-09 아동 목록 · `/children`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 기관 담당 선생님 |
| 인증 | `role === "org"` |
| 진입 | 메뉴 "아동 목록" · 대시보드 [리포트 승인] · [보호자 연결 요청] · 잇다 시작하기 · 새 리포트 알림 [보기] |

`routes/org/children.tsx` · 옛 아이 등록(I-04) · 아동 상세(I-09-1) · 관찰·분석 결과(I-10) · 공유 전 검토(Gate 2, I-11) · 메시지(I-12)를 합쳤습니다.
세 칸(아이 · 리포트 승인 · 연결 요청)과 아이 팝업 · 등록 팝업으로 이뤄집니다.

**진입 주소**

| 주소 | 열리는 것 |
| --- | --- |
| `?tab=kids`(기본, 주소에선 생략) · `approve` · `req` | 그 칸 |
| `?register=1` | 등록 팝업 |
| `?child={id}` | 그 아이 팝업 [리포트] 탭 (명부에 없으면 열지 않음) |
| `?tab=approve&open=insight&id={id}` | 그 리포트 (없으면 대신 열지 않음). `open` 이 그 밖 값이면 첫 건 |

연 뒤에는 `tab` 만 남기고 주소의 `?` 뒤를 지웁니다.

**화면 구성**

1. 머리 — "‹ 대시보드" · "아동 목록" · [?] · 오른쪽에 **우리 기관 코드** "XXXX-XXXX [복사]"(O-01, 못 받으면 숨김) · [+ 아이 등록].
   우리 기관 코드는 이미 다른 기관에 다니는 아이의 보호자에게 알려 줘 연결 요청을 받는 데 씁니다
2. 칸 — [아이 N](안 읽은 받은 리포트가 있으면 빨간 점) · [리포트 승인 N] · [연결 요청 N](0이면 숫자 숨김)
3. **[아이] 칸** (10명씩)
   - 검색 "이름 또는 관리번호"(대소문자 무시, 부분 일치) + 동의 거르기 [전체][동의함][보호자 동의 전][동의 철회] (#396). 바꾸면 1쪽으로, 주소에 남지 않습니다. 결과가 없으면 "조건에 맞는 아이가 없어요"
   - 승인할 리포트나 안 읽은 받은 리포트가 있는 아이가 위로, 나머지는 명부 순서
   - 아이 카드: 이름 · "생년월일 · #관리번호" · "새 리포트 N" · 동의 칩("보호자 동의 전" / "동의 철회", 누르면 아이 팝업 [보호자] 탭) · [새 리포트 읽기](첫 안 읽은 글을 바로 엶) 또는 [열기]. 카드 아무 곳이나 눌러도 이 버튼과 같게 열린다
   - 명부가 비면 "아직 등록한 아이가 없어요"
4. **[리포트 승인] 칸** = Gate 2 — 우리 기관이 승인할 차례인 리포트(O-40 `pending`). 줄: 아이 · "{기간} · 기록 N건" · 미리보기 · "교사 작성 포함" 또는 "리포트 도착"(+ 지난 기록 근거가 있으면 "지난 기록 포함") · [읽고 승인].
   누르면 아이 팝업이 그 리포트를 띄운 채 열리고, 처리하면 다음 리포트가 이어서 열립니다. 비면 "승인할 리포트가 없어요"
5. **[연결 요청] 칸** (O-60, 10건씩) — 보호자가 우리 기관 코드로 보낸 요청. 비면 "기다리는 연결 요청이 없어요"
   - 카드: 아이 · 생년월일 · "MM.DD HH:mm 요청" · "요청한 보호자 · 이름들"(없으면 "이름 없는 보호자") · "기관 내부 아동 ID" 입력(50자) · [수락] · [거절]
   - [거절] → 그 자리에서 [취소][거절하기] + "거절해도 보호자에게 따로 알리지 않습니다. 보호자는 다시 요청할 수 있습니다." (O-62)
   - [수락](O-61) — 비어 있으면 "관리번호를 입력해 주세요". 수락한 아이는 "보호자 동의 전"으로 명부에 나타납니다

| 응답 (연결 요청) | 화면 |
| --- | --- |
| 409 `DUPLICATE_EXTERNAL_ID` | 관리번호 칸 아래 "이미 사용 중인 관리번호입니다". 요청은 남습니다 |

**규칙**

- **받을 기관을 고르는 단계는 없습니다.** 승인하면 보호자와, 보호자가 공유에 동의해 둔 기관(`granted`)에 바로 열람 권한이 생깁니다(#233). 승인 뒤 동의한 기관은 지난 글을 받지 않습니다.
- 리포트 승인 · 보류 모두 **되돌릴 수 없습니다.** 그래서 두 버튼 모두 확인 창을 거칩니다. 각 기관에는 원본이 아니라 동의 범위에 맞게 변환된 최소 정보만 갑니다.
- **다른 기관 정보(그 아이가 다니는 다른 기관 · 그 기관의 동의)는 보이지 않습니다** (#297). 보호자는 기관마다 따로 동의할 뿐 다른 기관에 알리는 데 동의하지 않았습니다.
  예외는 리포트 승인의 "승인하면 볼 수 있는 곳"과 받은 글의 보낸 기관입니다 — 승인하면 어디로 가는지 알고 눌러야 해서입니다.
- 동의 상태는 **우리 기관 기준 동의(`consent`)** 로 고릅니다: `granted` 동의함 / `not_granted` 보호자 동의 전 / `revoked` 동의 철회. 아이 전체 상태(`status`)는 쓰지 않습니다.
- [기록]에는 **우리 기관이 승인한 요약만** 보입니다. 다른 기관 기록은 승인을 거친 리포트로만 봅니다. 기록이 없는 날은 만들지 않습니다.
- 초대 코드는 **10분 · 1회용**입니다. 한 아이에 여러 개를 발급해 보호자마다 따로 보낼 수 있고, 보호자 연락처는 받지 않습니다. **이미 다른 기관에 다니는 아이는 새로 등록하지 않고** 우리 기관 코드로 연결 요청을 받습니다.

## I-15 준비물·확인사항 · `/checklists`

기관이 명부의 아이들에게 준비물 · 확인할 것을 보내고, 보호자가 확인했는지 봅니다(api-spec §4.7). 머리띠 메뉴의 마지막 칸입니다.
공유 동의와 상관없이 명부에 있는 아이에게 보냅니다.

**새 요청** ([+ 새 요청]으로 펼침 · ✕ 는 입력을 비우고 접음) — "보낸 뒤에는 고칠 수 없어요. 잘못 보냈으면 내리고 다시 보내 주세요."

1. 항목 줄 — 1~10줄, 줄마다 100자(글자 수 표시, 넘으면 빨갛게). "+ 줄 추가" · 줄 지우기
2. 받을 아이 — "명부 전체 (N명)" 전체 선택/해제 + 명부(O-10)의 아이 체크박스. 고른 수 표시. 명부가 비면 "명부에 아이가 없어요. 아동 목록에서 먼저 등록해 주세요."
3. [보내기] → 확인 창 "**N명에게 보냅니다**" + 항목 목록 + "보낸 뒤에는 고칠 수 없고 내리기만 할 수 있어요." → O-70

2. 줄 아무 곳이나 누르면 펼치고 접습니다([내리기] 제외). 펼치면 — 항목 전부 + 아이별 "확인 · {보호자} · {일시}" / "확인 전" / "명부에서 빠짐"(줄 그음, 숫자에서 빠짐). 보호자 중 한 명이 확인하면 그 아이 몫은 끝납니다
3. [내리기] → 확인 창 "이 요청을 내릴까요?" · "받은 아이 모두의 보호자 화면에서 사라져요. 되돌릴 수 없어요." → O-72(이미 내렸어도 성공).
   실패하면 목록 위에 "내리지 못했어요. 새로고침한 뒤 다시 시도해 주세요.", `401` 이면 로그인 풀림 문구 + [다시 로그인]
4. **쪽 번호** — 받아 둔 목록을 10건씩 나눠 보입니다. 서버는 여전히 50건씩(`nextBefore`) 주고, **마지막 쪽에서만** [이전 요청 더 보기]가 보입니다.
   누르면 50건을 더 받아 새로 받은 첫 건이 있는 쪽으로 옮깁니다. 실패하면 "이전 요청을 불러오지 못했어요. 다시 시도해 주세요."
   보내기 · 내리기로 첫 쪽을 다시 받으면 더 받아 둔 것은 버리고 처음부터 다시 셉니다
5. 없으면 "아직 보낸 요청이 없어요" · "위에서 첫 요청을 보내 보세요."

  첫 화면 · 새로고침 · 선생님이 처리한 뒤 다시 받은 값으로는 알리지 않습니다
- **떠난 화면의 실패 알림** — 검토에서 기다리던 승인이 화면을 떠난 뒤 실패하면 메뉴가 8초 토스트로 알립니다(`lib/notice.ts`)

### 목록 + 처리 팝업 (기관 공통)

기록 확인 · 요약 검토 · 아동 목록(리포트 승인)은 같은 틀입니다 — `components/ui/ListPopup.tsx`(`ListPopup` · `useWalk`), `Pager.tsx`, `components/org/WorkList.tsx`.

- 목록 줄의 버튼을 누르거나 **줄(카드) 아무 곳이나 누르면** 처리 팝업이 뜹니다(버튼이 없는 줄 — 요약을 다시 만드는 중 — 은 눌러도 안 열림). 머리에 제목 · 부제 · "n / N"(남은 건이 2건 이상일 때) · ✕
- **처리하면 다음 건이 이어서 열립니다.** 처리한 줄은 "✓ … · 처리했어요"처럼 바뀌었다가 2초 뒤 목록에서 빠지고, 팝업은 같은 자리의 다음 건(없으면 앞 건)으로 넘어갑니다. 남은 게 없으면 닫힙니다.
  약 2초 뒤 목록과 메뉴 배지를 서버와 맞춥니다
- 닫기: ✕ · 바깥 누르기 · Esc. 처리 중에는 닫히지 않습니다. 위에 확인 창이 떠 있으면 Esc 는 확인 창만 닫습니다
- 팝업이 떠 있는 동안 뒤 화면은 스크롤되지 않습니다. 화면 폭 520px 이하에서는 아래에서 올라오는 시트입니다
- **쪽 번호** — 기록 확인은 5건, 나머지는 10건씩. 한 쪽뿐이면 숨기고, "1–10 / 22건" + ‹ 1 2 3 ›(7쪽이 넘으면 처음 · 끝 · 지금 앞뒤만). 쪽 번호는 주소에 남지 않고, 처리로 지금 쪽이 없어지면 마지막 쪽으로 갑니다
- 키보드 단축키(승인 · 보류 · 이동)는 두지 않습니다 — 잘못 눌러 승인될 수 있습니다
- 화면 자체는 다시 묻지 않습니다(폴링 없음). 목록은 처리 뒤에만 다시 받고, 메뉴 배지만 10초마다 바뀝니다. 대시보드만 10초마다 다시 받습니다

## P-01 보호자 진입 · `/parent/invite`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 보호자 (최초 진입 · 아이 추가) |
| 인증 | 불필요 (공개) — 화면 안에서 카카오 로그인을 시작합니다 |

**단계**

| 단계 | 내용 |
| --- | --- |
| `intro` | 서비스 소개 + "카카오로 시작하기" → 백엔드 `/oauth2/authorization/kakao` 로 페이지 이동. 보호자 화면을 쓰다 로그인이 풀려서 왔으면 버튼 위에 "로그인이 만료됐어요. 다시 로그인하면 보던 화면으로 돌아가요" (I-01 "로그인이 풀렸을 때") |
| `terms` | 약관 동의 (카카오 동의와 별개) — "동의하고 계속하기"가 서버에 저장한다(`POST /auth/terms`) |
| `code` | 초대 코드 입력 → 수락(G-04). 보관된 코드가 있으면 들어오자마자 자동으로 수락 |
| `done` | 연결 결과 — "△△ 학생과 연결됐어요" + 동의가 남았으면 "아직 공유 동의가 남았어요. 동의해야 기관 기록이 △△에게 이어져요" + "공유 동의하러 가기"(이미 동의했으면 "공유 내용 확인하기") → `/parent/consent?childId=&institutionId=` |

진입 지점에 따라 시작 단계가 다릅니다.

| 들어온 사람 | 시작 단계 |
| --- | --- |
| 처음 오는 보호자 (초대 링크 포함) | `intro` |
| 약관에 동의하지 않은 보호자 — 막 가입했거나, 약관 판이 바뀌었거나 (`/auth/me` 의 `termsAgreed: false`) | `terms` |
| 약관에 동의한 보호자 ("아이 추가"나 새 초대 링크로 들어옵니다) | `code` (첫 연결을 마쳤으면 진행 표시 대신 "‹ 홈으로") |
| 기관 계정으로 로그인한 사람 | "기관 계정으로 로그인돼 있어요" 안내 + 기관 화면으로 |

**회원 탈퇴** · `terms` · `code` 단계 아래 작은 "회원 탈퇴". 약관에 동의하지 않았거나 연결된 아이가 없는 보호자는
입구(guard)가 설정(P-04)으로 보내지 않아서, 여기서 떠날 길을 둡니다. 확인 시트는 [탈퇴 확인 시트](#탈퇴-확인-시트-공통)의
보호자 문구입니다. 탈퇴를 처리하는 중인 보호자는 이 화면 대신 `/withdrawal` 로 갑니다(입구 · 세션 확인도 같습니다).

**초대 코드 보관** · `?code=`가 있으면 sessionStorage(`itda_invite_code`)에 보관합니다.
카카오 로그인 · 회원가입을 다녀와도 남아 있고, 로그인이 끝나면 `homePathFor`가 보관된 코드가
있는 보호자를 이 화면으로 보냅니다. 처음 가입하는 사람은 가입 화면에서 "보호자"가 미리
골라집니다. 수락에 성공하거나(이미 연결됨 포함) 코드가 틀리면 지웁니다.

카톡 인앱 브라우저에서 외부 브라우저로 넘어가면 sessionStorage가 사라질 수 있어 `code`
단계에 직접 입력 칸을 둡니다. 공백 · 하이픈 · 대소문자는 서버가 무시합니다.

**수락 결과**

| 응답 | 화면 |
| --- | --- |
| 200 | `done` — `childStatus`가 `pending_consent`면 "아직 공유 동의가 남았어요". 수락은 아이 상태를 바꾸지 않습니다 |
| 409 `LINK_ALREADY_EXISTS` | 이미 연결된 아이 — 실패로 보지 않고 다음으로. 온보딩을 마친 보호자는 `/parent`, 아니면 "이미 연결된 아이예요" |
| 400 `INVALID_INVITE_CODE` | "코드가 올바르지 않거나 만료됐어요. 기관에 새 코드를 요청하세요." |
| 403 `PARENT_REQUIRED` | "기관 계정으로 로그인돼 있어요. 보호자 카카오 계정으로 다시 로그인해 주세요." |
| 403 `SIGNUP_NOT_COMPLETED` | `/signup?role=parent` |
| 403 `TERMS_NOT_AGREED` | `terms` 로 — 코드 단계를 연 채 약관 판이 바뀐 경우. 동의하면 보관된 코드를 다시 자동 수락 |

**약관 항목**

| 키 | 라벨 | 필수 |
| --- | --- | --- |
| `tos` | 서비스 이용약관 동의 | 필수 |
| `privacy` | 개인정보와 민감정보 수집 동의 | 필수 |

선택 항목 "새로운 소식 알림 받기"는 뺐습니다 — 알림을 보내는 기능이 없습니다(#337).

| 200 · 코드 없음 · 이미 아이가 연결됨 | `/parent` — 약관 판이 바뀌어 다시 동의한 보호자 |

4. **동의하면 이렇게 돼요** — 기관 유형과 상관없이 같은 세 줄(○○ 기관, △△ 아이)
   - ○○ 선생님이 쓴 △△ 기록을 AI가 정리하고, 선생님이 확인한 글을 보호자에게 보여줘요.
   - 확인된 기록으로 만든 주간 리포트를, 아이가 다니는 다른 기관 중 동의한 곳과 서로 볼 수 있어요.
   - 언제든 설정 > 기관 권한에서 끌 수 있어요. 끄면 이 기관은 받은 리포트를 더 볼 수 없고, 이 기관 기록이
     들어간 리포트도 다른 기관에서 가려져요.
5. 동의 체크 "위 내용대로 ○○ 공유에 동의합니다. 언제든 설정 > 기관 권한에서 끌 수 있어요." → 하단 고정 "동의하고 시작하기"
6. 온보딩 중이면 `markOnboarded()` 후 `/parent`, 이미 온보딩을 마친 보호자도 `/parent`
   (설정·알림에서 들어왔으면 그 화면으로 돌아갑니다)

**규칙**

- 동의하지 않으면 다음으로 넘어갈 수 없습니다.
- 동의 버튼은 스크롤 위치와 무관하게 보이도록 **하단 고정**입니다.
- 이 화면은 최초 동의와 **이후 새 기관의 권한 요청**을 겸합니다
  (둘 다 `not_granted` 상태인 기관을 찾아 표시).
- 대상은 `?childId=&institutionId=` 로 받습니다 — P-01 이 초대 코드를 수락한 뒤 지정해
  보냅니다. 쿼리가 없으면 P-01 로 돌려보내고, 동의할 내용을 찾지 못하면 다른 아이로 채우지
  않고 "동의할 내용을 찾을 수 없어요"를 보여 줍니다. G-02 는 이미 이 기관에 동의한 경우도
  404 로 주므로 같은 안내가 나갑니다.
- 동의할 때는 G-02 가 준 `allowedFields`(항목 코드)를 G-41 에 그대로 보냅니다.
- **지킬 수 있는 것만 적습니다.** 예전의 기관 유형별 항목 목록("알레르기 정보 공유 · 의료 기록 공유 안 함" 등)은 거르는
  코드가 없는 약속이라 지웠습니다(#310). 진단명 · 개인정보 검사도 AI 판단이라 놓칠 수 있어 약속하지 않습니다.

**오류 처리**

## P-14 리포트 상세 · `/parent/report/:id`

**기능**

2. 승인 기관과 "10월 28일 ○○초등학교에서 정리했어요"(기관을 모르면 "기관 정보 없음" · "10월 28일 정리됨")

5. **함께 보는 기관** — 지금 이 글을 볼 수 있는 다른 기관, 이름순. 기관 수신함 · 공유 내역(P-05)과 같은 기준(권한 · 명부 · 동의)이라

6. 안내 "기관별 공유 동의를 끄면 그 기관은 더 이상 이 글을 볼 수 없어요." + "설정에서 공유 동의 보기" → P-04.

7. 처음 열면 서버가 본 시각을 남깁니다(G-36). 그래서 목록의 "새 글"과 하단 탭의 점이 꺼집니다

3. **기관 권한** — 기관별 토글
   - 기관 줄에 받은 리포트가 있으면 "받은 리포트 N편 · 가려짐 K ›"(가려진 것이 없으면 뒷부분 생략) → P-05. 0편이면 없음.
     권한이 꺼진 기관도 받은 이력이 있으면 보입니다(#317)
   - 끄기를 누르면 확인 시트 "○○ 권한을 끌까요?" → G-41 revoke, 응답의 `consent` 로 표시를 고치고 공유 내역을 다시 불러와
     "가려짐 K" 를 바로 고칩니다(끈 기관 기록이 들어간 리포트를 받은 **다른 기관** 개수도 함께 바뀔 수 있음)
     - **이 기관은 받은 주간 리포트를 더 볼 수 없어요. 이 기관 기록이 들어간 리포트도 다른 기관에서 가려져요.**
     - 앞으로 이 기관이 올리는 기록은 △△ 기록으로 정리하지 않아요. 이미 처리 중이던 기록은 마저 정리될 수 있어요.
     - 이 기관이 이미 쓴 기록은 기관에 남아요.
     - 보호자님은 지금처럼 모든 기록과 리포트를 볼 수 있어요.
     - 다른 보호자가 이 기관에 한 공유 동의도 함께 꺼져요.
     - 다시 켜도, 기관이 이미 받았다가 가려진 리포트는 다시 보이지 않아요.
   - 시트는 화면 높이의 90%까지이고 안내만 안에서 스크롤합니다. [취소] · [권한 끄기]는 하단에 고정이라 작은 화면 ·
     글자 확대에서도 닿습니다
   - 켜기는 P-02(`/parent/consent?childId=&institutionId=&from=settings`)로 이동 — 무엇이 공유되는지 보고
     동의하면 이 화면으로 돌아옵니다
   - 기관 코드로 연결을 요청해 기관의 수락을 기다리는 기관(`child.linkRequests`)은 목록 아래에 점선 행으로
     "수락 대기 중 · 기관이 수락하면 알림으로 알려 드려요". 토글이 없습니다 — 명부에 오르기 전이라 동의할 수 없습니다
   - **지금은 연결되지 않은 기관** — 공유 내역(G-45)에는 있는데 기관 권한 목록(명부)에 없는 기관. 토글 없이 "받은 리포트 N편 ·
     가려짐 K ›" 만 → P-05. 명부에서 빠진 기관의 가려진 내역으로 들어가는 길입니다
4. "+ 기관 직접 추가" → P-13
5. **아이 정보** — 알레르기와 복용약(N개) → P-06,
   준비물·확인사항(N건 남음 / 완료) → P-12. N 은 확인 안 한 요청 전체 수(G-50 `status=needs_check`)
6. **계정** — "약관 보기" → [약관](#약관--termskey)(`/terms/tos`) · "로그아웃" · "회원 탈퇴" →
   [탈퇴 확인 시트](#탈퇴-확인-시트-공통)(보호자 문구). 계정 아래 안내에 "탈퇴하면 아이와의 연결이 모두 끊겨요."를 더합니다

목록 아래 안내: "권한을 끄면 그 기관은 받은 주간 리포트를 더 볼 수 없고, 그 기관 기록이 들어간 리포트도 다른 기관에서
가려져요. 기관이 이미 쓴 기록은 기관에 남아요."

**규칙** · 권한 끄기 화면에는 **무엇이 남고**(기관이 이미 쓴 기록, 보호자 열람) **무엇이 거둬지는지**(그 기관이 받은 리포트, 그 기관 기록이 들어간 리포트) 반드시 적습니다. 지금 동작보다 강하게 약속하지 않습니다 — "이미 보낸 정보는 회수되지 않는다"는 사실과 반대라 쓰지 않습니다. 헤더에서 아이를 바꾸면 화면 상태(기관 목록 · 확인 대화 · 오류 문구)를 새로 시작합니다 — 이전 아이의
기관이 남은 채 동의 끄기가 새 아이로 가지 않게 합니다(#289). 같은 아이에서 다시 불러오면 기관 목록을 서버 값으로 맞춥니다 —
명부에서 빠진 기관이 토글과 함께 남아 "지금은 연결되지 않은 기관" 과 겹치지 않게 합니다(#317).

## P-12 준비물·확인사항 · `/parent/checklists`

**기능**

1. 요청 카드 — 기관 이름 · 보낸 날짜 · 항목 줄
2. 상태 배지 — `확인 필요`(강조 테두리) / `확인 완료`. 순서는 서버 그대로(확인 필요 전부 → 확인 완료 최근 20개)

   보호자 중 한 명이 확인하면 모두에게 확인 완료이고 되돌리지 않음
4. 확인 완료 카드 아래 "김보호 · 11.04 19:02 확인" — 이름이 없으면 "다른 보호자"
5. 404 `CHECKLIST_NOT_FOUND` → "이 요청을 더 이상 확인할 수 없어요." + 목록 다시 읽기. 기관이 내렸는지 명부에서 빠졌는지는 단정하지 않음
6. 없으면 "받은 준비물·확인사항이 없습니다."

## P-13 기관 직접 추가 · `/parent/consent/manage/add`

**기능**

1. 기관 코드 입력(`XXXX-XXXX`, 공백·하이픈·대소문자 무시) → 조회(G-43)
2. 찾지 못하면 "일치하는 기관을 찾지 못했어요. 코드를 다시 확인해주세요."
3. 찾으면 기관 정보 + "기관이 수락하면 알림으로 알려 드려요." + "연결 요청을 위해 아이 이름·생년월일과 보호자 이름이
   기관에 전달돼요. **기록과 리포트 공유는 기관 수락 후 동의 화면에서 정해요.**"
4. "나중에" / "연결 요청 보내기"(G-44) → "연결을 요청했어요" 완료 화면("기록과 리포트 공유는 그때 동의 화면에서 정하면
   돼요") → "설정으로 돌아가기"
5. 설정(P-04)의 기관 권한 목록 아래에 그 기관이 "수락 대기 중"으로 보입니다(아이 응답의 `linkRequests`)

**규칙**

- 조회 단계에서는 **연결하지 않습니다.**
- 요청은 **바로 연결되지 않습니다.** 기관이 수락(O-61)하면 아이가 그 기관 명부에 오르고, 그때 "새 기관 권한 요청"
  알림(P-11)으로 떠서 동의 화면(P-02)에서 공유에 동의합니다. 그래서 이 화면은 공유를 묻지 않습니다.
- 요청은 수락 전부터 기관의 연결 요청 목록(O-60)에 아이 이름 · 생년월일 · 요청한 보호자 이름으로 보입니다. 그래서
  "수락 전에는 아무 정보도 공유되지 않는다"고 쓰지 않습니다.
- 거절은 알리지 않습니다. "수락 대기 중"에서 사라지고, 다시 요청할 수 있습니다.

**오류**

| 응답 | 화면 |
| --- | --- |
| 404 `INSTITUTION_CODE_NOT_FOUND` | "일치하는 기관을 찾지 못했어요. 코드를 다시 확인해주세요." |
| 409 `INSTITUTION_ALREADY_LINKED` | "이미 연결된 기관이에요. 설정의 기관 권한에서 확인해 주세요." |

## P-05 기관 공유 내역 · `/parent/settings/shares/:institutionId`

> 예전 "활동 이력"(`/parent/history`, 10/30 삭제)의 뜻 — **언제, 어느 기관에, 무엇이 전달되었는지** — 을 기관 단위로 되살렸습니다(#317).

**기능**

1. 그 기관에 열린 이 아이 **주간 리포트** 목록, 열린 날짜 최신순. 아이는 헤더에서 고른 아이(설정과 같은 기준), 헤더는 뒤로가기
2. 한 줄: "2026년 10월 4주차 리포트" · "○○에서 정리 · 10월 29일 열림" · 상태 "지금 볼 수 있음" / "가려짐 · 11월 2일" /
   "가려짐"(거둔 기록 없이 명부 · 동의로 가려진 경우). 누르면 리포트 상세(P-14)
3. 공유 내역에 그 기관이 없으면 "받은 리포트가 없어요"

**규칙**

- **가려진 공유도 보입니다.** 리포트 상세의 "함께 보는 기관"은 같은 기준으로 지금 볼 수 있는 기관만 보이는 점이 다릅니다.
- "지금 볼 수 있음" 은 기관 수신함과 같은 판정이라 보호자 화면과 기관 수신함이 어긋나지 않습니다.
- 가려진 이유와 기관이 열어 봤는지는 보이지 않습니다.
- 지금 명부에서 빠진 기관도 받은 이력이 있으면 들어올 수 있습니다(설정의 "지금은 연결되지 않은 기관").
- 일지 · 요약은 기관 밖으로 나가지 않아 여기 없습니다.

**호출 API** · `getInstitutionShares`(G-45)

## 학부모 공통 셸

- **하단 탭 4개** — 홈 · 타임라인 · 리포트 · 설정
  (일지 상세는 타임라인 탭, 리포트 상세는 리포트 탭으로 활성 표시)
- **리포트 탭 점** — 헤더에서 고른 아이에게 아직 열어 보지 않은 리포트가 있을 때. "특이사항 없음" 주(quiet)는 열어 볼
  상세가 없어 세지 않습니다(#470). 보호자 입구(`parent/guard.tsx`)가
  세고, 홈·리포트로 들어갈 때와 리포트 상세에서 나올 때 다시 셉니다. 다른 탭으로 옮길 때는 다시 세지 않습니다
- **헤더**(`ParentPageHeader`) — 뒤로가기 또는 아이 전환 아바타, 제목/부제, 알림 벨
- **아이 전환** — 아바타 클릭 시 드롭다운. 아이가 1명뿐이면 화살표가 보이지 않아
  한 자녀 사용자에게는 기존과 동일하게 보입니다. 드롭다운 하단에 "+ 아이 추가"
- **아이 전환 점** (#300, #329) — 아이가 둘 이상이고 **고르지 않은 다른 아이**에게 아직 열어 보지 않은 리포트나
  **대기 중 기관 권한 요청**이 있으면 아바타에 점. 펼친 목록에서는 둘 중 하나라도 있는 아이 줄마다(고른 아이 포함) 점.
  점은 하나이고 이유는 화면 읽기 문구가 나눕니다 — 그 아이로 바꾸면 리포트 탭 점과 알림 벨 점이 이유를 보여 줍니다.
  고른 아이 소식은 그 두 점이 알립니다
  - 리포트는 리포트 탭 점과 같은 값(보호자 입구가 센다)이고, 권한 요청은 입구가 읽는 아이 목록(G-10)에서 동의 상태가
    `not_granted` 인 기관이 있는지로 셉니다 — 대기 중 요청(G-40)과 같은 기준이라 요청이 늘지 않습니다. 다시 세는 때는
    같습니다(홈·리포트로 들어갈 때, 리포트 상세에서 나올 때, 아이를 바꿀 때). 동의는 입구 밖의 동의 화면(P-02)을 거쳐
    돌아오면 입구가 아이 목록을 다시 읽어 바로 꺼집니다
  - 동의했다가 끈 기관(`revoked`)과 수락을 기다리는 기관 연결 요청(`linkRequests`)은 알리지 않습니다(G-40 과 같다).
    일지도 알리지 않습니다 — 보호자가 읽었는지 남기는 값이 없습니다
  - 화면 읽기에서는 버튼 이름 "아이 전환, 다른 아이에게 확인할 것 있음", 목록 줄은 이유별로 "안 본 리포트 있음" ·
    "권한 요청 있음"(둘 다면 둘 다)으로 읽힙니다
- **알림 점** — `getPendingInstitutionRequests(childId)` 결과가 1건 이상이거나, 확인 안 한 준비물·확인사항
  (`getChecklists(childId, { needsCheckOnly: true })`)이 1건 이상일 때. 홈 · 설정 · 타임라인 · 리포트가 각각 부릅니다

## 탈퇴 확인 시트 (공통)

가입 화면(I-01c) · 보호자 진입(P-01 `terms` · `code`) · 설정(P-04)의 "회원 탈퇴"가 띄웁니다(`components/WithdrawAccount`).
기관 계정에는 두지 않습니다 — 서버가 `403 ORGANIZATION_WITHDRAWAL_NOT_SUPPORTED` 로 막습니다. 기관은 계정 메뉴의
[담당자 넘기기](#기관-공통-셸-머리띠-메뉴)로만 탈퇴합니다.
**서버가 탈퇴를 열지 않았으면(`/auth/me` 의 `withdrawalEnabled: false`) 버튼을 그리지 않습니다.**

**다른 탭에서 다른 계정으로 로그인하면 이 탭을 새로 고칩니다(앱 전체).** 같은 브라우저의 탭들은 출입증 쿠키를 함께 써서, 그대로 두면
예전 계정의 화면으로 새 계정의 요청을 보내게 됩니다. 로그인 착지(`/oauth/success`)가 브라우저 저장소의 로그인 표시(로그인한 계정의
`userId` 포함)를 바꾸고, 다른 탭은 그 변경(또는 다시 보일 때 표시가 바뀐 것)을 보고 새로 고칩니다(`reloadOnLoginElsewhere`). **표시의
계정이 그 탭이 처음 확인한 계정과 같으면 새로 고치지 않습니다** — 같은 사람이 다시 로그인한 것이고, 기관 담당자가 쓰던 요약 검토 ·
검증 수정 본문은 화면 상태에만 있어 새로 고치면 사라집니다. 그 탭이 비로그인이었거나 계정을 아직 몰랐으면 새로 고칩니다. 표시는 **실제 로그인으로 들어왔을 때만** 바꿉니다 —
이 탭에서 카카오 로그인을 시작했고(카카오로 떠나기 전 sessionStorage 에 남긴 표시, 30분 안) 백엔드가 `/oauth/success` 를 새로
불러왔을 때입니다. 이미 로그인한 사람이 `/oauth/success` 주소를 직접 열거나, 앱 안에서 `/oauth/success` 로 옮겨 가는 것(탈퇴 안내의
[돌아가기])은 다른 탭을 새로 고치지 않습니다.

**설정(P-04)의 탈퇴 대상은 화면의 아이 목록을 가져온 계정입니다.** 아이 목록 응답 헤더 `X-Itda-User-Id` 에서 꺼냅니다 — `/auth/me` 를
따로 물으면 다른 탭에서 계정이 바뀐 직후 목록은 A, 계정은 B 가 될 수 있습니다. 아이 목록만 모의 데이터이고 로그인은 실제이면
목록에 실제 계정이 없어 탈퇴 버튼을 그리지 않습니다.

**버튼이 처음 그려질 때의 계정만 지웁니다.** 그 계정의 `userId` 를 고정해 요청에 싣습니다. 그 뒤 화면 데이터가 다시 읽혀 다른 계정
(다른 탭에서 로그인한 사람)으로 바뀌어도 대상은 바뀌지 않고, 바뀐 것을 알아채면 [탈퇴하기]를 막고 "다른 계정으로 로그인이
바뀌었어요. 화면을 새로 고친 뒤 다시 확인해 주세요." 를 띄웁니다. 확인 창을 열 때도 `/auth/me` 로 지금 계정을 다시 물어 봅니다. 서버도 지금 로그인한 계정과 다르면 `409 WITHDRAWAL_ACCOUNT_MISMATCH` 로 막습니다.

"정말 탈퇴할까요?" 아래 목록 (보호자 문구 · 가입 전에는 앞의 두 줄과 마지막 줄의 뒷문장이 빠집니다)

- **연결된 아이와의 연결이 모두 끊겨요.**
- 내 공유 동의는 철회돼요. 같은 기관에 다른 보호자의 동의가 남아 있으면 그 기관 공유는 계속돼요.
- 카카오 연결이 끊기고, 카카오 회원번호가 지워져요.
- 같은 카카오 계정으로 다시 들어와도 새로 가입하는 거예요. 아이를 다시 연결하려면 기관에서 초대 코드를 새로 받아야 해요.

[취소] · [탈퇴하기] → `DELETE /api/v1/auth/me` (api-spec §2.7)

시트는 네이티브 모달(`<dialog>` 의 `showModal()`, 약관 본문 창과 같은 방식)이라 떠 있는 동안 뒤 화면을 누르거나 Tab 으로 닿을 수
없습니다. 처음 포커스는 [취소]에 두고(엔터 한 번에 탈퇴가 나가지 않게), Tab 은 시트 안에서 돕니다. Esc · 배경 · [취소]로 닫으면
"회원 탈퇴" 버튼으로 포커스를 돌려줍니다. 탈퇴를 보내는 중에는 닫히지 않습니다.

| 응답 | 화면 |
| --- | --- |
| `204` | `/withdrawal` + 이동 상태 `completed` (서버는 쿠키를 지우지 않음 — 탈퇴한 계정의 출입증은 늘 401). 주소에 싣지 않아 직접 열어서는 완료 화면이 보이지 않습니다 |
| `202` · `409 WITHDRAWAL_IN_PROGRESS` | `/withdrawal` |
| `502 KAKAO_UNLINK_FAILED` | 시트에 "카카오 연결을 끊지 못해 탈퇴하지 못했어요. 잠시 뒤 다시 해 주세요." 계정은 그대로 |
| `403 ORGANIZATION_WITHDRAWAL_NOT_SUPPORTED` | 시트에 "기관 계정은 아직 탈퇴할 수 없어요." |
| `401` | 시트에 "로그인이 풀렸어요. 다시 로그인한 뒤 해 주세요." |

## 탈퇴 안내 · `/withdrawal`

| 항목 | 내용 |
| --- | --- |
| 사용자 | 탈퇴를 신청한 사람 (보호자 · 가입 전), 후임에게 기관을 넘긴 이전 기관 담당자(#478) |
| 진입 | 탈퇴 확인 시트, 그리고 탈퇴를 처리하는 중인 회원을 로그인 착지 · 가입 · 보호자 진입 · 보호자 입구 · 보호자 세션 확인 · 기관 화면 가드가 보냄 |
| 인증 | 없음 — 역할 묶음 밖. 결과는 `/auth/me` 로 봅니다 |

탈퇴 확인 시트가 실제 `204` 를 받고 넘긴 이동 상태(`completed`)가 있으면 바로 "탈퇴가 끝났어요". 아니면(직접 열었거나 처리 중)
`/auth/me` 를 3초마다 다시 읽어 나눕니다.

| `/auth/me` | 화면 |
| --- | --- |
| `401 ACCOUNT_WITHDRAWN` | 이 브라우저의 표시만 지우고 "탈퇴가 끝났어요" + [처음 화면으로]. 로그아웃 API 는 부르지 않습니다 — 그 사이 다른 탭에서 로그인한 사람의 쿠키가 실려 가 그 로그인을 끊을 수 있습니다. 탈퇴한 계정의 출입증은 서버가 늘 401 로 막습니다 |
| 그 밖의 `401` (만료 · 쿠키 없음 · 로그아웃) | "로그인이 풀렸어요" — **완료로 보이지 않습니다.** 다시 로그인하면 진행을 볼 수 있고, 가입 화면이 나오면 끝난 것이라고 안내 + [다시 로그인] |
| `withdrawal: "in_progress"` | "탈퇴를 처리하고 있어요" — 카카오 연결을 끊고 계정 정보를 정리한다(보호자는 아이 연결과 공유 동의도 함께). 화면을 닫아도 서버가 이어서 처리 |
| 지금 계정이 탈퇴를 요청한 계정(확인 시트가 넘긴 `userId`)과 다름 | "다른 계정으로 로그인돼 있어요" — 그 사이 다른 탭에서 로그인했다. 그 계정의 상태를 결과로 읽지 않습니다 |
| `withdrawal: "none"` — 탈퇴 확인 시트에서 왔을 때 | "탈퇴하지 못했어요" (첫 카카오 호출이 실패해 서버가 접수를 취소함) + [돌아가기] → `/oauth/success` |
| `withdrawal: "none"` — 주소로 직접 들어왔을 때 | "진행 중인 탈퇴가 없어요. 계정은 그대로예요." + [돌아가기] — 신청한 적 없는 사람에게 실패라고 보이지 않습니다 |

## 공통 UI 규칙

화면을 고칠 때 아래를 깨지 않는지 확인합니다. 제품 원칙에서 직접 나온 것입니다.

1. Gate 2 승인 · 보류는 되돌릴 수 없으므로 확인 창을 거칩니다. 받을 기관은 아무도 고르지 않고 보호자의 기관별 공유 동의로 정해집니다.
2. 낮은 확신도 기록에 자동 확정 버튼을 두지 않습니다.
3. 상담 도우미 답변에는 항상 근거 출처를 붙이고, 없으면 "확인된 기록에는 없어요".
4. 아동 타임라인에서 기록이 없는 날은 비워 표시합니다.
5. 수신함에는 원본이 아니라 변환된 최소 정보만 표시합니다.
6. 학부모 화면에 자유질의 챗봇을 넣지 않습니다.
7. 미동의 기관은 선택 불가 + 사유 표시입니다.
8. 권한 끄기 화면에는 **무엇이 남고**(기관이 이미 쓴 기록, 보호자 열람) **무엇이 거둬지는지**(그 기관이 받은 리포트, 그 기관 기록이 들어간 리포트) 반드시 적습니다. 지금 동작보다 강하게 약속하지 않습니다 — "이미 보낸 정보는 회수되지 않는다"는 사실과 반대라 쓰지 않습니다.
9. 상태는 색 단독으로 전달하지 않습니다. 텍스트 라벨을 항상 함께 씁니다.
10. 기관 화면 본문은 16px 이상, 클릭 타깃은 44px 이상(`tap` 유틸).
11. 아이별 데이터는 반드시 `childId`로 조회합니다.
