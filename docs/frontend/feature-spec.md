## 1. 서비스 개요

장애아동 등 여러 기관의 돌봄을 동시에 받는 아이의 기록은 학교 · 센터 · 활동지원사 ·
치료실에 흩어져 있습니다. 보호자는 같은 설명을 기관마다 반복하고, 기관은 다른 곳에서
어떤 지원이 효과적이었는지 모릅니다.

잇다는 기관이 올린 원본 기록을 **아이별로 모아 요약**하고, **사람이 두 번 승인**한
것만, **보호자가 허락한 기관에만** 전달합니다.

### 설계 원칙

| 원칙 | 의미 |
| --- | --- |
| 사람이 두 번 승인한다 | AI는 요약과 후보 제시만. 확정과 발송은 사람이 한다 |
| 보호자가 통제한다 | 기관별 · 항목별 동의. 언제든 회수 가능 |
| 근거 없는 말을 만들지 않는다 | 모든 요약·답변에 근거 출처. 없으면 답하지 않는다 |
| 원본은 고치지 않는다 | 수정은 append-only. 원본 삭제·변경 없음 |
| 되돌릴 수 없는 지점을 분명히 한다 | 발송 직전 경고, 기본값은 아무것도 선택하지 않은 상태 |

## 2. 사용자 역할

| 역할 | 코드값 | 사용 화면 | 진입 |
| --- | --- | --- | --- |
| 기관 담당자 | `org` | 기관 대시보드 (데스크톱 1440) | `/login` — 카카오 로그인 |
| 보호자 | `parent` | 학부모 웹앱 (모바일 375) | 카카오 로그인 → 기관 연결 |

인증은 **카카오 로그인**으로 통일합니다. 기획서 12절의 SMS OTP와 초대코드 방식은
쓰지 않습니다.

역할 판정은 각 레이아웃 라우트의 `clientLoader`에서 이뤄지고, 판정 전에는 로딩 화면만
보입니다. 다른 역할의 화면이 순간 노출되는 경우는 없습니다.

## 3. 핵심 흐름

### 3.1 기록 파이프라인

```
기록 등록 → 매칭 → 검증 → 요약 → [1차 검토] → Child Context 적재
                                       ↑ 사람 승인 (Gate 1)

Child Context 누적 → Insight 도출 → [공유 전 검토] → 수신 기관별 변환 → 수신함
                                          ↑ 사람 승인 (Gate 2) · 되돌릴 수 없음
```

- **기록 등록 → 1차 검토 대기**까지는 사람 개입 없이 자동 진행됩니다.
- **Gate 1**(1차 검토) — 기록을 등록한 선생님이 요약의 **사실 정확성**을 승인합니다.
- **Gate 2**(공유 전 검토) — **근거를 최다 제공한 기관**의 선생님이 **발송 적절성**을
  판단합니다. 되돌릴 수 없는 지점입니다.

### 3.2 매칭 결과 분기

| 결과 | 처리 |
| --- | --- |
| `confirmed` | 자동 진행 (큐에 나타나지 않음) |
| `multi` | 확인 필요 큐 — 후보 중 사람이 선택 |
| `low` | 확인 필요 큐 — 사람이 확인 |
| `unmatched` | 확인 필요 큐 — 이름으로 직접 검색 |

### 3.3 검증 결과 분기

| 판정 | 처리 |
| --- | --- |
| `PASS` | 요약 생성 후 Gate 1로 |
| `REVIEW` | 요약 생성하되 사유가 된 문장을 표시하고 Gate 1에서 확인 |
| `BLOCK` | 파이프라인 정지. 수정 요청 큐로 (원본 수정 후 재등록) |

### 3.4 보호자 온보딩

```
기관: 아이 등록 (status: pending_consent) → 보호자 연결 요청 생성
         ↓
보호자: 카카오 로그인 → 서비스 약관 동의
         ↓
       대기 중인 연결 요청 확인
         ↓
       아이 정보 확인 → 기관 확인 → 공유 범위 동의
         ↓
       아이 상세정보(알레르기·복용약) 입력 → 홈
```

최초 연결은 **연결 요청(pending link) 방식 하나**로 갑니다. 기관이 아이를 등록하면
연결 요청이 생성되고, 보호자가 카카오 로그인하면 그 요청이 화면에 뜹니다.

보호자가 **나중에 다른 기관을 추가로 연결**할 때는 기관 코드 입력(P-13)을 씁니다.
최초 온보딩 경로가 아니라 설정 화면에서만 쓰입니다.

> 남은 확정 사항은 **매칭 키**입니다 — 기관이 등록한 아이와 카카오 로그인한 보호자를
> 서버가 무엇으로 이어줄지(§9). 기관이 보호자 전화번호 전체를 입력하지 않기로 했기
> 때문에(§7-12), 뒤 4자리 + 아이 이름·생년월일로 후보를 좁힌 뒤 보호자가 화면에서
> 최종 확인하는 방식을 제안합니다.

보호자 동의가 완료되기 전까지 아이는 `pending_consent` 상태이고, **기관은 그 아이의
기록을 올릴 수 없습니다.** 파이프라인이 한 줄도 돌지 않습니다.

## 5. 상태 전이

### 5.1 아이 (`ChildStatus`)

```
[기관이 등록]
      ↓
pending_consent ──(보호자 동의 완료)──> active ──(동의 전면 회수)──> suspended
                                          ↑                              │
                                          └────────(재동의)──────────────┘
```

`pending_consent` 상태에서는 기록 업로드가 차단됩니다.

### 5.2 기관별 동의 (`ConsentState`)

```
not_granted ──(동의)──> granted ──(권한 끄기)──> revoked
     ↑                                              │
     └──────────(기관이 다시 요청)───────────────────┘
```

- `revoked`는 **앞으로의** 전달만 막습니다. 이미 보낸 정보는 회수되지 않습니다.
  이 사실은 회수 화면에 반드시 문구로 표시합니다.
- 알림에서 "거절"은 `not_granted`를 유지하고 알림 목록에서만 제외합니다
  (기관이 다시 요청할 수 있어야 하므로).

### 5.3 검증 (`ValidationStatus`)

```
PASS   → 요약 생성 → Gate 1
REVIEW → 요약 생성(사유 문장 표시) → Gate 1
BLOCK  → 정지 → 수정 요청 큐 → (원본 수정 후 새 기록으로 재등록)
```

### 5.4 Gate 1 (`Gate1Status`)

```
pending ──(승인 / 수정 후 승인)──> approved → Child Context 적재
        └─(반려 + 사유)─────────> rejected → 원본으로부터 요약 재생성 → pending
```

### 5.5 Gate 2 (`Gate2Status`)

```
pending ──(발송 승인 · 수신 기관 1곳 이상)──> approved → sent  ※ 되돌릴 수 없음
        └─(보류)────────────────────────────> held
```

## 6. 권한 · 접근 제어

| 대상 | 규칙 |
| --- | --- |
| 기관 화면 전체 | `role === "org"` |
| 학부모 화면 (`/parent/**`) | `role === "parent"` + 연결된 아이 1명 이상 |
| `/parent/invite`, `/parent/consent` | 공개 (카카오 로그인 · 최초 기관 연결 진입) |
| 아동 데이터 | 해당 아이에 연결되고 `granted` 상태인 기관만 |
| Gate 2 승인 | 해당 Insight의 `primarySource` 기관만 |
| 보호자 데이터 조회 | 반드시 `childId` 스코프. 전역 조회 금지 |

> 현재 역할 판정은 클라이언트(localStorage)에서만 이뤄집니다. **서버 측 인가는 필수로
> 별도 구현되어야 합니다.** 클라이언트 가드는 UX 목적이며 보안 경계가 아닙니다.

## 7. 제품 불변 규칙

기획 · 디자인 · 구현이 함께 지켜야 하는 규칙입니다. 화면을 바꿀 때 이 중 하나라도
깨지면 제품 원칙을 어긴 것입니다.

1. **Gate 2 수신 기관 체크박스 기본값은 전체 해제.** 0곳이면 발송 버튼 비활성.
2. 낮은 확신도 기록에 **자동 확정 버튼을 두지 않습니다.** 사람이 아이를 선택합니다.
3. 상담 도우미 답변에는 **항상 근거 출처**를 붙이고, 없으면 "확인된 기록에는 없어요".
4. 아동 타임라인에서 **기록이 없는 날은 비워 표시**합니다. 추정치로 채우지 않습니다.
5. 수신함에는 원본이 아니라 **변환된 최소 정보**만 표시합니다.
6. 학부모 화면에 **자유질의 챗봇을 넣지 않습니다.**
7. 미동의 기관은 **선택 불가 + 사유 표시**입니다. 선택 후 거부 방식은 쓰지 않습니다.
8. 동의 회수 화면에는 **"이미 보낸 정보는 회수되지 않는다"** 문구가 반드시 있어야 합니다.
9. 상태를 **색 단독으로 전달하지 않습니다.** 텍스트 라벨을 항상 함께 씁니다.
10. 기관 화면 본문은 **16px 이상**, 클릭 타깃은 **44px 이상**.
11. **아이별 데이터는 반드시 `childId`로 조회합니다.**
12. 보호자 본인 정보를 기관이 대신 입력하지 않습니다. **보호자가 카카오 로그인으로
    직접 인증**합니다.
13. 원본 기록은 수정·삭제하지 않습니다. **append-only.**

## 8. 비기능 요구사항

| 항목 | 기준 |
| --- | --- |
| 기관 화면 | 데스크톱 1440 기준, 사이드바 고정 |
| 학부모 화면 | 모바일 375 기준. `md`/`lg`에서 카드 폭 430 → 560 → 640px |
| 서체 | 시스템 한글 폰트. 웹폰트 없음 (학부모 첫 화면 용량) |
| 접근성 | 색 단독 전달 금지, 44px 타깃, `aria` 라벨, 포커스 표시 |
| 오프라인 | 연결 끊김 시 "기록은 그대로 있습니다" 안내 + 재시도 (P-09) |
| 빈 상태 | 모든 목록 화면에 전용 빈 상태 문구 |
| 렌더링 | SPA(`ssr: false`). 역할 판정 전에는 로딩 화면만 노출 |

## 9. 미구현 · 확정 필요 목록

프론트 화면은 완성됐지만 실제 동작을 위해 남은 작업입니다.

### 백엔드 · AI 팀 확인 필요

| 항목 | 내용 |
| --- | --- |
| 카카오 로그인 | 인가 코드 교환 위치, 리다이렉트 URI, 동의 항목(닉네임·전화번호 등) 범위 |
| 역할 구분 | 카카오 계정 하나로 기관 담당자와 보호자를 어떻게 구분할지 |
| 세션 전달 | httpOnly 쿠키 vs Authorization 헤더 |
| 보호자–아이 연결 매칭 키 | 기관이 등록한 아이와 카카오 로그인한 보호자를 무엇으로 이어줄지 (전화번호 뒤 4자리 대조 + 보호자 최종 확인 제안) |
| 파일 업로드 | multipart 스펙, 용량 제한, 허용 확장자 |
| 파이프라인 상태 | 폴링 vs SSE/WebSocket |
| 필드 네이밍 | camelCase / snake_case 통일 |
| 페이지네이션 | 목록 API 정책 (현재 프론트는 전체 조회 가정) |
| 리포트 생성 | 주간/월간 집계 주체와 주기 |
| 상담 지원 | AI 응답 + 근거 출처 반환 형식 |

상세는 [api-spec.md](../api/api-spec.md)에 정리했습니다.
