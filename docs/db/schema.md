# DB 스키마

테이블이 무엇을 담고, 어떤 규칙으로 쓰는지 설명합니다. 노션 「DB 수정본」은 이 문서의 사본입니다.

- **스키마의 원본은 Flyway 마이그레이션입니다** — `backend/src/main/resources/db/migration`. 컬럼 타입 · 길이 · NULL · 제약의 정확한 값은 거기 있습니다
- 이 문서는 테이블의 뜻, 꼭 지킬 규칙, 이름만 봐서는 모르는 컬럼만 적습니다
- 상태가 어떻게 바뀌는지 같은 동작은 [도메인 문서](../README.md#도메인)에 있습니다

---

## 1. 한눈에

PostgreSQL 16, 테이블 28개입니다.

| 묶음 | 테이블 |
| --- | --- |
| 계정 | `users` · `organization` · `terms_agreement` · `revoked_session` · `kakao_unlink_webhook` · `organization_handover` |
| 아이 · 연결 · 동의 | `child` · `child_organization`(명부) · `invitation` · `child_guardian` · `child_organization_request` · `sharing_consent` · `child_care_info` |
| 기록 | `raw_record_upload` · `raw_record` · `journal_entry` · `matching_result` · `validation_result` |
| 요약 · 검토 · 공유 | `summary_result` · `summary_run_request` · `human_review` · `child_context` · `insight_run` · `insight_result` · `sharing_history` · `insight_notification` |
| 준비물 | `checklist` · `checklist_target` |

```
organization ─< child_organization >─ child ─< child_guardian >─ users(보호자)
                                        │
raw_record ─< journal_entry ─< matching_result · validation_result
                    │
                    └─> summary_result ─ child_context ─> insight_result ─< sharing_history
```

선은 논리적 관계입니다. DB에 외래 키는 없습니다 (§2.1).

---

## 2. 공통 규칙

### 2.1 외래 키를 걸지 않고, 지우지 않는다

- 테이블에는 `child_id` 같은 **ID 값만** 저장합니다. DB 외래 키 제약을 만들지 않고, JPA 연관관계(`@ManyToOne` 등)도 쓰지 않습니다. 참조가 맞는지는 서비스가 확인합니다
- 그래서 **DB는 어떤 삭제도 막아 주지 않습니다.** 아이 행을 지우면 일지 · 동의가 없는 ID를 가리킨 채 남습니다
- 그 짝으로 **행을 지우지 않습니다.** 사용자가 화면에서 지우는 것은 `deleted_at`에 시각을 적는 것으로 처리합니다. 조회는 `deleted_at IS NULL`인 행만 봅니다
- `deleted_at`이 있는 테이블: `users` · `child` · `child_organization` · `child_guardian` · `raw_record` · `journal_entry`

**예외 — 1차 검토에서 제거한 기록은 30일 뒤 실제로 지웁니다.** 되돌릴 수 없고 다시 읽는 곳도 없어 아이 기록만 쌓이기 때문입니다.
매일 새벽 4시 `RemovedRecordPurgeWorker`가 제거한 지 30일이 지난 일지와 그 매칭 · 검증 결과 · 요약 · 원본 파일을 지웁니다.

### 2.2 AI 입력은 저장하지 않는다

AI에 보내는 입력은 기존 테이블에서 그때그때 조립합니다. 복사해 두면 원본이 고쳐졌을 때 어긋나기 때문입니다.
대신 어떤 입력을 썼는지는 결과 테이블에 ID로 남깁니다 (`validation_result.matching_result_id` 등). AI 응답 원본은 결과 테이블의 `raw_response`에 둡니다.

### 2.3 타입

- **ID** — `bigint`, `GENERATED BY DEFAULT AS IDENTITY`
- **시각** — `timestamp without time zone`, 서울 시각(`TZ=Asia/Seoul`). `created_at`은 모든 테이블, `updated_at`은 값이 바뀌는 테이블에만 있습니다
- **enum** — `varchar` + 허용 값 검사 제약(`<테이블>_<컬럼>_check`). 엔티티에는 반드시 `@Enumerated(EnumType.STRING)`을 붙입니다. 빠뜨리면 순서 번호로 저장돼, enum 순서만 바뀌어도 과거 데이터의 뜻이 바뀝니다
- **목록 · 객체** — JSON 문자열을 `text`에 담습니다 (`claims`, `candidates`, `scope` 등). DB는 내용을 검사하지 않습니다

## 3. 테이블

### 3.1 계정 → [계정 도메인](../domains/account.md)

#### `users`

회원 한 명. 기관 담당자와 보호자가 같은 테이블입니다.

- `kakao_id` — 카카오 회원번호, UNIQUE. 개발용 로그인 회원은 `dev:{이름}`, 탈퇴를 마치면 `withdrawn:{id}`로 바꿔 같은 카카오 계정이 새로 가입할 수 있게 합니다
- `role` — `ORGANIZATION` · `PARENT`. **NULL이면 가입 미완료**입니다
- `organization_id` — 기관 담당자의 소속 기관
- `withdrawal_status` · `withdrawal_requested_at` · `kakao_unlink_*` · `webhook_withdrawal_reported_at` — 진행 중인 탈퇴와 카카오 연결 해제 재시도 기록. 탈퇴를 마치면 `deleted_at`을 채웁니다

#### `organization`

기관 하나. 기관 하나에 담당자 계정 하나입니다.

- `type` — `SCHOOL` · `CENTER` · `ACTIVITY_SUPPORT`
- `business_number` — 사업자등록번호, UNIQUE (형식만 검사)
- `code` — 보호자에게 알려 주는 기관 코드(8자리), UNIQUE. 기관 정보를 처음 열 때 만듭니다

#### `terms_agreement` · `revoked_session` · `kakao_unlink_webhook` · `organization_handover`

- `terms_agreement` — 회원이 어떤 약관의 어느 판에 동의했는지. (`user_id`, `term_key`, `version`) UNIQUE. 약관 본문은 `backend/src/main/resources/terms`
- `revoked_session` — 로그아웃한 로그인 번호. `session_id` UNIQUE. 이 로그인의 출입증은 늘어난 것까지 막습니다
- `kakao_unlink_webhook` — 카카오 연결 해제 웹훅 수신함. 카카오의 3초 응답 기한을 지키려고 받자마자 한 줄 남기고, 회원 처리는 따로 합니다
- `organization_handover` — 담당자 넘기기 인계 코드(8자, 12시간). `code` UNIQUE

### 3.2 아이 · 연결 · 동의 → [아이 · 보호자](../domains/child-guardian.md) · [동의](../domains/consent.md)

#### `child`

아이 한 명. 기관마다 따로 만들지 않고, 여러 기관 명부가 같은 행을 가리킵니다.

- `status` — `PENDING_CONSENT` · `ACTIVE` · `SUSPENDED`. 동의로 정해집니다 ([동의](../domains/consent.md#동의가-바꾸는-것))

#### `child_organization` — 명부

어느 아이가 어느 기관 명부에 있는지.

- (`child_id`, `organization_id`) UNIQUE · (`organization_id`, `external_id`) UNIQUE
- `external_id` — 기관 관리번호. 명부에서 빼면 비워서 다시 쓸 수 있게 합니다
- **매칭 후보는 명부에 있으면서 그 기관에 살아 있는 동의가 있는 아이**입니다 (`ChildRepository.findConsentedByOrganizationId`)

#### `invitation` · `child_guardian` · `child_organization_request`

- `invitation` — 보호자 초대 코드. `code` UNIQUE, 10분(`expires_at`) · 일회용. 만료는 상태가 아니라 시각으로 판단합니다
- `child_guardian` — 아이와 보호자 연결. (`child_id`, `user_id`) UNIQUE. 기관과 상관없는 전역 연결이고, `invitation_id`로 어느 기관 코드로 연결됐는지 남깁니다
- `child_organization_request` — 보호자가 기관 코드로 보낸 연결 요청. `requested_by`가 행의 주인이고, 보호자마다 따로 남습니다

#### `sharing_consent` — 동의

보호자 × 아이 × 기관마다 한 줄입니다.

- `scope` — 허용 항목 JSON 배열 (`["daily_summary","weekly_insight"]`). 같은 기관의 살아 있는 동의는 모두 같은 항목으로 맞춥니다
- `status` — `ACTIVE` · `REVOKED`. 철회하면 `revoked_by` · `revoked_at` · `revoke_reason`(`GUARDIAN_REVOKED` · `GUARDIAN_UNLINKED` · `ROSTER_REMOVED`)을 채웁니다. 행을 지우지 않아 철회 이력이 남습니다
- 같은 보호자가 다시 동의하면 `scope`를 제자리에서 고칩니다. 그래서 "언제 어떤 항목으로 바꿨는지"는 남지 않습니다

#### `child_care_info`

보호자가 적는 알레르기 · 복용약. `child_id` UNIQUE, 두 목록은 JSON 문자열, 통째로 덮어씁니다. **기관에 공유하지 않습니다.**

### 3.3 기록 → [기록 도메인](../domains/records.md)

#### `raw_record_upload` · `raw_record`

- `raw_record_upload` — 브라우저가 S3에 바로 올리는 업로드의 접수. 완료하면 `raw_record`를 만들고 `raw_record_id`를 채웁니다. 하루가 지나도 완료하지 않은 접수는 파일과 함께 정리합니다
- `raw_record` — 올린 파일 하나. `stored_path`는 저장소 안 이름(로컬 디스크 또는 S3 키)
  - ⚠️ `institution_id`는 기관 ID를 **문자열**로 저장합니다. 예전에 다른 값을 담던 컬럼이라 타입이 남았습니다. `summary_result.institution_id`(숫자)와 비교할 때 변환이 필요합니다
  - `hint_name` · `hint_birthdate` — 파일명에서 찾은 아이. 매칭의 힌트입니다
  - `status` — 값은 `PENDING` 하나뿐입니다. 처리 진행은 `journal_entry.status`가 맡습니다

#### `journal_entry` — 일지

원본 파일에서 나눈 기록 한 건. 매칭부터 1차 검토까지 이 행의 `status`로 진행합니다 ([일지 상태](../domains/records.md#일지-상태)).

- `content` 최대 5,000자 · `entry_date` 관찰 날짜 · `sequence_no` 파일 안 순서
- `child_id` — 매칭으로 정해진 아이. 정해지기 전에는 NULL
- `summary_id` — 들어간 요약. 요약에 반영되지 않은 일지도 채웁니다
- `agent_retry_count` — AI가 멈춰 지금 단계를 되돌린 횟수. 상한을 넘으면 실패로 넘깁니다
- `revised_by` · `revised_at` — 검증에서 막힌 본문을 마지막으로 고친 선생님과 시각
- `failure_stage` · `failure_reason` — `SYSTEM_ERROR`일 때만 채웁니다. 단계는 `MATCHING` · `VALIDATION` · `SUMMARY`, 원인은 아래와 같습니다

| `failure_reason` | 뜻 | 고칠 곳 |
| --- | --- | --- |
| `REQUEST_REJECTED` | 백엔드가 계약과 다른 요청을 보냄 | 백엔드 요청 |
| `RESPONSE_UNREADABLE` | AI 응답을 읽을 수 없음 (빈 응답 포함) | AI 응답 |
| `EVIDENCE_MISMATCH` | 백엔드의 근거 재검사에 걸림 | AI 근거 계산 |
| `AGENT_UNAVAILABLE` | AI 장애로 되돌린 횟수가 상한을 넘음 | 없음 — AI가 살아나면 되돌림 |
| `CONTENT_TOO_LONG` | 기록이 너무 길어 AI에 보내지 않음 | 없음 — 줄인 파일을 다시 올림 |
| `INTERNAL_ERROR` | 그 밖의 백엔드 오류 | 백엔드 |

원인을 고친 뒤 되돌리는 방법은 [운영 스크립트](../../backend/scripts/README.md#시스템-오류로-멈춘-일지-되돌리기)에 있습니다. 어느 문장이 문제였는지는 로그에만 남깁니다.

#### `matching_result` · `validation_result`

AI 판정 한 번에 한 줄입니다. 다시 판정하면 새 줄이 쌓이고, 최신 줄을 씁니다.

- `matching_result` — `status`(`AUTO` · `REVIEW` · `MULTI` · `UNMATCHED` · `FAILED`) · `matched_child_id` · `confidence` · `candidates` · `evidence` · `mentioned_child_ids`(본문에 이름이 나온 아이 전부) · `hint_mismatch`
  - `reviewer_id` — 선생님이 확인 큐에서 처리했으면 그 회원 ID. ⚠️ 다른 테이블과 달리 **문자열**입니다. NULL이면 AI가 자동 확정한 것입니다
- `validation_result` — `verdict`(`PASS` · `REVIEW` · `BLOCK` · `FAILED`) · `issue_types` · `evidence`. `matching_result_id`는 입력으로 쓴 매칭 결과입니다

### 3.4 요약 · 검토 · 공유 → [검토](../domains/review.md) · [공유](../domains/sharing.md)

#### `summary_result` — 요약

아이 × 날짜 × 기관 묶음의 요약. (`child_id`, `entry_date`, `institution_id`, `revision`) UNIQUE.

- `revision` — 같은 묶음의 몇 번째 요약인지. 승인 전에 일지가 더 오면 새 판을 만듭니다
- `content` — AI가 쓴 요약 원문. `no_content`(쓸 관찰 사실 없음)면 빈 문자열
- `claims` — 문장별 근거 JSON. **선생님이 문장 카드를 고쳐 승인하면 카드 결과로 다시 씁니다.** 문장마다 `source`(`AI` · `EDITED` · `TEACHER`)가 붙습니다
- `covered_entry_ids` · `uncovered_entry_ids` — 반영된 · 반영되지 않은 일지
- `needs_review` · `review_reasons` — 공유 전에 사람이 봐야 하는 이유 (`다른아동이름` 등)
- `status` — `GENERATED` · `GATE1_PENDING` · `APPROVED` · `CONFIRMED` · `REVERTED` · `HOLD` · `REMOVED`

`summary_run_request` — 자동 요약을 끈 기관에서 선생님이 누른 [요약] 요청. 묶음마다 한 줄이고, `handled_until`까지 누른 요청은 처리한 것입니다.

#### `human_review` — 사람의 결정

1차 · 2차 검토의 결정을 누가 · 언제 · 무엇을 했는지 쌓습니다. `review_type`(`GATE1` · `GATE2`) · `target_type`(`SUMMARY` · `INSIGHT`) · `target_id` · `decision`(`APPROVED` · `CORRECTED` · `HOLD` · `REMOVED` · `REOPENED` · `CONFIRMED` · `REVERTED`).

어느 요약이 "수정 후 승인"인지는 이 테이블에 `decision = CORRECTED` 행이 있는지로 봅니다.

#### `child_context` — 아동 맥락

1차 검토에서 승인된 요약을 아이별로 쌓습니다. `summary_result_id` UNIQUE, 고치지도 지우지도 않습니다.

- `content` — **사람이 승인한 최종 글.** 보호자 일지와 기관 타임라인이 이것을 보여 줍니다
- **인사이트는 `content`가 아니라 `summary_result.claims`를 재료로 씁니다.** 이 행은 "어느 요약이 승인됐나"를 가리키고, 문장 · 근거 · 날짜 · 기관은 `summary_result_id`로 꺼냅니다
- 요약은 **선생님과 다음 돌봄을 맡는 다른 기관 담당자**가 읽는 기록이라, 돌봄 기관의 기록체로 씁니다. 보호자용 말투는 인사이트에서 정합니다

#### `insight_run` · `insight_result` — 인사이트

- `insight_run` — 아이 × 주마다 인사이트를 만든 실행 기록. (`child_id`, `period_from`, `period_to`, `revision`) UNIQUE
  - 인사이트가 0건이어도 `DONE` + `insight_count = 0`으로 남겨 다시 부르지 않습니다. 집는 것이 INSERT라 같은 실행이 겹치지 않습니다
  - `last_context_id` — 이 실행이 본 `child_context`의 최대 ID. 그 뒤에 승인이 더 들어오면 다음 판을 만듭니다
- `insight_result` — 인사이트 한 편. `situation` · `behavior` · `supports` · `content`, 근거 `claim_ids` · `source_entry_ids` · `source_institution_ids`, 도구로 찾은 근거 `looked_up_claim_ids`, `cross_institution`(두 기관 이상을 이었나). `status`는 `GATE2_PENDING` · `APPROVED` · `HOLD`

#### `sharing_history` — 열람 권한

인사이트는 보내지 않고 **열람 권한을 엽니다.** (`insight_result_id`, `receiver_type`, `receiver_id`) UNIQUE.

- `receiver_type` — `GUARDIAN` · `ORGANIZATION`. `sender_organization_id`는 2차 검토를 승인한 기관
- `read_at` — 처음 열어 본 시각. 열람 방식이라 이것이 유일한 흔적입니다
- `revoked_at` · `revoke_reason` — 동의가 꺼지거나 연결이 끊기면 권한을 거둡니다. 사유는 `sharing_consent`와 같습니다

#### `insight_notification` — 메일

아이 × 주마다 승인된 인사이트를 묶어 보낸 메일 기록. (`child_id`, `period_from`, `period_to`, `revision`) UNIQUE. `status`는 `RUNNING` · `SENT` · `NO_RECIPIENT` · `BLOCKED` · `FAILED`. 본문은 남기지 않습니다.

### 3.5 준비물 → [준비물 · 확인사항](../domains/checklist.md)

- `checklist` — 기관이 보낸 요청. `items`는 줄 목록 JSON, 내리면 `canceled_at`을 채웁니다
- `checklist_target` — 받은 아이마다 한 줄. (`checklist_id`, `child_id`) UNIQUE. 보호자 한 명이 확인하면 `confirmed_by` · `confirmed_at`을 채웁니다

## 4. 스키마 바꾸기

**운영 DB 스키마는 Flyway 마이그레이션만 바꿉니다.** 백엔드가 뜰 때 아직 적용하지 않은 파일을 차례로 실행하고, `docker` 프로필은 `ddl-auto: validate`라 엔티티와 테이블이 다르면 뜨지 않습니다.

- `V1__baseline.sql` — Flyway로 옮기기 전(2026-11-10) 엔티티가 만들던 스키마. 그 전부터 있던 운영 DB는 실행하지 않고 V1까지 적용된 것으로 표시만 했습니다
- `V2__sync_enum_checks.sql` — `ddl-auto: update`가 고치지 않아 운영 DB에서 낡아 있던 enum 검사 제약 7개를 엔티티와 맞춥니다
- `V3__drop_unused_status_values.sql` — 코드에서 쓰지 않는 일지 · 원본 기록 상태 값을 검사 제약에서 뺍니다

**스키마를 바꾸는 PR**

1. 엔티티를 고치고, 다음 번호로 마이그레이션 파일을 더합니다 (`V4__무엇을_바꾸는지.sql`). **머지된 마이그레이션 파일은 고치지 않습니다**
2. `./gradlew integrationTest --tests '*FlywayMigrationIntegrationTest'`로 빈 DB에 마이그레이션을 돌려 엔티티와 맞는지 봅니다
3. 이 문서의 해당 테이블과 맨 아래 변경 이력을 고칩니다

**마이그레이션을 쓸 때 주의할 것**

- **enum 값 추가 · 삭제** — 엔티티의 enum만 고치면 새 값 저장이 거부됩니다. 마이그레이션에서 `DROP CONSTRAINT IF EXISTS` 뒤 새 목록으로 `ADD CONSTRAINT`합니다 (`V2` 참고). 테스트는 Hibernate가 테이블을 새로 만들어 이 문제가 보이지 않습니다. 값을 지울 때는 그 값을 가진 행이 남아 있으면 마이그레이션이 실패하므로 배포 전에 운영 DB를 확인합니다 (`V3` 참고)
- **기존 행이 있는 테이블에 NOT NULL 컬럼** — 기본값을 주거나, NULL 허용으로 더하고 값을 채운 뒤 NOT NULL로 바꿉니다
- **행이 쌓인 테이블의 인덱스** — `CREATE INDEX CONCURRENTLY`로 씁니다. 그 문장만 담은 파일로 두면 Flyway가 트랜잭션 밖에서 실행합니다. 이를 위해 `spring.flyway.postgresql.transactional-lock: false`를 둡니다. 켜 두면 Flyway가 연 트랜잭션을 기다리며 영원히 멈춥니다
- **컬럼 삭제 · 이름 변경** — 되돌린 이전 이미지가 그 컬럼을 찾으면 뜨지 않습니다. 코드에서 먼저 안 쓰게 배포한 뒤, 다음 PR에서 지웁니다
- **되돌리기** — 이미지를 되돌려도 실행된 마이그레이션은 남습니다. 반대 작업을 하는 새 마이그레이션을 더합니다. 위험한 변경 전에는 백업합니다 ([인프라 문서](../../infra/README.md#db-마이그레이션))
